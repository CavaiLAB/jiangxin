    #协作约定

    状态：已定。2026-11-26 改成两个仓库的约定；当时的提议，产品负责人 2026-11-27 都认可了，同一天也答了此前待定的事，答复写进了各节。第 2 节「整理者」的说法、第 3 节「延期」「按提议推进」两种标法、第 10 节的分法，是照这次答复补的，属整理时的做法。延期的和先放着的事列在第 10 节。

    #1 仓库与分工

    • 现在只剩两个项目（已定）：产品 jiangxin，企业级框架 kun。都在 CavaiLAB 下，所有者是 CavaiLAB（已定）。
    • 另外两个仓库不在维护的范围里：前端框架 Qian 的仓库已归档，只读，已发布的包留着（已定）；SanYuanAgent 的仓库保留，暂不维护（已定）。
    • 两个仓库都由产品负责人负责（已定）。
    • 平台级的事在 jiangxin 里改：平台做什么、总体架构、路线、名称、匠心与 Kun 的分工。
    • 产品的代码在 jiangxin（已定）。产品指 Agent 工作区的 Web 端与桌面端、管理端、产品的插件、部署清单；现在有什么，见平台主页的「现状」。
    • Kun 是通用的组件，不负责任何业务；最终的界面放在匠心，也可以放到另一个仓库（已定）。最终的界面、管理端和带业务的 Kun 组件都放 jiangxin（已定）。登录、工作区和管理端等产品页面统一放到 jiangxin 重新设计，旧布局和样式可以淘汰；Kun 保持现有基础框架和接口，继续负责认证、会话和权限（已定）。
    • 两个仓库之间只经契约和发布出来的包协作，不做跨仓库的源码引用；匠心按钉住的版本装 Kun 发布的包与镜像，Kun 不依赖匠心（已定）。
    • DSH 是上游的项目，不是我们的仓库。匠心按钉死的版本装它发布的 npm 包，不改它的源码。
    • 要改代码，去代码所在的仓库提 PR，按那边的规则办。

    #2 分支与合并

    • main 是主干，受保护，不直接推送。
    • 改动走分支和 PR，CI 通过、合并前至少一人复核之后合入（已定）。现在由整理者复核，产品负责人发话以后合并（已定）。整理者指整理这些文档、把要定的事列给产品负责人、复核改动的那一方。
    • 提交信息写清改了什么、为什么；有任务编号的带上编号。
    • 建仓期间的初始文档是由建仓的人直接推到 main 的，那以后都走分支和 PR。

    #3 方向怎么定

    • 方向性的事由产品负责人定。定了的写进对应的文档，标「已定」；整理时的读法与做法、提议、待定也照实标明，不把提议写成已定。他说了条件、条件由整理时的评估来判定的，标「带条件」，写明条件是什么、评估的结论是什么。定了先放着、等别的事的，标「延期」，写明要先有什么。定了到时候照提议做的：做法已经在答复里写明的，直接标「已定」；整篇照提议、或者细节还要到时候再定的，标「按提议推进」，整篇的在篇首写明。
    • 本仓库不放决策记录，文档里不写裁定的编号（已定）。裁定另有记录，不放在公开的仓库里；公开的文档只写现行的结论（已定）。
    • 只影响 Kun 的决定，在 Kun 的仓库里登记成决策任务（已定）。
    • 已定的事不在实现里悄悄改。有异议，提出来等产品负责人定。
    • 纯技术的选择，不改变产品的行为、不改对外承诺的，由整理者评估后直接定，记下来，事后告诉产品负责人（已定）。
    • 要产品负责人定的事，攒成一张表一次问；卡住工作的单独问（已定）。
    • 纯技术的选择交给整理者，照上面那一条定，编码代理不自行定。别的需要人拍板的问题，编码代理也不自行决定，写进对应文档的「待定」一节或第 10 节的清单，等人裁定。

    #4 任务管理

    已定：任务跟代码走，各仓库各有一份任务目录，jiangxin 放汇总看板。匠心开工时，在本仓库建一个和 Kun 一样的任务看板（已定）。现在只有 Kun 有任务目录，匠心的任务看板和汇总看板都还没有建。

    • 现状：Kun 的任务文件和看板在仓库根目录的 pm/。一个任务一个 Markdown 文件，看板从主干的 pm/tasks/ 生成。人和编码代理用同一套命令。
    • 任务要重新整理（已定）：照路线第 2.2 节的十二条工作线重排 Kun 的看板，先做权限的远程接口和模型服务的接口这两份契约；界面与渲染器归匠心，数据描述的后端、流程、等人输入归 Kun（已定）。

    #5 文档

    • 文档用中文。
    • 不写参考平台和对标项目的名字。
    • 说现状的时候写清是「已有」还是「规划」，不把规划写成已经实现。
    • 不放密钥和内部地址，不放还没修复的安全问题的细节。
    • 平台只按一句话描述（已定）：企业级的 AI 原生平台。人用自然语言说清要什么，智能体把它落成可运行的系统；系统上线后在人的反馈里继续改进。
    • 下面几种说法 2026-11-26 起不再用：平台此前的一条理念，连同解释它的章节、图和词条（已定）；「两种角色」（已定）；「三个框架」（已定）。随它们一起不再用的还有（已定）：与那条理念同一批的几个叫法；拿两种角色当角色名的那两个称呼；把 jiangxin 叫作「组合体」、说它交付「两样东西」。
    • 讲结构时这样写：匠心是产品，Kun 是企业级框架，Agent 运行时用 DSH。说到人，用平常的话：用平台的人、做开发的人、管理员。这两条已定。
    • 「形态」这个词只用来说部署的两种形态：带不带模型推理。分这两种是已定的；这个词只这样用，是文档的约定。
    • 匠心根据工业填报、管理和 Agent 工作区的实际场景制定自己的设计规范，Ant Design 仅供参考（已定）。底稿见设计规范，等产品负责人看过才算数。
    • 前后端都要有面向开发者和 Agent 的文档、MCP 和 CLI 入口，让人能找到匠心组件、Kun 接口和可运行的示例（已定）。现在有什么、缺什么，见在平台上做开发第 10 节。
    • 文档里要写清楚四件事（已定）：平台做什么与设计理念、重点是工业智能制造；DSH 更新之后做什么；别人怎么在平台上做开发；DSH 怎么与企业级平台交互。各在哪一篇，见平台主页的「文档」。
    • 文档站用 Rspress，搭在 jiangxin 仓库的 website/ 下（已定）。文档以 Markdown 放在仓库里，那是唯一的一份。站点放哪些内容、怎么构建，见 website 的说明。
    • Kun 要有单独的网站，放使用文档和给大模型用的文档（已定）。网站的域名是 kun.2017601.xyz（已定）。网站给大模型的入口先不接进 DSH，等 Web 端的工作区服务（已定）。等公网入口、证书和站点内容验收通过，再把本仓库导航与正文里指向 Kun 文档的链接切到网站上；在那以前照旧指向 Kun 的仓库。
    • 图用 Mermaid 语法写，在 GitHub 上直接能看；站点用 Pele 把它渲染成静态图（已定）。
    • 每个 PR 上 CI 都会构建站点，死链、失效的锚点和画不出来的图会让它失败。提交前也可以在 website/ 下自己构建一次。
    • 站点部署在内网，合并到 main 后由 CI 发布（已定）；部署清单在部署仓库。现在不在 CavaiLAB 下另建部署仓库（已定）。

    #6 质量门禁

    仓库门禁
    Kun警告即错误；公共 API 清单；依赖方向检查；一致性测试；契约与样例的一致性检查；单元测试与集成测试
    匠心现在 CI 只构建文档站。产品代码的检查在本机跑：各包的类型检查与单测、桌面壳的单测、发行目录的启动前检查，命令见 AGENTS.md。这些检查要接进 CI（已定），还没有做

    代码要符合 ISO 等国际相关标准（已定）。遵循的标准里的十个方面，做标准对照和工程检查（已定）；先补四项检查：密钥扫描、静态安全扫描、许可白名单、覆盖率阈值（已定）。以等保二级为建设目标，并纳入国密要求，单独跟踪（已定）。

    #7 版本与发布

    什么版本发布位置
    Kun一条日历版本线（已定）内核包通过可信发布（OIDC）发到 nuget.org，平台包发到 CavaiLAB 的公开 GitHub Packages 并关联 CavaiLAB/kun（已定）。当前的稳定版见 Kun 的发布页
    匠心工业智能体平台日历版本号：vYYYY.M.D 正式版，vYYYY.M.D-N 补丁版，vYYYY.M.D-beta.N 测试版，月和日不补零，构建时注入（已定）。各包 package.json 里的版本号是包自己的内部版本，另算延期，到第一次发布时再定。还没有发布过
    DSH上游的版本号，钉死在 distribution/package.json，不写范围上游发布在 npm 上。升级的做法见 DSH 更新之后做什么

    以后 Kun 的客户端包（远程授权接口的 .NET 与 TypeScript 包等）一做出来就公开，发到 nuget.org 与 npmjs，装的时候不用令牌（已定）。发布要用这两处的账号或发布用的令牌，由产品负责人开通或提供。

    哪个版本的匠心配哪个版本的 Kun 与 DSH，由 jiangxin 维护一张版本矩阵（已定）。

    Qian 不再发新版，已发布的包留在 GitHub Packages 上，继续可以安装（已定）。还在用更早的旧运行时或旧插件 SDK 的项目，换成 @cavailab/qian-runtime@0.2.1 与 @cavailab/qian-plugin-sdk@0.2.1，更新依赖和锁文件；做法见 Qian 仓库里的迁移指南。

    #11 公开

    仓库是公开的（已定）。

    公开的仓库里不放这几类内容：

    • 产品清单与建设状态。
    • 对私有的来源产品的功能盘点与差距描述。只写可以承接的能力类别。
    • 私有产品的名字。要提到时写「私有产品」「原来的私有仓库」这类说法；引用的原话里有，就换成方括号里的说法并在文首说明。提交历史、导入时过渡目录快照中的原件与任务日志、迁移工具，以及源码里带着这个名字的标识（环境变量名这类，随以后的改名处理）不在此列。
    • 改名的经过。前端框架的旧名、旧仓库的地址都不写，也不用「原」加框架名指代来源；讲位置写路径或现在的名字，指向历史文件的链接用新仓库里钉住提交的链接。决策记录与历史文档、给使用者的迁移指南、改名与导入工具，以及提交历史、导入时过渡目录快照中的原件与任务日志、源码里带旧名的标识（随以后的改名处理）不在此列。
    • 密钥、内部地址、还没修复的安全问题的细节、私有仓库的内部实现细节。
