    Qian 架构决策记录（ADR）索引
    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #2026-11-20 产品裁定

    本次裁定接着 2026-11-20 迁移与发布裁定 编号，记录产品负责人同一天对「匠心工业智能体平台」的决定：Agent 运行时、界面外壳、客户端、名称与版本号、代码放在哪个仓库。

    引号里是原话，方括号里是整理时替换的说法：原话里提到的私有产品，按协作约定第 11 节换成「［私有产品］」。本文第 1 节只记已定的事；没有定的在第 3 节，标「提议」或「待定」。

    DSH 是一个开源的智能体运行框架，以 npm 包 @deepseek-ai/dsh 发布，按 MIT 许可使用。组合体现在钉的版本是 0.2.2-rc.5，见 distribution/README.md。

    编号产品负责人裁定原话
    P37Agent 运行时用 DSH。平台现在在做迁移，这一条是最终定下来的。原话还说前期可以完全基于它；第一版是不是全部基于 DSH，没有定，见第 3 节「平台现在做迁移工作，但是最终定下来了。Agent Runtime 使用DSH」「前期可以完全基于它」
    P38界面外壳用 DSH 自己的客户端，网页与桌面都是。前端框架 Qian 冻结在 0.2.1；组件以后缺哪个，按 DSH 的写法迁进我们自己的界面包。另一种方案是保留 Qian、按 DSH 的规范改，没有选「DSH 当外壳」（答两种外壳方案选哪个：一是界面用 DSH 自己的客户端，Qian 冻结在 0.2.1，组件以后缺哪个按 DSH 的写法迁进自己的界面包；二是保留 Qian、按 DSH 的规范改）
    P39客户可能用到两个端：Web 端和客户端（桌面）。管理端先不做，目录先建好「客户有可能会有两个端web端和客户端，管理端的话先不做,可以创建好文件夹。」

    #3 提议与待定

    下面这些产品负责人没有定。

    事项现在的情况状态
    第一版是不是全部基于 DSH倾向是全部基于。原话是「前期可以完全基于它」待定
    SanYuanAgent 以后怎么接没有方案。产品负责人的倾向是不放弃自研的 Agent 框架，原话是「我不想放弃，我想兼容两套 Agent 框架，或者后续兼容更多的 Agent SDK」。P2、P3、P8 把它定为平台的第三个框架、理念里的「全智」、三种形态的大脑；术语表把 Agent 框架写成 SanYuanAgent 加 Agent 平台。P37 之后这几处怎么讲，一并待定待定
    登录、租户、策略、审计由哪个后端提供没有定待定
    一个用户一个 DSH 实例建议，没有确认。理由：DSH 的一个实例里只有一种调用方身份，就是实例的主人；会话里没有用户和租户；设置、插件、凭据整个实例共用。所以多用户靠每人一个实例（一个容器、一台虚拟机或一台桌面）隔开，登录、租户、授权放在实例外面的门户里，实例里的插件只做护栏提议
    包名前缀 @jx/现在的代码用它提议
    放不下全称的地方用短名「匠心」程序坞、托盘、窄标题这类地方提议
    桌面客户端走哪条路比较过两条：甲，自己写一个薄的 Electron 壳，里面跑已发布的 DSH（apps/desktop/ 是它的原型）；乙，从钉死的源码构建 DSH 上游的桌面壳，用补丁换品牌。建议走甲。对比见 apps/desktop/README.md 的「两条路线」提议
    普通用户要不要插件页定了之后，再定发行配置里插件管理那几行怎么配待定
    移动端仓库与归属原来提议网页、桌面、移动三种端；P39 说的是两个端待定
    现有的应用外壳怎么办见第 2 节最后一行待定（11 月 20 日）；本次迁移的验收方式已于 11 月 21 日按 P42 确认，代码以后的用途仍待定
