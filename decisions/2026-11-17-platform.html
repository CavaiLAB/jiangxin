    Qian 架构决策记录（ADR）索引
    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单
    组件模型 v2：一切皆插件、声明式组件、一键安装、目录市场

    #2026-11-17 平台级裁定

    记录产品负责人 2026-11-17 对平台的裁定，引号里是原话，方括号里是整理时替换的说法。本文只记已定的事；待确认的事在各文档的「待定」里。

    #1 已定

    编号裁定原话
    P1总名是匠心智能体平台，不再使用 Yi。它是企业级的框架，不面向个人消费者；从拖拽式的低代码构建转为基于原生 AI、用自然语言构建系统「我现在要做的事情不是一个 toC 的，它是一个企业级的框架」「基于原生 AI，可以完成基于自然语言的系统构建」「所以我把这个系统取名叫匠心智能体平台，不再使用 Yi」
    P2平台之下三个框架：Kun；Qian，即现在的前端框架 yue；SanYuanAgent，即私有产品里的 Python Agent 引擎「下面包括 Kun、yue（后期改名为 Qian）、［Python Agent 引擎］……改名为 SanYuanAgent」
    P3理念是三元全智生命体：平台（企业级框架）是三元，SanYuanAgent 是全智，平台最终演化出更多的生命体「基于平台就是企业级的框架，全智是 SanYuanAgent 框架，最后平台可以进化更多的生命体」
    P4底座不变：K8s、云原生、微服务。原来的定位没有问题，这次是拆分与聚合「之前的整个框架的定位是没有问题的，只是把它做一些拆分和聚合」「以前还是太乱了，现在可能需要更多人参与或协同」
    P5迁到 CavaiLAB 下的新仓库：一个主页仓库加各子项目，名字不带前缀，jiangxin、kun、qian、sanyuan-agent；先对内（私有；可见性后来改了，见 P19）；先建仓库写框架级文档，代码之后慢慢迁。主页是 jiangxin 仓库的 README「项目需要一个 Github 项目主页+各个子项目」「先不要完全的迁移代码，先创建库吧，后期慢慢进行迁移，但是可以写文档。主要是框架级的文档」
    P6一切皆插件是统一的原则；目标是社区里现成的开源 Agent 组件能装进平台直接用「一切皆是插件 everything-is-a-plugin」
    P7每个人有一个或多个 Agent；Agent 之间沟通的机制由平台定义；发给每个 Agent 的内容要由人审核；可以承接私有产品里已有的实现「每个人都有一个或多个 Agent」「每个 Agent 和其他 Agent 沟通的机制需要进行定义，就是发给每个 Agent 的内容需要人来进行审核」
    P8工蜂、章蜂、群蜂对应工站、产线、工厂；SanYuanAgent 是它们的大脑，要提供给工站、产线、工厂「工蜂、章蜂、群蜂 对应工站、产线、工厂」「SanYuanAgent 就是他们的大脑。需要提供给工站、产线、工厂」
    P9文档站继续用 Rspress，不换工具。原仓库的文档站现在就是 Rspress「文档 还是使用 rspress」
    P10现在就在 jiangxin 仓库里搭 Rspress 文档站。怎么把几个仓库的文档聚进来不在这条裁定里「现在搭」（答「要不要现在在 jiangxin 仓库里搭 Rspress 文档站」）
    P11文档站部署到内网的 K3s，合并到 main 后由 CI 自动发布「部署到 K3s」「CI 自动发布」
    P12站点上的图改用 Pele 渲染。图的源码不变，仍然是 Mermaid 语法「改用 Pele」（答「站点的图表改用 Pele 渲染吗」）
    P13SanYuanAgent 是一个独立运行的 SDK。每个端都要用到它，包括机器人这类边缘设备；装上就能用。它与 Kun 怎么往来、与模型服务怎么往来，要设计出来「SanYuanAgent 这应该是一个独立运行的 SDK，因为它是一个后面每个端都需要用到的例如机器人等边缘设备。应该安装上就可以用」「所以你要考虑和 Kun 这个框架如何去交互，如何和模型服务进行交互」
    P14模型服务由 Kun 提供；机器人这类设备本地可能还有小模型「因为后面模型服务也有 Kun 提供，但是还有可能机器人本地也会有小模型」
    P15SanYuanAgent 先迁核心。Python 引擎分核心、服务层、媒体适配层三部分，核心先迁入 sanyuan-agent，另两部分随后「首先迁移核心的 Agent 框架 到 SanYuanAgent」
    P16核心的名字：发行名 sanyuan-agent，导入名 sanyuan_agent，命令行 sanyuan-agent，环境变量的前缀改为 SANYUAN_AGENT_。服务层与媒体适配层的名字没有定选「sanyuan-agent」（答「核心迁入 SanYuanAgent 后叫什么名字」）
    P17核心带历史迁入。这一步不动原仓库：原仓库里那一份照旧在用；改为依赖新包、删掉旧的那一份是以后单独的一步，过渡期它上面的改动同步到新仓库选「带历史」（答「核心的提交历史带不带进新仓库」）；选「这一步先不动［原仓库］」（答「核心迁过来之后，［原仓库］里原来那一份怎么办」）
    P18核心保持 Apache-2.0，许可文件里对所借鉴开源项目的附加声明保留。服务层与媒体适配层的许可没有定选「保持 Apache-2.0」（答「核心迁入后用什么许可」）
    P19四个新仓库改为公开，是产品负责人本人在 GitHub 上改的。核心的迁移结果直接推到公开的仓库。P5 的「先对内」由此改写「我手动改成的 public ，直接推送吧」
    P20Kun 与原 Qian 的后端现在开始迁入 CavaiLAB/kun，改名在迁移过程中做完。合并后的仓库由此定为 CavaiLAB/kun「Kun 和 Qian 开始进行迁移，迁移过程中进行改名，迁移至（https://github.com/CavaiLAB/kun）」
    P21前端现在开始迁入 CavaiLAB/qian，改名在迁移过程中做完，不再等后端按域归并的最后一批「前端开始进行迁移，迁移过程中进行改名，迁移至（https://github.com/CavaiLAB/qian）」

    同一天，产品负责人在来源仓库里接受了后端的合并蓝图（idadawn/qian 主干的 docs/adr/ADR-023-kun-qian-merge-blueprint.md，裁定是同仓库 pm/tasks/S1-DEC-036.md 的 D1–D14）：原 Qian 的后端并入 Kun，包名并为 Kun.*，两档分层，许可全部改 MIT，租户号用 Guid，前端由 yue 更名为 qian，运行期字面不改，按阶段落地。这些在本仓库里一律按已定写。

    现行决策现行的写法出入
    模型服务网关（ADR-015）模型调用都过模型网关，应用不许绕开它直连模型P14：设备上的本机小模型过不了模型网关。提议登记成一条明确的例外，只限设备本机地址上的模型，用量由引擎上报
