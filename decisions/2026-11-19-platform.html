    Qian 架构决策记录（ADR）索引
    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #2026-11-19 平台级裁定

    记录产品负责人 2026-11-19 对平台的裁定，编号接着 2026-11-17 平台级裁定。引号里是原话，方括号里是整理时替换的说法。本文只记已定的事；待确认的事在各文档的「待定」里。

    #1 已定

    编号裁定原话
    P22平台上分两种角色。平台开发围绕 Agent 框架与企业级应用平台做开发。普通开发或最终用户基于 Agent 平台，在企业级框架上构建自己需要的软件；Agent 框架与企业级核心的开发不由他们负责，他们只使用工具。平台开发使用的工具可能是通用的编码智能体「我们会分为两种角色」「第一种角色：平台开发，主要围绕 Agent 框架和企业级应用来进行开发」「第二种角色：普通开发或最终用户，他们能基于这个 Agent 平台，在企业级框架上构建自己所需要的软件形态」「有一个前提，就是 Agent 框架的开发和右侧企业级核心开发他们不负责，只是负责使用工具」「我们开发平台使用的工具可能会是 Claude、Codex」
    P23平台开发交付两样东西：一个 Agent 框架，一个企业级应用平台。两者互补，最终是一体化的产品。jiangxin 仓库就是组合体：Agent 加企业级框架「平台开发出来的是一个 Agent 的框架和企业级的应用平台」「左侧是一个 Agent 的框架（完整的［桌面端智能体应用那样的］，当然也可以办公），右侧是企业级框架」「这就形成了一个互补的关系」「最终我们是一体化的产品」「jiangxin repo 就是组合体（agent + 企业级框架）」
    P24最终用户的使用界面是 Agent 平台。Agent 平台的客户端基于企业级框架。企业级应用平台不另做一套入口：Agent 平台收起对话区，就是它「最终用户的使用界面应该就是 Agent 的平台」「Agent 平台客户端 要基于企业级框架」；「十一项都按推荐定」（第 6 项，见第 2 节）
    P25最终用户有两种扩展：基于企业级应用平台开发插件；给 Agent 增加组件。平台提供所需的基础组件，并内置智能体、知识库模板等内容。企业级框架里有应用市场，可以通过 Agent 框架开发、上架「他可以自己开发插件，基于企业级的应用平台，也可以给 Agent 增加组件」「平台会提供所有需要的基础组件，并且内置了像智能体、知识库模板等内容，让他们能通过 Agent 框架快速实现自己的业务」「内部也会有应用市场，可以通过 Agent 框架开发上架」
    P26所有发布的应用（插件）之间可以互相通讯。缺省：应用提供的能力与事件在目录里看得到；调用与订阅按声明、经批准放行「所有发布的应用（或者叫插件可能更合适），它们之间都是可以互相通讯的」；「十一项都按推荐定」（第 4 项）
    P27遗留的历史系统要能集成进企业级框架，并融合进 Agent 框架。历史系统在企业内网的，连接器的执行部分装在内网，只向外连「还需要考虑到一些遗留的历史系统……这些系统也有可能集成到这套企业级框架里。需要考虑这部分怎么去融合，也就是怎么通讯并融合到整个 Agent 框架里面」；「十一项都按推荐定」（第 9 项）
    P28每个 Agent 发出去的内容都要由人审核。起步出站、入站两道都必审。「发出去」包括三类：发给别的 Agent、发给别人、写外部系统「后续每个人都会拥有一个或几个 Agent，这些 Agent 可以进行协同办公。但前提是，每个 Agent 发出去的内容都需要人来进行审核」；「十一项都按推荐定」（第 2、3 项）
    P29给「我的 Agent」长期挂组件，加一种 Agent 一级的范围「十一项都按推荐定」（第 7 项）
    P30组件里新增一种「知识库」内容「十一项都按推荐定」（第 8 项）
    P31路线重排，最小的一圈提前。顺序见路线与迁移第 2.1 节的里程碑「十一项都按推荐定」（第 10 项）
    P32拖拽设计器缓做。先让 Agent 写，设计器以后作为第二种编写方式「十一项都按推荐定」（第 11 项）
    P33最终交付给客户的，可以是多租户的版本，也可以是单租户的版本「最终交付客户的可以是一个多租户的版本，也可以是一个单租户的版本」
