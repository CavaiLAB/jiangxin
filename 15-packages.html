    #包与应用的去向

    状态：2026-11-27 新写。产品负责人同一天给了产品页面的新方向（已定）：Kun 保持现有基础框架和接口，继续负责认证、会话和权限；登录、工作区和管理端等产品页面统一放到匠心重新设计，旧布局和样式可以淘汰；次序是先列清各个包的去向，再修订文档，再用登录页跑通前后端流程。这一篇是第一步里匠心这一半的清单。

    「到了哪一步」一列是事实，按目录里的文件与构建脚本核对过，依据写在同一行。「去向」一列里标「已定」的出自产品负责人的裁定，其余是整理时的提议，没有拍板。Kun 那边的包、已发布的包、文档、示例和站点导航，在 Kun 的仓库里整理，这里只列匠心要接替的几样，见第 2.3 节。

    #1 怎么读

    「到了哪一步」分四档：

    档指什么
    有代码能跑有源码和能执行的脚本或检查，照它的说明能在本机跑起来
    只有骨架有目录与配置，没有能用的功能
    只有文档目录里只有说明
    还没有目录还没有建

    「去向」分五种：照旧；重新设计（留着这个位置，内容按新的方向重做）；新建；归并（并进别的包或目录）；归档（不再改，留作参考或退掉）。

    #2 清单

    #2.1 应用与服务

    项是什么到了哪一步依据去向
    apps/web/Web 端在本机的启动脚本，和放在反向代理后面的验证有代码能跑：本机起一个单人的实例，用假模型start.sh、dev.sh 调发行目录的启动器 distribution/bin/jx-dsh；proxy-test/run.sh 在 Docker 里做实际转发的验证照旧，留作本机试用与反向代理的验证。按人托管的那部分放进新建的工作区服务（工作区服务归匠心，已定）
    apps/desktop/桌面端：薄的 Electron 壳，里面跑发行目录里的 DSH有代码能跑，原型，没有发布过src/ 下是壳的主进程与页面；package.json 里有 dev、test、smoke、pack:mac；tests/ 下有单测照旧。桌面端走薄壳（已定）
    apps/console/管理端只有文档目录里只有 README.md新建。放本仓库、随生成应用的最小一圈开始做（已定）；照匠心的设计规范重新设计，Kun 里现有的租户与成员页、平台控制台、旧的应用外壳在这里重做（已定）
    认证页登录、选择租户（界面上叫「选择工作空间」）、强制改密、找回密码这一族页面还没有本仓库里没有。现在用的是 Kun 里现有的那一套新建。页面放匠心重新设计（已定）；放在哪个目录、怎么托管是提议，见第 3 节
    工作区服务接工作区的域名，用 Kun 的登录组件认人，把登录的人送进他自己的 DSH 实例还没有本仓库里没有新建。归匠心，用 C# 写，基于 Kun 的包（已定）；放在哪个目录是提议，见第 3 节

    #2.2 包、插件与样板

    项是什么到了哪一步依据去向
    packages/brand-theme/（@jx/brand-theme）品牌包：把 DSH 界面上的名称、标志、主题色和文案换成匠心的有代码能跑，装在发行目录里src/ 下有宿主与浏览器两半；pnpm run check 跑类型检查、单测、构建；发行目录里有它的打包件和生成的补丁 70-jx-brand-theme.yml照旧。配色现在是从 logo 取样的初稿，设计规范定稿以后跟着改（提议）
    packages/enterprise-workbench/（@jx/enterprise-workbench）企业插件的样板：自己的后端接口加一个整页面板，设备台账的数据是假的有代码能跑，作为样板装在发行目录里src/ 下有宿主、浏览器两半和共用的协议；tests/ 下两组单测；发行目录里有打包件和补丁 80-sample-jx-enterprise-workbench.yml照旧，当写插件的模板。包的说明写着正式发行前从发行目录拿掉
    packages/ui-kit/（@jx/ui-kit）界面组件包：shadcn 生成的基础组件、手写的数据表格和抽屉，和插件的构建脚本 jx-dsh-plugin-build。源码库，不是插件有代码能跑src/ 下的组件；tests/ 下三组单测；tools/build-plugin.mjs 是构建脚本照旧，是匠心各处页面共用的组件层。基础组件用 shadcn 加 Tailwind，放这个包（已定）；做成一个插件、各插件共用一份（已定，工作线 9）。认证页和管理端不在 DSH 里跑，要用它得先把依赖 DSH 的部分分开，见第 3 节（提议）
    以后可能加的四个包：dsh-compat、enterprise-auth、enterprise-policy、enterprise-auditDSH 实例一侧的兼容层、登录对接、工具护栏、审计只有文档只写在 packages 的说明里，名字和分工是提议照旧作提议。enterprise-auth 管的是 DSH 实例一侧，认证页不放进它（提议）

    #2.3 Kun 里由匠心接替的页面

    Kun 的仓库里有几样产品页面，都是 Kun 的 pnpm 工作区里不发布的私有包，装的是已归档的 Qian 发布的包。新方向以后由匠心接替；它们在 Kun 里留不留、什么时候退，由 Kun 的仓库列，退掉的时点到时再问产品负责人。

    Kun 里的是什么匠心这边接替的
    packages/qian-identity-ui认证页族：登录、多租户选择、强制改密、连接器落点。构建产物由身份服务在 /login 下同源托管匠心的认证页（已定放匠心重新设计）。新页面跑通以前登录照它用，这是整理时的读法
    packages/qian-tenancy-signup-ui租户自助开通的申请人公开页与平台运营的申请页申请人公开页也是给人看的产品页面，提议随认证页一起在匠心重做；运营的申请页并进管理端（提议）
    apps/qian-shell、packages/qian-shell-kit、packages/qian-tenancy-ui旧的应用外壳、外壳的接线、租户与成员页管理端。旧外壳、租户与成员页在匠心的管理端里重做（已定）

    #2.4 发行、工具与站点

    项是什么到了哪一步依据去向
    distribution/发行目录：钉死版本的 DSH、以打包件装入的插件包、配置补丁、启动器与启动前检查。Web 端和桌面端共用有代码能跑npm ci --ignore-scripts 以后 node bin/jx-preflight.mjs 能过；vendor/ 下两个打包件；patches/ 下 11 个配置补丁；scripts/vendor-packages.sh 重打插件包照旧。检查接进 CI（已定），还没有做
    patches/对 DSH 源码的补丁只有骨架：两个样例，没有用于任何构建两个 .patch 文件；apps/desktop/scripts/check-patches.sh 只检查它们能不能打上照旧。原则上不改 DSH 的源码
    contracts/以后从 Kun 的契约生成的类型只有文档目录里只有 README.md照旧占位。认证页要调的账号接口进了 Kun 的公开契约以后，类型从那里生成到这里（提议）
    brand/匠心 logo 的原图，不在任何代码许可之内有原图source/ 下五张图照旧。认证页、管理端和品牌包用同一份原图（提议）
    tools/mock-model/本机的假模型服务有代码能跑server.mjs，只用 Node 自带模块照旧
    tools/check-shell-vars.mjs查 shell 脚本里变量后面紧跟中文的写法有代码能跑单个脚本，AGENTS.md 里写了什么时候跑照旧
    tests/egress/外联检查：在不通外网的容器网络里看实例想连哪些地址有代码能跑，要 Dockerrun.sh、build-images.sh 与三份镜像定义照旧
    website/文档站，只放本仓库的文档有代码能跑，CI 在构建pnpm build；.github/workflows/docs-site.yml 在每个 PR 上构建、合并后发布照旧。加上给大模型的入口，见在平台上做开发第 10 节（提议）
    .github/workflows/CI有，只有文档站一个工作流docs-site.yml照旧。产品代码的检查接进 CI（已定），还没有做
    deploy/产品的部署清单还没有目录没有建新建。放这里、只有一套、企业版与单机版共用（已定）
    docs/平台的文档有本站照旧

    本仓库里没有 Qian 的包要归档：匠心的代码不装 @cavailab/qian-*。

    #3 认证页、管理端与工作区各在哪

    放在哪状态
    认证页提议新建 apps/auth/：构建成静态页面，由 Kun 的身份服务在自己的域名下同源托管页面放匠心重新设计、认证与会话由 Kun 负责，已定；目录与托管方式是提议
    管理端apps/console/放本仓库已定，目录已建；还没有代码
    Agent 工作区界面是 DSH 自己的客户端（已定），从 distribution/ 启动；Web 端前面是工作区服务工作区服务归匠心、用 C# 写已定；提议放 services/workspace/，和 Node 的几个应用分开

    认证页为什么提议单独一个应用、交给身份服务托管：

    • 凭据只在身份服务的域名里。 Kun 的认证页规格（草案）写的原则是：密码、验证码、选择租户用的票据只在身份服务同源的页面与 HttpOnly 的 cookie 里流转，不经过别的应用的脚本。所以认证页要和身份服务同源。
    • Kun 现在就能托管别人构建的认证页。 身份服务有一个配置项指向认证页的构建产物目录，在 /login 下同源托管，现有的那一套就是这样装上去的。照现在的代码看，换成匠心构建的产物，不用为此改 Kun 的代码；新页面要守它的托管约定：产物以 /login/ 为基路径，根上要有 index.html，/login、/login/select-tenant、/login/connector/{connectorId} 这些页面路由都回到这个入口。见 Kun 身份服务的说明。
    • 不放进管理端。 管理端在自己的域名上、过 Kun 的网关，认证页在身份服务的域名上；普通用户登录以后直接进工作区，不经过管理端。管理端随生成应用的最小一圈才开始做，登录页要先跑通，分开以后互不等。

    三者共用什么（提议，除标了已定的）：

    共用的怎么用
    基础组件@jx/ui-kit，shadcn 加 Tailwind（已定）。它现在按 DSH 插件写：抽屉的壳是 DSH 的弹窗，数据表格用了 DSH 的控件，几处样式照 DSH 量出来，构建脚本产出的是 DSH 插件。认证页和管理端不在 DSH 里跑，要先把不依赖 DSH 的基础组件和依赖 DSH 的部分分开，再各自打包
    设计规范同一份，见设计规范。规范还是底稿
    品牌同一份 logo 原图与产品名（已定用匠心的名称与 logo）。品牌包是 DSH 插件，认证页和管理端不装它，从 brand/ 取原图，配色取设计规范里的那一套
    登录状态照 Kun 现有的做法，各自做依赖方：浏览器在身份服务那里登录一次，身份服务的域名上留下单点登录的会话；管理端经 Kun 的网关、工作区服务用 Kun 的登录组件，各自走授权码流程换自己的会话，已经登录过就不用再输一遍。令牌不进浏览器的脚本。哪个页面都不另存一套用户

    #4 用登录页跑通前后端：匠心这一侧先要有什么

    用登录页跑通前后端流程（已定）。下面是匠心这一侧要先有的东西，是提议；最后一列写明哪几样要等 Kun。

    要先有的是什么等不等 Kun
    登录页的设计设计规范里登录页的模板：版式、状态、错误态、深浅色、中英文不等
    认证页的应用apps/auth/：构建、本机预览、单测，产物能被身份服务托管不等
    能在 DSH 以外用的基础组件见第 3 节「基础组件」一行不等
    调哪些接口身份服务的账号接口（在 /api/identity 下：取防伪令牌、登录、选择租户、改密、列连接器等）与 OpenID Connect 的协议端点。接口已有，写在身份服务的说明里要等：账号接口还没有进 Kun 的公开契约。进了以后从契约生成类型放 contracts/
    错误怎么显示结构化错误按 Kun 冻结的契约；页面按错误码分支部分要等：认证相关的错误码在 Kun 的认证页规格里还是提案，要先登记
    本机怎么起构建认证页，起 Kun 的身份服务或本机联调的宿主，让它托管这份产物，再起一个最小的依赖方要等：托管目录怎么配、本机联调的宿主怎么起，要写进 Kun 的使用文档
    登录以后到哪已定的是普通用户进工作区、管理员进管理端、入口页兜底。跑通这一步时工作区服务和管理端都还没有，用一个最小的依赖方页面显示当前的人与租户、能登出不等
    品牌新页面直接用匠心的名称与 logo不等
    验收浏览器打开依赖方，跳到匠心的登录页（在身份服务的域名下），账号密码登录；有几个租户时选择租户；回到依赖方，显示当前的人与租户；登出。密码错、限流这些错误态照 Kun 的规则显示；页面里没有 Qian 的包；过一遍自动的无障碍检查不等

    认证页的其余几页排在登录页跑通以后：2026-11-27 的答复里定了先做找回密码与验证码登录，其余随后；和新方向合起来，登录页先跑通，再做这两样，这是整理时的读法，见路线第 2.4 节。
