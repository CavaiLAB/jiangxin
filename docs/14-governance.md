# 协作约定

> 状态：提议，2026-11-26 改成两个仓库的约定。多数条目沿用已经在执行的做法；标「已定」的是产品负责人裁定过的；还没有定的列在第 10 节。

## 1 仓库与分工

- 现在只剩两个项目（已定）：产品 [jiangxin](https://github.com/CavaiLAB/jiangxin)，企业级框架 [kun](https://github.com/CavaiLAB/kun)。都在 CavaiLAB 下，所有者是 CavaiLAB（已定）。
- 另外两个仓库不在维护的范围里：前端框架 Qian 的仓库已归档，只读，已发布的包留着（已定）；SanYuanAgent 的仓库保留，暂不维护（已定）。
- 每个仓库有负责的人，名单待定。
- 平台级的事在 `jiangxin` 里改：平台做什么、总体架构、路线、名称、匠心与 Kun 的分工。
- 产品的代码在 `jiangxin`（已定）。产品指 Agent 工作区的 Web 端与桌面端、管理端、产品的插件、部署清单；现在有什么，见[平台主页](https://github.com/CavaiLAB/jiangxin/blob/main/README.md)的「现状」。
- Kun 是通用的组件，不负责任何业务；最终的界面放在匠心，也可以放到另一个仓库（已定）。没有新的话之前放 `jiangxin`。
- 两个仓库之间只经契约和发布出来的包协作，不做跨仓库的源码引用。提议：匠心按钉住的版本装 Kun 发布的包与镜像，Kun 不依赖匠心。
- DSH 是上游的项目，不是我们的仓库。匠心按钉死的版本装它发布的 npm 包，不改它的源码。
- 要改代码，去代码所在的仓库提 PR，按那边的规则办。

## 2 分支与合并

- `main` 是主干，受保护，不直接推送。
- 改动走分支和 PR，CI 通过并经过评审之后合入。评审人数待定，提议至少一人。
- 提交信息写清改了什么、为什么；有任务编号的带上编号。
- 建仓期间的初始文档是由建仓的人直接推到 `main` 的，那以后都走分支和 PR。

## 3 方向怎么定

- 方向性的事由产品负责人定。定了的写进对应的文档，标「已定」；整理时的读法、提议、待定也照实标明，不把提议写成已定。他说了条件、条件由整理时的评估来判定的，标「带条件」，写明条件是什么、评估的结论是什么。
- 本仓库不放决策记录，文档里不写裁定的编号（已定）。文档写的是现行的结论。以后新定的事怎么留记录，没有定；现在的做法是直接改对应的文档。
- 只影响 Kun 的决定，在 Kun 的仓库里登记成决策任务（已定）。
- 已定的事不在实现里悄悄改。有异议，提出来等产品负责人定。
- 需要人拍板的问题，编码代理不自行决定，写进对应文档的「待定」一节或第 10 节的清单，等人裁定。

## 4 任务管理

已定：任务跟代码走，各仓库各有一份任务目录，`jiangxin` 放汇总看板。现在只有 Kun 有任务目录，汇总看板还没有建。

- 现状：Kun 的[任务文件和看板](https://github.com/CavaiLAB/kun/blob/main/pm/README.md)在仓库根目录的 `pm/`。一个任务一个 Markdown 文件，看板从主干的 `pm/tasks/` 生成。人和编码代理用同一套命令。
- 任务要重新整理（已定）。按收拢后的方向排的十二条工作线是提议，见[路线](13-roadmap.md)第 2.2 节。

## 5 文档

- 文档用中文。
- 不写参考平台和对标项目的名字。
- 说现状的时候写清是「已有」还是「规划」，不把规划写成已经实现。
- 不放密钥和内部地址，不放还没修复的安全问题的细节。
- 平台只按一句话描述（已定）：企业级的 AI 原生平台。人用自然语言说清要什么，智能体把它落成可运行的系统；系统上线后在人的反馈里继续改进。
- 下面几种说法 2026-11-26 起不再用：平台此前的一条理念，连同解释它的章节、图和词条（已定）；「两种角色」（已定）；「三个框架」（已定）。照整理时的读法，随它们一起不再用的还有：与那条理念同一批的几个叫法；拿两种角色当角色名的那两个称呼；把 `jiangxin` 叫作「组合体」、说它交付「两样东西」。
- 讲结构时这样写：匠心是产品，Kun 是企业级框架，Agent 运行时用 DSH。说到人，用平常的话：用平台的人、做开发的人、管理员。这两条是整理时的读法。
- 「形态」这个词只用来说部署的两种形态：带不带模型推理。分这两种是已定的；这个词只这样用，是文档的约定。
- 文档里要写清楚四件事（已定）：平台做什么与设计理念、重点是工业智能制造；DSH 更新之后做什么；别人怎么在平台上做开发；DSH 怎么与企业级平台交互。各在哪一篇，见[平台主页](https://github.com/CavaiLAB/jiangxin/blob/main/README.md)的「文档」。
- 文档站用 Rspress，搭在 `jiangxin` 仓库的 `website/` 下（已定）。文档以 Markdown 放在仓库里，那是唯一的一份。站点放哪些内容、怎么构建，见 [website 的说明](https://github.com/CavaiLAB/jiangxin/blob/main/website/README.md)。
- Kun 要有单独的网站，放使用文档和给大模型用的文档（已定）。
- 图用 Mermaid 语法写，在 GitHub 上直接能看；站点用 Pele 把它渲染成静态图（已定）。
- 每个 PR 上 CI 都会构建站点，死链、失效的锚点和画不出来的图会让它失败。提交前也可以在 `website/` 下自己构建一次。
- 站点部署在内网，合并到 `main` 后由 CI 发布（已定）；部署清单在部署仓库。

## 11 公开

仓库是公开的（已定）。

公开的仓库里不放这几类内容：

- 产品清单与建设状态。
- 对私有的来源产品的功能盘点与差距描述。只写可以承接的能力类别。
- 私有产品的名字。要提到时写「私有产品」「原来的私有仓库」这类说法；引用的原话里有，就换成方括号里的说法并在文首说明。提交历史、导入时过渡目录快照中的原件与任务日志、迁移工具，以及源码里带着这个名字的标识（环境变量名这类，随以后的改名处理）不在此列。
- 改名的经过。前端框架的旧名、旧仓库的地址都不写，也不用「原」加框架名指代来源；讲位置写路径或现在的名字，指向历史文件的链接用新仓库里钉住提交的链接。决策记录与历史文档、给使用者的迁移指南、改名与导入工具，以及提交历史、导入时过渡目录快照中的原件与任务日志、源码里带旧名的标识（随以后的改名处理）不在此列。
- 密钥、内部地址、还没修复的安全问题的细节、私有仓库的内部实现细节。

公共包源上的包改指新的源码地址这一项已按现状关闭（已定）：Kun 的包从 2026.11.21 起指向 `CavaiLAB/kun`，此前发布的版本的元数据改不了。
