# 协作约定

> 状态：提议（2026-11-17）。多数条目沿用来源仓库里已经在执行的做法；标「已定」的是产品负责人裁定过的；标「待定」的要在[路线](06-roadmap.md)的阶段 1 定下来。

## 1 仓库与分工

- 一个框架一个仓库、一种主语言。每个仓库有负责的人，名单待定。
- 平台级的事在 [jiangxin](https://github.com/CavaiLAB/jiangxin) 里改：理念、总体架构、路线、名称、三个框架的分工。
- 框架之间只经契约和发布出来的包协作，不做跨仓库的源码引用。
- 代码在各框架仓库，引擎的服务层与媒体适配层还在原来的私有仓库。要改代码，去代码所在的仓库提 PR，按那边的规则办。

## 2 分支与合并

- `main` 是主干，受保护，不直接推送。
- 改动走分支和 PR，CI 通过并经过评审之后合入。评审人数待定，提议至少一人。
- 提交信息写清改了什么、为什么；有任务编号的带上编号。
- 这几条从阶段 1 治理就位起执行。阶段 0 建仓期间，初始文档由建仓的人直接推到 `main`。

## 3 决策记录

- 影响多个框架的决定写成平台级的决策记录，放在 `jiangxin` 的 `docs/decisions/`；只影响一个框架的，放在那个框架的仓库。第一份是 [2026-11-17 平台级裁定](decisions/2026-11-17-platform.md)。
- 记录里分清「已定」「提议」「待定」。
- 已定的事不在实现里悄悄改。有异议，另提一份决策记录。
- 需要人拍板的问题，编码代理不自行决定，登记出来等人裁定。

## 4 任务管理

待定。

- 现状：`kun` 过渡目录里的任务（`_import/qian/pm/`）用「任务即文件」：一个任务一个 Markdown 文件，看板由脚本生成，人和编码代理用同一套命令。迁移期间看板从 `kun` 出。
- 合并蓝图的写法（已接受）：任务文件与看板整体搬进后端仓库，任务编号不变。
- 分成几个仓库之后要重定：任务文件留在各自的仓库，还是集中到一处；跨仓库的路线与里程碑用什么看。已登记的倾向是任务跟代码走，各仓库各有任务目录，`jiangxin` 放汇总看板；待确认。

## 5 文档

- 文档用中文。
- 不写参考平台和对标项目的名字。
- 说现状的时候写清是「已有」还是「规划」，不把规划写成已经实现。
- 不放密钥和内部地址，不放还没修复的安全问题的细节。
- 文档站用 Rspress，搭在 `jiangxin` 仓库的 `website/` 下（已定）。各仓库的文档仍以 Markdown 放在各自的仓库里，那是唯一的一份；站点把 `jiangxin` 与三个框架仓库的 README 和 `docs/` 聚到一起，框架仓库的按钉住的提交取（做法是提议）。
- 图用 Mermaid 语法写，在 GitHub 上直接能看；站点用 Pele 把它渲染成静态图（已定）。
- 每个 PR 上 CI 都会构建站点，死链、失效的锚点和画不出来的图会让它失败。提交前也可以在 `website/` 下自己构建一次。
- 站点部署在内网的 K3s 上，合并到 `main` 后由 CI 发布（已定）；部署清单在部署仓库。`kun` 过渡目录里那个文档站（`_import/qian/website/`）的组件页与 API 参考怎么并进来，见[仓库与归属](05-repositories.md)第 4 节。

## 6 质量门禁

各框架迁入时，把来源仓库的门禁一起带过来：

| 框架 | 门禁 |
|---|---|
| Kun | 警告即错误；公共 API 清单；依赖方向检查（合并时改为显式的档位表）；一致性测试；契约与样例的一致性检查；单元测试与集成测试 |
| Qian | 八项：代码规则、类型检查、单元测试、可访问性、首屏性能预算、分层边界、发布形状、循环依赖；另有视觉回归 |
| SanYuanAgent | 代码规则、类型检查、单元测试；「核心不得引用服务层」的边界测试；「核心可以单独安装」的检查 |

## 8 许可

- Kun 的 .NET 包族、命令行，以及前端的包：全部用 MIT（已定，2026-11-17）。已经按原许可发布的旧版本不受影响。许可文件随代码迁入。
- SanYuanAgent：核心保持 Apache-2.0（已定，见[平台级裁定](decisions/2026-11-17-platform.md) P18）。服务层与媒体适配层的许可待定，服务层现在没有开放，是否开放阶段 1 定。

## 9 编码代理

- 每个仓库根目录有 `AGENTS.md`，是 Codex、Claude Code 等编码代理的入口；`CLAUDE.md` 只指向它。
- 代理和人守同一套规则：认领任务、走 PR、过门禁、不自行拍板。
- 代理写的日志和提交要写明是哪个代理。

## 11 公开

四个新仓库已于 2026-11-17 改为公开。

公开的仓库里不放这几类内容：

- 产品清单与建设状态。
- 对私有的来源产品的功能盘点与差距描述。只写可以承接的能力类别。
- 私有产品的名字。要提到时写「私有产品」「原来的私有仓库」这类说法；引用的原话里有，就换成方括号里的说法并在文首说明。提交历史、过渡目录里还没搬出的原件与任务日志、迁移工具，以及源码里带着这个名字的标识（环境变量名这类，随以后的改名处理）不在此列。
- 改名的经过。前端框架的旧名、旧仓库的地址都不写，也不用「原」加框架名指代来源；讲位置写路径或现在的名字，指向历史文件的链接用新仓库里钉住提交的链接。决策记录与历史文档、给使用者的迁移指南、改名与导入工具，以及提交历史、过渡目录里还没搬出的原件与任务日志、源码里带旧名的标识（随以后的改名处理）不在此列。
- 密钥、内部地址、还没修复的安全问题的细节、私有仓库的内部实现细节。

还要定的：代码导入新仓库之后，公共包源上的包何时改指新的源码地址。
