# 2026-11-19 平台级裁定

> 记录产品负责人 2026-11-19 对平台的裁定，编号接着 [2026-11-17 平台级裁定](2026-11-17-platform.md)。引号里是原话，方括号里是整理时替换的说法。本文只记已定的事；待确认的事在各文档的「待定」里。

## 1 已定

| 编号 | 裁定 | 原话 |
|---|---|---|
| P22 | 平台上分两种角色。平台开发围绕 Agent 框架与企业级应用平台做开发。普通开发或最终用户基于 Agent 平台，在企业级框架上构建自己需要的软件；Agent 框架与企业级核心的开发不由他们负责，他们只使用工具。平台开发使用的工具可能是通用的编码智能体 | 「我们会分为两种角色」「第一种角色：平台开发，主要围绕 Agent 框架和企业级应用来进行开发」「第二种角色：普通开发或最终用户，他们能基于这个 Agent 平台，在企业级框架上构建自己所需要的软件形态」「有一个前提，就是 Agent 框架的开发和右侧企业级核心开发他们不负责，只是负责使用工具」「我们开发平台使用的工具可能会是 Claude、Codex」 |
| P23 | 平台开发交付两样东西：一个 Agent 框架，一个企业级应用平台。两者互补，最终是一体化的产品。`jiangxin` 仓库就是组合体：Agent 加企业级框架 | 「平台开发出来的是一个 Agent 的框架和企业级的应用平台」「左侧是一个 Agent 的框架（完整的［桌面端智能体应用那样的］，当然也可以办公），右侧是企业级框架」「这就形成了一个互补的关系」「最终我们是一体化的产品」「jiangxin repo 就是组合体（agent + 企业级框架）」 |
| P24 | 最终用户的使用界面是 Agent 平台。Agent 平台的客户端基于企业级框架。企业级应用平台不另做一套入口：Agent 平台收起对话区，就是它 | 「最终用户的使用界面应该就是 Agent 的平台」「Agent 平台客户端 要基于企业级框架」；「十一项都按推荐定」（第 6 项，见第 2 节） |
| P25 | 最终用户有两种扩展：基于企业级应用平台开发插件；给 Agent 增加组件。平台提供所需的基础组件，并内置智能体、知识库模板等内容。企业级框架里有应用市场，可以通过 Agent 框架开发、上架 | 「他可以自己开发插件，基于企业级的应用平台，也可以给 Agent 增加组件」「平台会提供所有需要的基础组件，并且内置了像智能体、知识库模板等内容，让他们能通过 Agent 框架快速实现自己的业务」「内部也会有应用市场，可以通过 Agent 框架开发上架」 |
| P26 | 所有发布的应用（插件）之间可以互相通讯。缺省：应用提供的能力与事件在目录里看得到；调用与订阅按声明、经批准放行 | 「所有发布的应用（或者叫插件可能更合适），它们之间都是可以互相通讯的」；「十一项都按推荐定」（第 4 项） |
| P27 | 遗留的历史系统要能集成进企业级框架，并融合进 Agent 框架。历史系统在企业内网的，连接器的执行部分装在内网，只向外连 | 「还需要考虑到一些遗留的历史系统……这些系统也有可能集成到这套企业级框架里。需要考虑这部分怎么去融合，也就是怎么通讯并融合到整个 Agent 框架里面」；「十一项都按推荐定」（第 9 项） |
| P28 | 每个 Agent 发出去的内容都要由人审核。起步出站、入站两道都必审。「发出去」包括三类：发给别的 Agent、发给别人、写外部系统 | 「后续每个人都会拥有一个或几个 Agent，这些 Agent 可以进行协同办公。但前提是，每个 Agent 发出去的内容都需要人来进行审核」；「十一项都按推荐定」（第 2、3 项） |
| P29 | 给「我的 Agent」长期挂组件，加一种 Agent 一级的范围 | 「十一项都按推荐定」（第 7 项） |
| P30 | 组件里新增一种「知识库」内容 | 「十一项都按推荐定」（第 8 项） |
| P31 | 路线重排，最小的一圈提前。顺序见[路线与迁移](../06-roadmap.md)第 2.1 节的里程碑 | 「十一项都按推荐定」（第 10 项） |
| P32 | 拖拽设计器缓做。先让 Agent 写，设计器以后作为第二种编写方式 | 「十一项都按推荐定」（第 11 项） |
| P33 | 最终交付给客户的，可以是多租户的版本，也可以是单租户的版本 | 「最终交付客户的可以是一个多租户的版本，也可以是一个单租户的版本」 |

## 2 十一个待定项与答复

同一天，一份整体方案把还没有定的事列成十一项，每项给了推荐与备选。产品负责人的答复是「十一项都按推荐定，写进平台文档」，随后对第 5 项另作了裁定。

| 项 | 待定的事 | 推荐 | 结果 |
|---|---|---|---|
| 1 | 把当天说定的方向记成平台裁定 | 记 | 按推荐，即本文 |
| 2 | 人审的方向 | 起步出站、入站两道都必审 | 按推荐，P28 |
| 3 | 「发出去」的范围 | 发给别的 Agent、发给别人、写外部系统都算 | 按推荐，P28 |
| 4 | 应用互通的缺省 | 目录里看得到；调用与订阅按声明、经批准放行 | 按推荐，P26 |
| 5 | Agent 平台客户端的代码放在哪里 | 单独一个仓库，并且不登录企业租户也能单独运行 | 没有按推荐。产品负责人随后说：客户端要基于企业级框架，最终是一体化的产品，`jiangxin` 仓库就是组合体。见 P23、P24 |
| 6 | 企业级应用平台要不要单独的入口 | 不另做一套。Agent 平台收起对话区，就是它 | 按推荐，P24 |
| 7 | 给「我的 Agent」挂组件用什么范围 | 加 Agent 一级的范围 | 按推荐，P29 |
| 8 | 知识库怎么进组件 | 新增一种「知识库」内容 | 按推荐，P30 |
| 9 | 连接器的执行部分装在哪里 | 历史系统在内网的，执行部分装在内网，只向外连 | 按推荐，P27 |
| 10 | 路线要不要重排 | 重排，最小的一圈提前 | 按推荐，P31 |
| 11 | 拖拽设计器 | 缓做。先让 Agent 写，设计器以后作为第二种编写方式 | 按推荐，P32 |

方案里十一项之外的内容没有逐条确认，在各文档里仍然标「提议」。

## 4 与来源仓库现行决策的出入

下面几条与 `kun` 过渡目录里已接受的决策记录有出入。它们已登记进那边的决策任务 S1-DEC-038（D22–D26，2026-11-19）。回写之前，过渡目录里的原件仍是原来的写法；有出入时以平台级裁定为准。

| 现行决策 | 现行的写法 | 出入 |
|---|---|---|
| 组件模型（ADR-020） | 范围的种类是租户、应用、Agent 会话三种 | P29：加一种 Agent 一级的范围 |
| 组件模型（ADR-020） | 组件的内容种类里没有知识库 | P30：新增一种「知识库」内容 |
| 与私有智能体产品的边界（ADR-016）、需求文档里平台不做的 AI 功能 | 私有智能体产品自有的知识库算作它的 AI 资产，权威在那边；需求文档把知识库列在平台的范围之外 | P30：知识库是组件里的一种内容。两边怎么分，待定 |
| 流程引擎（ADR-012）与第二阶段的需求文档 | 流程的视图设计器、表单与列表的设计器排在第二阶段 | P32：设计器缓做。第二阶段里依赖设计器的部分怎么调整，待定（11 月 24 日补：产品负责人说这一问先移除，见 [2026-11-24 平台级裁定](2026-11-24-platform.md)第 2 节） |
| 授权模型（ADR-006）、与私有智能体产品的边界（ADR-016）、来源仓库的阶段划分 | 智能体主体、Agent 调用平台能力的路径排在最后一个阶段启用 | P31：最小的一圈提前，智能体主体在第一个里程碑启用 |
| 组件模型（ADR-020） | 被范围过滤掉的项不出现在目录与提示词里，调用也被拒绝 | P26 说应用提供的能力与事件在目录里看得到。提议的读法：看得到的是本租户里做构建与安装的人，运行时的过滤不变。待确认，见[应用互通](../10-app-interop.md)第 6 节 |
| 应用市场（ADR-014） | 没有出入。开通与升级时逐项批准组件向平台申请的权限，是现行的决策 | P26 定的缺省与它一致。应用之间的调用与订阅怎么并进这份申请，是提议 |
| 网关分层（ADR-010）、Agent 的调用路径（ADR-016） | 没有出入 | 本次裁定不改流量路径 |
