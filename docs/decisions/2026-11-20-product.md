# 2026-11-20 产品裁定

本次裁定接着 [2026-11-20 迁移与发布裁定](2026-11-20-release.md) 编号，记录产品负责人同一天对「匠心工业智能体平台」的决定：Agent 运行时、界面外壳、客户端、名称与版本号、代码放在哪个仓库。

> 引号里是原话，方括号里是整理时替换的说法：原话里提到的私有产品，按[协作约定](../07-governance.md)第 11 节换成「［私有产品］」。本文第 1 节只记已定的事；没有定的在第 3 节，标「提议」或「待定」。

DSH 是一个开源的智能体运行框架，以 npm 包 `@deepseek-ai/dsh` 发布，按 MIT 许可使用。组合体现在钉的版本是 `0.2.2-rc.5`，见 [distribution/README.md](https://github.com/CavaiLAB/jiangxin/blob/main/distribution/README.md)。

## 1 已定

| 编号 | 产品负责人裁定 | 原话 |
|---|---|---|

| P38 | 界面外壳用 DSH 自己的客户端，网页与桌面都是。前端框架 Qian 冻结在 0.2.1；组件以后缺哪个，按 DSH 的写法迁进我们自己的界面包。另一种方案是保留 Qian、按 DSH 的规范改，没有选 | 「DSH 当外壳」（答两种外壳方案选哪个：一是界面用 DSH 自己的客户端，Qian 冻结在 0.2.1，组件以后缺哪个按 DSH 的写法迁进自己的界面包；二是保留 Qian、按 DSH 的规范改） |
| P39 | 客户可能用到两个端：Web 端和客户端（桌面）。管理端先不做，目录先建好 | 「客户有可能会有两个端web端和客户端，管理端的话先不做,可以创建好文件夹。」 |
| P40 | 产品名用「匠心工业智能体平台」，换上匠心的 logo。产品的版本号用日历版本号：`vYYYY.M.D` 是正式版，`vYYYY.M.D-N` 是当天正式版之后的补丁版，`vYYYY.M.D-beta.N` 是测试版；月和日不补零；产品版本号在构建时注入，不写在各个包的 `package.json` 里 | 「注意替换一些名称（匠心工业智能体平台）和 logo 我的版本号的规则还是按照 ［私有产品］ 中 的版本号规则。」 |

## 2 取代了此前的哪几条

| 此前的写法 | 出处 | 被哪条取代 | 程度 |
|---|---|---|---|
| SanYuanAgent 是独立运行的 SDK，每个端都要用到它，包括机器人这类边缘设备 | [2026-11-17 平台级裁定](2026-11-17-platform.md) P13 | P37、P38 | 部分取代。Web 端和桌面客户端的 Agent 运行时是 DSH，「每个端都要用到 SanYuanAgent」对这两个端不再成立。SanYuanAgent 是独立运行的 SDK 这一点不受影响。机器人这类边缘设备用什么、SanYuanAgent 以后怎么接，待定 |
| Agent 平台的客户端基于企业级框架；据此写的提议是界面用 Qian 搭 | [2026-11-19 平台级裁定](2026-11-19-platform.md) P24；[角色与产品形态](../09-roles-and-product.md)第 3 节 | P38 | 部分取代。界面外壳是 DSH 的客户端，不用 Qian 搭。「客户端基于企业级框架」在后端这一半是否还成立，要看登录、租户、策略、审计由哪个后端提供，待定。P24 的另外两句：最终用户的使用界面是 Agent 平台，不受影响；企业级应用平台不另做一套入口、Agent 平台收起对话区就是它，在 DSH 的外壳下怎么落，待定 |
| 组合体里放 Agent 平台的客户端：网页、桌面、移动三种端；界面用 `qian` 发布的包搭，身份、权限、应用与能力来自 `kun`，智能来自 `sanyuan-agent` | [仓库与归属](../05-repositories.md)第 1.1 节（提议） | P37、P38、P39 | 取代。端是 Web 端和客户端（桌面），管理端先不做；外壳与 Agent 运行时是 DSH。移动端不在这次裁定里；后端由谁提供待定 |
| 组合体的代码从里程碑 M1 开始进 `jiangxin` | 同上（提议） | P41 | 取代：代码已经放进来，见[仓库与归属](../05-repositories.md)第 1.1 节 |
| 现有的应用外壳（在 `kun`）里通用的部分发布成包，Agent 平台的客户端在 `jiangxin` 里用这些包组装 | 同上（提议）；[2026-11-19 平台级裁定](2026-11-19-platform.md)第 3 节 | P38 | 前提变了：客户端的外壳改用 DSH 的客户端。应用外壳怎么办，待定 |

## 3 提议与待定

下面这些产品负责人没有定。

| 事项 | 现在的情况 | 状态 |
|---|---|---|
| 第一版是不是全部基于 DSH | 倾向是全部基于。原话是「前期可以完全基于它」 | 待定 |
| SanYuanAgent 以后怎么接 | 没有方案。P2、P3、P8 把它定为平台的第三个框架、理念里的「全智」、三种形态的大脑；[术语表](../glossary.md)把 Agent 框架写成 SanYuanAgent 加 Agent 平台。P37 之后这几处怎么讲，一并待定 | 待定 |
| 登录、租户、策略、审计由哪个后端提供 | 没有定 | 待定 |
| 一个用户一个 DSH 实例 | 建议，没有确认。理由：DSH 的一个实例里只有一种调用方身份，就是实例的主人；会话里没有用户和租户；设置、插件、凭据整个实例共用。所以多用户靠每人一个实例（一个容器、一台虚拟机或一台桌面）隔开，登录、租户、授权放在实例外面的门户里，实例里的插件只做护栏 | 提议 |
| 包名前缀 `@jx/` | 现在的代码用它 | 提议 |
| 放不下全称的地方用短名「匠心」 | 程序坞、托盘、窄标题这类地方 | 提议 |
| 桌面客户端走哪条路 | 比较过两条：甲，自己写一个薄的 Electron 壳，里面跑已发布的 DSH（`apps/desktop/` 是它的原型）；乙，从钉死的源码构建 DSH 上游的桌面壳，用补丁换品牌。建议走甲。对比见 [apps/desktop/README.md](https://github.com/CavaiLAB/jiangxin/blob/main/apps/desktop/README.md) 的「两条路线」 | 提议 |
| 普通用户要不要插件页 | 定了之后，再定发行配置里插件管理那几行怎么配 | 待定 |
| 移动端 | [仓库与归属](../05-repositories.md)原来提议网页、桌面、移动三种端；P39 说的是两个端 | 待定 |
| 现有的应用外壳怎么办 | 见第 2 节最后一行 | 待定 |
| Qian 冻结以后还发不发新版本 | P34、P35 讲的是 Qian 后续版本怎么定版本号、组件文档怎么生成 | 待定 |

另有几件要产品负责人确认的事：

| 事项 | 现在的写法 |
|---|---|
| 平台名与产品名 | 平台名是「匠心智能体平台」（P1），产品名是「匠心工业智能体平台」（P40）。两者是什么关系（产品是平台的一个交付版本，还是平台改名），没有定。文档里暂时两个都用：讲平台用平台名，讲组合体交付的产品用产品名 |
| DSH 的名字 | 本仓库的规则是不写参考平台和对标项目的名字。DSH 是组合体的依赖，不是对标的对象：代码里躲不开它的包名（`@deepseek-ai/*`）和配置行的名字；文档里只写「DSH」，不写它的全称（上游的品牌准则说全称是注册商标，不能用在别的项目名里）；分发时保留它的 MIT 版权与许可声明。这样写对不对，待确认 |
| logo 原图进公开仓库 | `brand/source/` 里放的是匠心 logo 的原图，旁边的 [brand/README.md](https://github.com/CavaiLAB/jiangxin/blob/main/brand/README.md) 写明标志不在任何代码许可之内。推送前由产品负责人决定 |
