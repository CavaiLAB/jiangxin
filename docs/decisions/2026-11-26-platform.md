## 2 原话

产品负责人 2026-11-26 说的，全文如下。换行照原样；方括号里是整理时替换的说法，原因见文首。

> 经过一段考虑，前端 Qian 归档，SanyuanAgent 保留先不维护，现在只剩下  Jiangxin 和 Kun ，现在整理几个项目描述和任务；\
> 1.移除［此前的理念］相关的描述，只描述 匠心工业智能体平台，企业级的 AI 原生平台。人用自然语言说清要什么，智能体把它落成可运行的系统；系统上线后在人的反馈里继续改进。\
> 2.两种角色移除\
> 3.移除三个框架，从新整理任务和移除 docs 等不必要的文档。\
> Kun 增加单独网站增加使用文档和说明。方便后续其他人使用，增加给大模型使用的类似 llm.txt 这种文档。方便进行调用。
>
> 企业级框架分为两种\
> 1.K8s集群，包括模型推理服务， GPU Stack 等\
> 2.不包括直接接入第三方模型服务，通过 API 方式，可以参考框架。\
> 3.提供多租户和单租户两个版本。\
> 但是不管哪种方式 统一由管理端进行管理。以上尽量使用插件的形式进行实现。所以你要设计一些标准的接口，方便我对接后面的模型推理服务，因为我只想提供一套。
>
> 代码要符合 ISO 等国际相关标准。文档中需要描述清楚以下几件事：\
> 1\. 这个平台是要做什么的，设计理念，不仅仅面向通用办公，更深入工业智能制造（重点是）\
> 2\. DSH 更新之后我应该做哪些工作。\
> 3\. 其他人怎么在这个平台上做开发。\
> 4\. DSH 怎么与我的企业级系统进行交互（像登录、模型服务都是我企业级平台需要提供的）。
>
> 另外，这个企业级平台后续不论做什么系统，权限都是要走这一套的，所以要在  Kun 框架上做好这部分。

第一段第 1 条里换成「［此前的理念］」的地方，原话用的是那条理念的简称。整理时向他报告这指的是 [P3](2026-11-17-platform.md) 记的那条理念，他随后补了一句：

> 把之前的理念［此前的理念名］全都移除。

## 3 读法与范围

### 3.1 P78：只剩两个项目

- 「前端 Qian 归档」说的就是 [P77](2026-11-25-platform.md)：仓库 2026-11-25 已经归档，只读，已发布的包留着。这次没有新的动作。
- 「SanyuanAgent 保留先不维护」读作：仓库留着，不归档；代码和文档停在现在的样子，不跟着平台更新。它接着 [P53](2026-11-24-platform.md)（暂缓开发，现在使用 DSH）说：不只是暂缓开发，文档也不再维护。这是整理时的读法。
- 「只剩下 Jiangxin 和 Kun」读作在用、在维护的项目是这两个。[P5](2026-11-17-platform.md) 建的四个仓库都还在。这是整理时的读法。
- Agent 运行时和界面外壳用 DSH，没有变（[P37、P38](2026-11-20-product.md)）。DSH 是匠心的依赖，不是我们自己的项目。
- SanYuanAgent 以后怎么接、还接不接，这次没有说，仍没有定。

### 3.2 P79：平台怎么描述，此前的理念移除

- 以后讲平台是什么，只用第 1 节 P79 里的那一句。它与 [P1](2026-11-17-platform.md) 同向：企业级，不面向个人消费者，用自然语言构建系统。平台的名字不变（[P45](2026-11-24-platform.md)）。
- P85 的第一件事里还带着一句：平台不只面向通用办公，更深入工业智能制造，这是重点。它没有另外编号，记在 P85 下面。
- 「［此前的理念］相关的描述」「把之前的理念［此前的理念名］全都移除」指 P3 记的那条理念，连同各篇文档里解释它的章节、图和词条。
- 连带拿掉的，是和它同一批的几个说法：借了它的词起的一处阶段名、一处目标状态的叫法，以及 [P8](2026-11-17-platform.md) 里「工蜂、章蜂、群蜂」的叫法。那三个蜂的叫法在理念的原图里是它的一组内容，所以随它一起拿掉。工站、产线、工厂三级是工业现场的内容，保留。这一段是整理时的读法；蜂的叫法没有单独问过，见第 6 节。
- 定位只用那一句，所以「三个框架」「组合体」「平台开发交付两样东西」这类讲结构的说法不再用来介绍平台。要讲结构时写：产品是匠心，企业级框架是 Kun，Agent 运行时用 DSH。这是整理时的读法。
- **旧记录里有两处改了原文。** 他说的是「全都移除」。照这句话：[2026-11-17 平台级裁定](2026-11-17-platform.md)里 P3 一行的裁定与原话都拿掉了，换成一句撤销说明；[2026-11-20 产品裁定](2026-11-20-product.md)第 3 节「SanYuanAgent 以后怎么接」一行里，那条理念的一个专用词换成了方括号的写法，别的字没有动。这是改写历史记录，只有这两处；别的旧记录照旧不改原文，只加补注。
- 各篇文档里的描述这次还没有移除，见第 7 节。

### 3.3 P80：两种角色移除

- 指 [P22](2026-11-19-platform.md) 的两种角色。以后不再按这两种角色讲平台。
- [P24、P25](2026-11-19-platform.md) 的内容他没有说要改：使用的界面是 Agent 平台，客户端基于企业级框架，不另做一套入口；可以基于企业级应用平台开发插件，也可以给 Agent 增加组件。这些保留，里面「最终用户」「平台开发」这些称呼以后换掉。这是整理时的读法。

### 3.4 P81：「三个框架」的说法移除，任务与文档重新整理

- 「移除三个框架」读作不再把 Kun、Qian、SanYuanAgent 并列成平台之下的三个框架（[P2](2026-11-17-platform.md)）。仓库不动：Qian 已归档，SanYuanAgent 留着。这是整理时的读法。
- [P23](2026-11-19-platform.md) 的「平台开发交付两样东西」「`jiangxin` 是组合体」随两种角色、「三个框架」一起不再用。产品的代码仍在 `jiangxin`（[P41](2026-11-20-product.md)）。这是整理时的读法。
- 「从新整理任务」读作重新整理任务。怎么整理没有定，这次没有动任何任务；里程碑 M0 至 M8 的顺序（[P31](2026-11-19-platform.md)）改不改，他没有说。
- 「移除 docs 等不必要的文档」读作把不再需要的文档删掉，不是把 `docs/` 整个删掉。这是整理时的读法。哪些删，另行整理；这次没有删任何文档。

### 3.5 P82：Kun 的网站与给大模型用的文档

- 已有：Kun 的仓库里有一个文档站，构建时已经产出 llms.txt。它只部署在内部，里面 Kun 的文档和前端框架的组件文档放在一起。
- 「增加单独网站」读作把它做成 Kun 自己的、别人打得开的站，补上使用文档。这是整理时的读法。对外放在哪，没有定。
- 「类似 llm.txt 这种文档」读作 llms.txt 这一类给大模型读的入口。已有的那一份够不够、还要补什么，没有定。
- 匠心的文档站是另一个站（[P9 至 P12](2026-11-17-platform.md)），这次没有动。它以后还聚不聚别的仓库的文档，见第 6 节。

### 3.6 P83：两种形态，两个版本，一个管理端，一套模型服务的接口

- **两种形态按带不带模型推理分。** 第一种是 K8s 集群，集群里带模型推理服务。第二种的原话是「不包括直接接入第三方模型服务，通过 API 方式」，读作：不包括模型推理，通过 API 直接接入第三方的模型服务。这是整理时的读法。
- 「可以参考框架」读作做法可以参考现成的开源框架。没有说是哪个。这是整理时的读法。
- **两个版本。** 「提供多租户和单租户两个版本」排在「分为两种」下面的第 3 条，读作另一件事：重申 [P33](2026-11-19-platform.md)。这是整理时的读法。
- **三条线。** 这次说的两种形态，与企业版、单机版（[P58、P59](2026-11-25-platform.md)）、与多租户和单租户（P33）是什么关系，他没有说。读作三条不同的线：带不带模型推理；跑在集群上还是一台服务器上；多租户还是单租户。这是整理时的读法。哪几种组合要交付，没有问。
- **统一由管理端管理。** 管理端在匠心（[P60、P65、P66](2026-11-25-platform.md)）。读作：两种形态、两个版本用同一个管理端，模型服务也在里面管。这是整理时的读法。
- **尽量用插件的形式。** 读作：模型推理的接入、两种形态的差别、两个版本的差别，尽量做成 Kun 的组件；换一个组件就换了形态，产品还是一套。这是整理时的读法。
- **标准的接口，只提供一套。** 读作：模型服务这一块留一个标准的接口。后面接自己的推理服务，还是接第三方的 API，都接在这个接口上，上面的产品不用跟着改。这是整理时的读法。接口的形状没有定。
- 与此前的关系：[P14](2026-11-17-platform.md)（模型服务由 Kun 提供）不变，这次加上两种形态、标准的接口、统一由管理端管理、尽量做成插件。
- 现状：规划。模型服务的接口还没有实现；Kun 里的模型组件现在只有骨架。两种形态各自的装配、单租户版的装配都还没有清单。

### 3.7 P84：标准

- 「符合 ISO 等国际相关标准」读作：定一份标准对照，配上相应的检查，文档里写明对着哪些标准、各自做到了哪一步。不是去做认证。这是整理时的读法。
- 对着哪些标准，没有定。

### 3.8 P85：文档要写清楚的四件事

- 四件事是：平台做什么、设计理念是什么，工业智能制造是重点；DSH 更新之后要做哪些工作；别人怎么在平台上做开发；DSH 怎么与企业级系统交互。
- 读作写在匠心的 `docs/`，它们是产品的文档；Kun 的使用文档放 Kun 自己的网站（P82）。这是整理时的读法。
- 第四件事的括号里说登录、模型服务由企业级平台提供。这与已定的一致：登录用 Kun 的身份服务（[P57、P64](2026-11-25-platform.md)），模型服务由 Kun 提供（P14）。
- 现状：这四篇都还没有写。

### 3.9 P86：权限统一走 Kun

- 「权限都是要走这一套」读作：平台上做的任何系统，判权限只问 Kun，不各做一套。管理端、应用、插件、Agent、DSH 一侧的服务都算。这是整理时的读法。
- 它与 2026-11-24 的一句同向：「所有涉及到权限的这些，后面我都会接入到 PaaS 服务上。统一使用 C# 进行提供。」那一句此前是没有编号的前提（[2026-11-25 平台级裁定](2026-11-25-platform.md)第 2 节），这次有了编号。
- [P60](2026-11-25-platform.md) 不变：Kun 是通用的组件，不负责业务。权限是通用的平台能力。
- 现状：Kun 的权限判定现在是给 .NET 进程里的代码用的。给别的进程、别的语言用的远程接口是规划，还没有实现。
