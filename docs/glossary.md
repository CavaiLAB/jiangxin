# 术语与名称对照

> 状态：规划稿（2026-11-17）。

## 1 名字换了什么

2026-11-17 起，几个名字的所指变了。读旧文档之前先看这张表。

| 名字 | 以前指什么 | 现在指什么 | 什么时候生效 |
|---|---|---|---|
| 匠心智能体平台 | — | 整个平台的名字 | 2026-11-17 |
| Yi（易） | 2026-11-11 定的产品族总名 | 不再使用 | 2026-11-17 |
| Kun | .NET 云原生微服务框架，包名 `Kun.*` | 为 Agent 时代构建的多租户平台框架：原 Kun 加上原 Qian 的后端，包名统一为 `Kun.*` | 定位已定；代码归并在路线阶段 3 |
| Qian | 基于 Kun 的平台层：`Qian.*` 包、平台插件 | 只作前端框架的名字，也就是原来的 yue | 更名排在路线阶段 3 里按域归并的最后一批。在那之前，原仓库里的 Qian 仍是旧含义 |
| yue | 前端组件库与外壳 | 过渡期的名字，将更名为 Qian | 同上 |
| NeuroAgent | iClaw 的 Python Agent 引擎 | 改名 SanYuanAgent | 路线阶段 2 |
| SanYuanAgent | — | 智能体引擎，一个独立运行的 SDK；工站、产线、工厂三级智能体的大脑 | 2026-11-17 |

「路线阶段」指[路线](06-roadmap.md)第 2 节的阶段 0 至 4。合并蓝图内部另有一套阶段 0 至 4，是路线阶段 3 里面的步骤。

读旧文档时注意：写于 2026-11-17 之前的文档里，「Qian」指平台层；「三层口径」指 Kun 框架层、Qian 平台层、yue 前端层。

**保留不改的 `qian` 字面。** 组件 id 的前缀 `qian.`、清单与配置的文件名（`.qian-plugin/plugin.json`、`qian.profile.yml`、`qian.patch.yml`）、`qian` 命令行、`@qian/*` 的导入名，这次都不改。它们已经落库、上线或冻结，改动的代价大而不带来功能。今后它们只是历史字面，不表示产品名，也不表示前端框架。

## 2 理念

| 术语 | 含义 |
|---|---|
| 三元全智生命体 | 平台的设计理念。三元给躯体，全智给心智，生命体给活法 |
| 三元 | 结构怎么融合：云边端；工蜂、章蜂、群蜂；人机物。在平台里对应底座 Kun 与 Qian |
| 全智 | 智能到什么水平。在平台里对应 SanYuanAgent。引擎的名字取自理念的头两个字，不表示它对应「三元」 |
| 生命体 | 平台上长出来的系统与智能体的组合，在反馈环里运转并改进 |
| 工蜂、章蜂、群蜂 | 智能体的三种形态，对应工站、产线、工厂（已定） |
| 具身智能体 | 工站一级的形态（工蜂）：感知工件，调用技能，控制工具完成作业 |
| 协同智能体 | 产线一级的形态（章蜂）：协调工序、工站和物料，保持生产节拍 |
| 超级智能体 | 工厂一级的形态（群蜂）：协调跨系统制造任务，支撑物理 AI 研发 |
| 具身大脑 | 工站技术架构里的一层：融合视觉、点云和工艺信息，识别工件，生成动作目标与约束 |
| 工控小脑 | 工站技术架构里的一层：校验运动约束，执行轨迹插补、伺服和工艺控制，反馈偏差 |
| 工业生命体 | 「从工业智能体走向工业生命体」里的目标状态。本仓库的理解：三级智能体连成一体，在反馈环里自己运转、代谢和进化；待产品负责人确认 |
| 反馈环 | 人的意图与判断 → 系统的理解与决策 → 环境被行动改变 → 结果成为反馈与记忆 → 回到人 |
| 自然语言构建 | 人用自然语言描述意图，智能体生成或修改声明式表面，经校验和人工批准后上线 |

## 3 平台术语

| 术语 | 含义 |
|---|---|
| 组件 | 一个文件夹加一份清单、若干声明式表面和可选的代码；分发与安装的单位 |
| 插件 | 组件的运行时形态：挂进共享上下文，贡献服务、监听器和可撤销的副作用 |
| 表面 | 组件向外暴露的一类声明式内容：技能、子 Agent、命令、钩子、MCP 服务器、工具、界面、元数据、业务元数据、配置补丁 |
| 清单 | 组件根目录下描述它的那份 JSON 文件 |
| 能力的三个角色 | 契约（接口与词汇）、提供方（实现）、消费方。消费方只依赖契约包 |
| 契约包 | 一项能力里只放接口、词汇类型、事件定义与错误码的那个包，没有实现 |
| 跨服务契约 | 服务之间共用的数据约定：令牌字段、事件信封、结构化错误、能力条目。冻结之后只做加法。与「契约包」是两回事 |
| 组件运行时 | 装载组件、把它们挂进共享上下文的那个很小的核心。后端与前端各有一个，语义相同 |
| 内核档、平台档 | 合并之后 Kun 的两档：内核档是不带产品语义、可以单独安装的通用机制；平台档带产品语义，以组件形式装配 |
| 范围 | 一项注册的归属：全局，或者恰好一个租户、应用或 Agent 会话 |
| profile | 一份具名的插件组装，也是一个可部署单元 |
| 组合包 | 带着一组配置条目的组件，被 profile 引用时整层叠加 |
| 补丁 | 对插件树里某个条目的替换、禁用或插入 |
| 插件树 | 由 profile、组合包和各层补丁叠出来的全部条目 |
| 目录市场 | git 仓库里的一份清单文件，列出可以安装的组件及其来源 |
| 信任等级 | 组件的来源等级，决定它能带什么形态的代码、在哪里运行 |
| 主体 | 行事的一方：`user`（人）、`service`（服务）、`agent`（智能体） |
| 委托链 | 令牌里写明「谁代表谁行事」的一串记录 |
| 能力目录 | 平台全部能力的登记：输入输出 Schema、副作用等级、所需权限、是否对 Agent 暴露 |
| 强制执行点 | 每次能力调用必经的权限判定位置 |
| 协同消息 | Agent 与 Agent 之间往来的消息，经平台的信箱转交 |
| 人审 | 人对协同消息、智能体生成的变更或高风险动作做批准、修改或驳回 |
| 独立运行 | SanYuanAgent 不接平台时的运行方式：身份、策略、记录都在本机，只要一个模型端点（提议） |
| 接入平台 | SanYuanAgent 接上 Kun 之后的运行方式：身份、能力、策略、审计、协同与模型服务由 Kun 提供。设备经入网接入，集群里的服务经网关换发的内部令牌接入（提议） |
| 入网 | 一台设备上的引擎第一次接入平台：在本机生成密钥，由主人本人在平台上批准，之后用设备密钥换短期令牌（提议） |
| 模型服务 | 由 Kun 提供的一项平台能力（已定）。照来源仓库已有的决策，它管模型目录、租户路由、配额与计量；模型请求的转发由模型网关承担 |
| 模型网关 | 转发模型请求并做限流、统计的外部组件，后面是推理集群与外部的模型供应方。它也承载 MCP 流量，所以有的地方写作「模型与 MCP 网关」 |
| 本机模型 | 设备上的小模型，由设备上的推理运行时提供。提议它不经过模型网关，用量由引擎上报 |
