# 术语表

> 状态：规划稿（2026-11-17）。2026-11-20 补了产品名、DSH 与组合体的术语（第 1、5 节）。

## 1 名字

| 名字 | 指什么 |
|---|---|
| 匠心智能体平台 | 整个平台的名字（2026-11-17 定名） |
| 匠心工业智能体平台 | 组合体交付给客户的产品的名字，用匠心的 logo（2026-11-20 定，P40）。它和平台名「匠心智能体平台」是什么关系，待定。放不下全称的地方用短名「匠心」，是提议 |
| Kun | 后端框架：为 Agent 时代构建的多租户平台框架，模型服务也由它提供；包名统一为 `Kun.*`（定位已定，代码归并在路线阶段 3） |
| Qian | 前端框架，包名 `@cavailab/qian-*`。冻结在 0.2.1（2026-11-20 定，P38） |
| SanYuanAgent | 智能体引擎，一个独立运行的 SDK，工站、产线、工厂三级智能体的大脑（2026-11-17 定名）。匠心工业智能体平台的 Agent 运行时改用 DSH 以后（P37），它以后怎么接，待定 |
| DSH | 一个开源的智能体运行框架，npm 包 `@deepseek-ai/dsh`，按 MIT 许可使用。匠心工业智能体平台的 Agent 运行时和界面外壳（2026-11-20 定，P37、P38）；现在钉的版本是 `0.2.2-rc.5`。文档里称呼它只写 DSH，不写它的全称：全称是注册商标，不进我们的产品名；照引上游原文和许可、商标声明时照写（这种写法待产品负责人确认） |

「路线阶段」指[路线](06-roadmap.md)第 2 节的阶段 0 至 4。合并蓝图内部另有一套阶段 0 至 4，是路线阶段 3 里面的步骤。「里程碑」指路线第 2.1 节的 M0 至 M8。

过渡目录里的原件多数写于这些名字定下之前，用的是当时的叫法；与本表有出入时，以平台级裁定（[2026-11-17](decisions/2026-11-17-platform.md)、[2026-11-19](decisions/2026-11-19-platform.md)）为准。

**名字里带 `qian` 的字面。** 组件 id 的前缀 `qian.`、清单与配置的文件名（`.qian-plugin/plugin.json`、`qian.profile.yml`、`qian.patch.yml`）、`qian` 命令行、`@qian/*` 的导入名保留不改（已定）：它们已经落库、上线或冻结，改动的代价大而不带来功能。它们只是字面，不表示产品名，也不表示前端框架。

## 2 理念

| 术语 | 含义 |
|---|---|
| 三元全智生命体 | 平台的设计理念。三元给躯体，全智给心智，生命体给活法 |
| 三元 | 结构怎么融合：云边端；工蜂、章蜂、群蜂；人机物。在平台里对应底座 Kun 与 Qian |
| 全智 | 智能到什么水平。在平台里对应 SanYuanAgent。引擎的名字取自理念的头两个字，不表示它对应「三元」 |
| 生命体 | 平台上长出来的系统与智能体的组合，在反馈环里运转并改进 |
| 工蜂、章蜂、群蜂 | 智能体的三种形态，对应工站、产线、工厂（已定） |
| 具身智能体 | 工站一级的形态（工蜂）：感知工件，调用技能，控制工具完成作业 |
| 协同智能体 | 产线一级的形态（章蜂）：协调工序、工站和物料，保持生产节拍 |
| 超级智能体 | 工厂一级的形态（群蜂）：协调跨系统制造任务，支撑物理 AI 研发 |
| 具身大脑 | 工站技术架构里的一层：融合视觉、点云和工艺信息，识别工件，生成动作目标与约束 |
| 工控小脑 | 工站技术架构里的一层：校验运动约束，执行轨迹插补、伺服和工艺控制，反馈偏差 |
| 工业生命体 | 「从工业智能体走向工业生命体」里的目标状态。本仓库的理解：三级智能体连成一体，在反馈环里自己运转、代谢和进化；待产品负责人确认 |
| 反馈环 | 人的意图与判断 → 系统的理解与决策 → 环境被行动改变 → 结果成为反馈与记忆 → 回到人 |
| 自然语言构建 | 人用自然语言描述意图，智能体生成或修改声明式表面，经校验和人工批准后上线 |

## 3 平台术语

| 术语 | 含义 |
|---|---|
| 组件 | 一个文件夹加一份清单、若干声明式表面和可选的代码；分发与安装的单位 |
| 插件 | 组件的运行时形态：挂进共享上下文，贡献服务、监听器和可撤销的副作用 |
| 表面 | 组件向外暴露的一类声明式内容：技能、子 Agent、命令、钩子、MCP 服务器、工具、界面、元数据、业务元数据、配置补丁。另新增知识库（已定，格式待定） |
| 清单 | 组件根目录下描述它的那份 JSON 文件 |
| 能力的三个角色 | 契约（接口与词汇）、提供方（实现）、消费方。消费方只依赖契约包 |
| 契约包 | 一项能力里只放接口、词汇类型、事件定义与错误码的那个包，没有实现 |
| 跨服务契约 | 服务之间共用的数据约定：令牌字段、事件信封、结构化错误、能力条目。冻结之后只做加法。与「契约包」是两回事 |
| 组件运行时 | 装载组件、把它们挂进共享上下文的那个很小的核心。后端与前端各有一个，语义相同 |
| 内核档、平台档 | 合并之后 Kun 的两档：内核档是不带产品语义、可以单独安装的通用机制；平台档带产品语义，以组件形式装配 |
| 范围 | 一项注册的归属：全局，或者恰好一个租户、应用或 Agent 会话。另加 Agent 一级的范围（已定），用来给某个 Agent 长期挂组件；它还没有进规格 |
| profile | 一份具名的插件组装，也是一个可部署单元 |
| 组合包 | 带着一组配置条目的组件，被 profile 引用时整层叠加 |
| 补丁 | 对插件树里某个条目的替换、禁用或插入 |
| 插件树 | 由 profile、组合包和各层补丁叠出来的全部条目 |
| 目录市场 | git 仓库里的一份清单文件，列出可以安装的组件及其来源 |
| 信任等级 | 组件的来源等级，决定它能带什么形态的代码、在哪里运行 |
| 主体 | 行事的一方：`user`（人）、`service`（服务）、`agent`（智能体） |
| 委托链 | 令牌里写明「谁代表谁行事」的一串记录 |
| 能力目录 | 平台全部能力的登记：输入输出 Schema、副作用等级、所需权限、是否对 Agent 暴露 |
| 强制执行点 | 每次能力调用必经的权限判定位置 |
| 协同消息 | Agent 与 Agent 之间往来的消息，经平台的信箱转交 |
| 人审 | 人对协同消息、Agent 要发出去的内容、智能体生成的变更或高风险动作做批准、修改或驳回 |
| 出站确认 | Agent 往外发之前，由发件方的主人确认。「发出去」包括发给别的 Agent、发给别人、写外部系统（已定） |
| 入站审核 | 别人的 Agent 发来的消息送达我的 Agent 之前，由我审核。起步出站、入站两道都必审（已定） |
| 独立运行 | SanYuanAgent 不接平台时的运行方式：身份、策略、记录都在本机，只要一个模型端点（提议） |
| 接入平台 | SanYuanAgent 接上 Kun 之后的运行方式：身份、能力、策略、审计、协同与模型服务由 Kun 提供。设备经入网接入，集群里的服务经网关换发的内部令牌接入（提议） |
| 入网 | 一台设备上的引擎第一次接入平台：在本机生成密钥，由主人本人在平台上批准，之后用设备密钥换短期令牌（提议） |
| 模型服务 | 由 Kun 提供的一项平台能力（已定）。照来源仓库已有的决策，它管模型目录、租户路由、配额与计量；模型请求的转发由模型网关承担 |
| 模型网关 | 转发模型请求并做限流、统计的外部组件，后面是推理集群与外部的模型供应方。它也承载 MCP 流量，所以有的地方写作「模型与 MCP 网关」 |
| 本机模型 | 设备上的小模型，由设备上的推理运行时提供。提议它不经过模型网关，用量由引擎上报 |

## 4 角色与产品形态

出自 [2026-11-19 平台级裁定](decisions/2026-11-19-platform.md)，展开见[角色与产品形态](09-roles-and-product.md)。

| 术语 | 含义 |
|---|---|
| 平台开发 | 两种角色之一：开发 Agent 框架与企业级应用平台的人 |
| 最终用户 | 两种角色之一，也叫普通开发：基于 Agent 平台，在企业级框架上构建自己需要的软件。不负责 Agent 框架与企业级核心的开发，只使用工具 |
| Agent 框架 | 平台开发交付的两样东西之一：智能体引擎 SanYuanAgent 加 Agent 平台。2026-11-20 起 Agent 运行时用 DSH（P37），Agent 框架由什么组成，待定 |
| 企业级应用平台 | 平台开发交付的两样东西之一，也叫企业级框架：后端 Kun 加前端 Qian，里面有应用市场 |
| Agent 平台 | 最终用户的使用界面。它的客户端基于企业级框架；收起对话区，就是企业级应用平台。2026-11-20 起界面外壳用 DSH 的客户端（P38），这两句被部分取代，见 [2026-11-20 产品裁定](decisions/2026-11-20-product.md)第 2 节 |
| 组合体 | 把 Agent 框架与企业级框架拼成一个产品的地方，即 `jiangxin` 仓库。现在放的是基于 DSH 的匠心工业智能体平台（2026-11-20，P41） |
| 工作区 | Agent 平台里对话区旁边的一栏，应用、应用市场、集成中心、系统管理的页面在这里打开（提议） |
| 确认卡 | Agent 要改数据或往外发内容时，在对话里给人确认的那张卡片（提议） |
| 业务插件 | 最终用户的两种扩展之一：基于企业级应用平台开发的插件，装上之后是工作区里的应用，也是 Agent 能调用的能力 |
| Agent 组件 | 最终用户的两种扩展之一：加在 Agent 上的组件，例如技能、子 Agent、知识库 |
| 知识库 | 组件里新增的一种内容：一批资料连同它的整理方式。格式待定 |
| 应用互通 | 发布的应用之间可以互相通讯。缺省：目录里看得到，调用与订阅按声明、经批准放行。见[应用互通](10-app-interop.md) |
| 历史系统 | 企业里已有的、不在平台上的业务系统。经连接器接入，见[历史系统接入](11-legacy-systems.md) |
| 连接器 | 把一套历史系统翻译成平台的能力、事件与数据的组件。历史系统在内网的，它的执行部分装在内网，只向外连 |
| 多租户的版本、单租户的版本 | 两种交付版本。提议它们是同一套代码的两种装配 |

## 5 组合体与 DSH

出自 [2026-11-20 产品裁定](decisions/2026-11-20-product.md)，以及组合体代码旁边的说明。代码在仓库根下，各目录的入口见[仓库与归属](05-repositories.md)第 1.1 节。

| 术语 | 含义 |
|---|---|
| Web 端、客户端 | 客户可能用到的两个端（已定，P39）。客户端指装在电脑上的桌面应用，代码在 `apps/desktop/` |
| 管理端 | 管理员用的后台：用户与组织、登录方式、模型接入、工具与插件的策略、审计、实例的开通与回收。先不做，目录 `apps/console/` 先建好（已定，P39） |
| 日历版本号 | 匠心工业智能体平台的产品版本号：`vYYYY.M.D` 正式版，`vYYYY.M.D-N` 补丁版，`vYYYY.M.D-beta.N` 测试版，月和日不补零，构建时注入（已定，P40）。没注入时显示「本地开发」。DSH 自己的版本号另算 |
| 发行目录 | `distribution/`：钉死版本的 DSH、要装的插件包、按文件名顺序叠加的配置补丁，加上启动器和启动前检查。Web 端和客户端都从它启动 DSH |
| 配置补丁 | 叠在 DSH 配置上的一份 YAML 文件，按行 id 关掉、整行改写或插入一行。发行目录的配置补丁放在 `distribution/patches/`，启动时用 `--patch` 叠在最上层，界面上改不动。和第 3 节的「补丁」（插件树里条目的替换）不是一回事 |
| 源码补丁 | 对 DSH 源码的改动，一处一个文件，放在 `patches/`。原则上不改 DSH 的源码，现在只有样例 |
| 品牌包 | `@jx/brand-theme`：把 DSH 界面里的名称、标志、主题色和文案换成匠心的。不改 DSH 的源码 |
| 启动前检查 | `distribution/bin/jx-preflight.mjs`：查 DSH 的版本、插件包、补丁对不对，查不过就不启动。DSH 加载不了某个插件时只停用它、照常启动，品牌包没加载就会带着 DSH 自己的品牌起来，所以要查 |
| 薄壳 | 客户端的一种做法：自己写的 Electron 壳里跑已发布的 DSH，窗口里装它的 Web 界面。另一种是从源码构建 DSH 上游的桌面壳。走哪条没有定，提议走薄壳 |
| 一个用户一个实例 | 提议，没有确认：每个用户一个 DSH 实例，多用户靠实例之间的隔离；登录、租户、授权放在实例外面的门户里 |
| 接触面 | 我们的代码直接碰到的 DSH 接口、配置行、环境变量和文件。升级 DSH 时逐项核对，清单在 `distribution/docs/touchpoints.md` |
| 外联检查 | `tests/egress/`：在不通外网的容器网络里，看 DSH 实例在一组固定操作里想连哪些地址 |
