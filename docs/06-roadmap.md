# 路线与迁移

> 状态：提议（2026-11-17）。已定的有两条：先建仓库、写文档，代码之后一点点迁入；前端更名和后端改名放在同一个冻结窗口里，排在后端归并的最后一批。阶段的划分与顺序是提议，待产品负责人确认。

## 1 迁移的规矩

1. **先建库写文档，代码分批迁。** 迁入完成之前，原仓库照常开发，原来在途的里程碑和任务不受影响。
2. **一个来源仓库只冻结一次。** 冻结窗口里原仓库只读，迁完就在新仓库继续。
3. **带着历史迁。** 提交历史一起带过来，不做「复制一份文件重新开始」。
4. **先并轨，后改名。** 先让两边的代码在一条流水线上跑通，再一个域一批地归并和改名。
5. **能验证才算完成。** 原有的测试和门禁在新仓库里全部通过，才算一步做完。

## 2 阶段

| 阶段 | 进入条件 | 做什么 | 完成条件 |
|---|---|---|---|
| **0 立项** | — | 在 CavaiLAB 建四个仓库；写主页和框架级文档 | 产品负责人对文档里的「提议」与「待定」逐项表态 |
| **1 治理就位** | 阶段 0 完成 | 定参与的人和权限、代码所有者；`main` 的保护与评审规则；任务管理方式；各仓库的 CI 基线；合并蓝图按新的仓库划分修订并确认 | [协作约定](07-governance.md)的待定清单清零；合并蓝图转为已接受 |
| **2 SanYuanAgent 迁入** | 阶段 1 完成 | Python Agent 引擎带历史迁入 `sanyuan-agent`；包名与导入名改掉；边界测试和独立运行测试照旧生效；说明文档以代码为准重写；统一技能的 front matter | 新仓库里测试通过；核心包可以单独安装运行；发出第一个包 |
| **3 Kun 归并与 Qian 更名** | 合并蓝图已接受；原仓库在途工作收口，开着的 PR 全部合入或关闭 | 按合并蓝图分步：冻结与导入 → 构建并轨 → 按域归并与改名 → 首个合并版。前端更名排在按域归并的最后一批，并在这一批迁入 `qian` 仓库 | 全部测试与门禁通过；后端与前端的包各成功发布一次；部署环境换用新包；原仓库归档 |
| **4 协同与生命体** | 阶段 2、3 完成 | 启用 `agent` 主体与委托链；Agent 归属到人；协同服务与人审；审核收件箱；自然语言构建的闭环；社区组件导入器 | 两个人各自的 Agent 在人审之下完成一次跨人协同；一个业务功能由自然语言生成，经批准后上线 |

阶段 3 内部的步骤和每一步的完成标志，见 [kun 仓库的迁移与归并](https://github.com/CavaiLAB/kun/blob/main/docs/migration.md)。

## 3 顺序的理由

- **阶段 2 与阶段 3 可以并行。** Agent 引擎和后端是两套代码，互不依赖。Agent 引擎近期没有在途改动，风险最小，适合先走一遍迁移流程。
- **阶段 3 最重。** 两个后端有重叠的职责，归并是一个域一批地做。原仓库这边正在推进的里程碑先收口，再进冻结窗口。
- **前端排在后端之后。** 后端各域的 `Qian.*` 都改成 `Kun.*` 之后再做前端更名（已定）。这样「Qian」同时指两样东西的时间最短，文档站也只改写一遍。
- **阶段 4 的设计可以早做。** 协同消息信封这类契约的设计不依赖代码迁移，阶段 1 就可以开始；实现要等阶段 2、3 完成。

## 4 风险

| 风险 | 应对 |
|---|---|
| 名字换了所指，新旧文档混着读会误解 | [名称对照](glossary.md)写明生效时点；旧仓库的说明文档指向新仓库 |
| 迁移期间两处同时开发，代码分叉 | 一个来源仓库只冻结一次，窗口里原仓库只读 |
| 归并时把在用的行为改坏 | 两边都有实现的，留有宿主在用、有测试覆盖的一边；每一批归并之后全量测试通过才算完成 |
| 改名让按名字判定的门禁不声不响地失效 | 改名之前先把门禁换成显式的档位表，并带自测 |
| 旧的 PR 编号在新仓库里指向别的东西 | 旧编号改写成带仓库名的完整形式 |
| 包改名影响已有的使用方 | 旧包标为弃用并指向新包名；首个合并版写明破坏性变更 |
| 合并蓝图按一个仓库写，现在分成几个仓库 | 阶段 1 先修订蓝图：目标仓库、目录布局、前端和命令行的去处、包名前缀 |
| 文档先于代码太多，写的和做的对不上 | 文档里区分「已有」与「规划」；每个阶段完成时回头更新 |
