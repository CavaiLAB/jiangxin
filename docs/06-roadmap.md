## 1 迁移的规矩

1. **先建库写文档，代码分批迁。** 迁入完成之前，来源仓库照常开发，在途的里程碑和任务不受影响。
2. **一个来源仓库只冻结一次。** 冻结窗口里来源仓库只读，迁完就在新仓库继续。
3. **带着历史迁。** 提交历史一起带过来，不做「复制一份文件重新开始」。
4. **先并轨，后改名。** 先让两边的代码在一条流水线上跑通，再一个域一批地归并和改名。
5. **能验证才算完成。** 原有的测试和门禁在新仓库里全部通过，才算一步做完。

### 2.1 里程碑

路线重排，最小的一圈提前（已定）。原来的阶段 4 把智能体主体、协同、自然语言构建放在一起，排在最后；Agent 平台既然是最终用户的入口，就不能等到最后才有。下表的顺序已定；每个里程碑都有一个能演示的完成标志。

| 里程碑 | 做什么 | 完成标志 |
|---|---|---|
| **M0 迁移收口** | 在做。后端归并，前端独立成库，引擎核心迁入，即上表的阶段 2、3。后端在途的里程碑照旧 | 阶段 2、3 的完成条件 |
| **M1 能问能查** | 三栏工作台；启用智能体主体；能力目录给 Agent 用，先只读；工作区的页面作为上下文 | 用户问一个数据问题，Agent 在本人的权限与授给它的范围之内查到，并在工作区打开对应的页面；没权限的人来问，被拒绝并留审计 |
| **M2 能办事** | 写类能力；对话里的确认卡；高风险动作要人确认 | Agent 起草一张单据，人确认后落库，审计里看得到是谁确认的 |
| **M3 一句话做应用** | 按元数据读写业务记录；列表与详情的渲染器；构建闭环；回滚 | 业务人员用自然语言做出一个带表单、列表、权限的应用，经批准后在租户里可用 |
| **M4 给 Agent 加组件** | 我的 Agent；组件库；技能、子 Agent、知识库模板；社区组件的导入 | 用户给自己的 Agent 装上一个技能和一个知识库，Agent 当场用上 |
| **M5 应用互通与市场** | 互通的声明与安装确认；流程；私有市场上架 | 两个应用经事件和能力调用配合完成一件事，其中一个从私有市场安装 |
| **M6 历史系统** | 连接器的规范；第一档与第二档；一个参考连接器；装在内网的执行部分 | Agent 查到历史系统里的数据，并在人确认后写回一笔 |
| **M7 协同与人审** | 信箱；待确认；两道关口；移动端审批 | 两个人的 Agent 在人审之下完成一次跨人协同 |
| **M8 端与三级** | 桌面端；设备接入；工站、产线、工厂 | 一台设备上的 Agent 入网，接受分派并上报结果 |

- M6 可以和 M3 至 M5 并行，它只依赖 M1 和 M2。
- M7 的契约设计现在就可以开始：消息信封、审核状态。
- M3 依赖的东西是当前最大的一块没做的：按元数据读写业务记录，列表与详情的渲染器。由 Schema 渲染的表单已有。
- M1 要三样东西各自先打通，再合起来演示：智能体主体、MCP 路由、三栏工作台。

各里程碑展开在：[角色与产品形态](09-roles-and-product.md)（M1、M2）、[一切皆插件](03-plugin-model.md)（M3、M4）、[应用互通](10-app-interop.md)（M5）、[历史系统接入](11-legacy-systems.md)（M6）、[Agent 协同](04-agent-collaboration.md)（M7）、[三种形态](08-industrial-forms.md)（M8）。

里程碑怎么拆成任务、与后端在途的里程碑怎么衔接，待定，见第 5 节。

## 3 顺序的理由

- **阶段 2 与阶段 3 可以并行。** Agent 引擎和后端是两套代码，互不依赖，引擎适合先走一遍迁移流程。引擎的改动频率在冻结之前再核对。
- **阶段 3 最重。** 两个后端有重叠的职责，归并是一个域一批地做。原定来源仓库这边正在推进的里程碑先收口、再进冻结窗口；2026-11-17 改为现在开始（P20）。
- **前端原定排在后端之后，2026-11-17 改为同时开始（P21）。** 原来的考虑是：后端各域的包名统一之后再动前端，文档站只改写一遍。同时开始之后，这一点不再自动成立。
- **阶段 4 的设计可以早做。** 协同消息信封这类契约的设计不依赖代码迁移，阶段 1 就可以开始；实现要等阶段 2、3 完成。
- **最小的一圈为什么提前（2026-11-19）。** 最终用户的入口是 Agent 平台。入口、智能体主体、Agent 调用能力这一圈不通，后面的构建、互通、协同都没有地方落。所以先做只读的一圈（M1），再做写（M2），之后才是构建、组件、互通、历史系统与协同。

## 4 风险

| 风险 | 应对 |
|---|---|
| 新旧文档混着读会误解 | 过渡目录里的原件与[平台级裁定](decisions/2026-11-17-platform.md)有出入时，以平台级裁定为准；来源仓库的说明文档指向新仓库 |
| 迁移期间两处同时开发，代码分叉 | 一个来源仓库只冻结一次，窗口里来源仓库只读 |
| 归并时把在用的行为改坏 | 两边都有实现的，留有宿主在用、有测试覆盖的一边；每一批归并之后全量测试通过才算完成 |
| 改名让按名字判定的门禁不声不响地失效 | 改名之前先把门禁换成显式的档位表，并带自测 |
| 旧的 PR 编号在新仓库里指向别的东西 | 旧编号改写成带仓库名的完整形式 |
| 包改名影响已有的使用方 | 旧包标为弃用并指向新包名；首个合并版写明破坏性变更 |
| 已接受的合并蓝图按一个仓库写，现在分成几个仓库 | 修订项已登记（S1-DEC-038，在 `kun` 的过渡目录里）；阶段 1 确认并回写：目标仓库、目录布局、前端和命令行的去处、包的作用域 |
| 前后端拆开之后又要跨仓库钉版本 | 由版本矩阵和契约的兼容性检查把关；端到端测试改用发布出来的镜像或包 |
| 文档先于代码太多，写的和做的对不上 | 文档里区分「已有」与「规划」；每个阶段、每个里程碑完成时回头更新 |
| 人审成了走过场 | 起步每条必审，并记下每条审了多久；放宽只能显式配置；审核界面把谁发给谁、要动用什么能力摆在最前面 |
| Agent 生成的应用质量参差 | 确认方案、校验器、一致性测试、预览，四道关；发布之后可以回滚 |
| 最小的一圈依赖的东西多 | M1 只做只读；智能体主体、MCP 路由、三栏工作台三样先各自打通，再合起来演示 |
| 历史系统接入的成本被低估 | 分三档，先做界面融合；一套系统一个连接器，能力一项一项放开 |
| 被诱导的 Agent 越权，或者把内容发出去 | 权限取交集；只许人做的能力不给 Agent；外部内容当数据；发出去之前人确认 |
