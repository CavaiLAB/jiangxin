## 2 里程碑与工作线

### 2.1 里程碑

路线重排过一次，最小的一圈提前（已定）：人用平台的入口是 Agent 工作区，入口这一圈不能等到最后才有。下表的顺序已定；每个里程碑都有一个能演示的完成标志。

| 里程碑 | 做什么 | 完成标志 |
|---|---|---|
| **M0 迁移收口** | Kun 的归并：两套后端代码并成一个仓库，发出合并后的版本 | Kun 已经发布合并后的稳定版；旧应用外壳按冻结的 Qian 0.2.1 归档验收，见 [Kun 的外壳迁移决策](https://github.com/CavaiLAB/kun/blob/main/pm/tasks/S1-DEC-039.md) |
| **M1 能问能查** | Agent 工作区接上平台；启用智能体主体；能力目录给 Agent 用，先只读；右侧的页面作为上下文 | 用户问一个数据问题，Agent 在本人的权限与授给它的范围之内查到，并在右侧打开对应的页面；没权限的人来问，被拒绝并留审计 |
| **M2 能办事** | 写类能力；对话里的确认卡；高风险动作要人确认 | Agent 起草一张单据，人确认后落库，审计里看得到是谁确认的 |
| **M3 一句话做应用** | 按元数据读写业务记录；表单、列表与详情的渲染器；构建闭环；回滚 | 业务人员用自然语言做出一个带表单、列表、权限的应用，经批准后在租户里可用 |
| **M4 给 Agent 加组件** | 我的 Agent；组件库；技能、子 Agent、知识库模板；社区组件的导入 | 用户给自己的 Agent 装上一个技能和一个知识库，Agent 当场用上 |
| **M5 应用互通与市场** | 互通的声明与安装确认；流程；私有市场上架 | 两个应用经事件和能力调用配合完成一件事，其中一个从私有市场安装 |
| **M6 历史系统** | 连接器的规范；第一档与第二档；一个参考连接器；装在内网的执行部分 | Agent 查到历史系统里的数据，并在人确认后写回一笔 |
| **M7 协同与人审** | 信箱；待确认；两道关口；移动端审批 | 两个人的 Agent 在人审之下完成一次跨人协同 |
| **M8 端与三级** | 桌面端；设备接入；工站、产线、工厂 | 一台设备上的 Agent 入网，接受分派并上报结果 |

- M6 可以和 M3 至 M5 并行，它只依赖 M1 和 M2。
- M7 的契约设计现在就可以开始：消息信封、审核状态。
- Agent 之间协同的机制排在 M7（先后已定）；设备上的本机模型等设备一侧用什么运行时定下来再定，排在 M8 之前（先后已定）。两件的细则仍待定。
- M3 依赖的东西是当前最大的一块没做的：按元数据读写业务记录，表单、列表与详情的渲染器。
- M1 要三样东西各自先打通，再合起来演示：智能体主体、MCP 路由、Agent 工作区接上平台。
- M7 一行里的「待确认」是排里程碑时写的。「待确认」这一页已定随确认卡的最小一圈先做，对应 M2，见下面的三条线。移动端还没有定。

| 先后 | 做什么 | 做完能演示什么 | 对应的里程碑 |
|---|---|---|---|
| 第一条线 | 确认卡的最小一圈：平台上等人输入的任务与推送，对话里的确认卡与「待确认」的页面，加一个要人确认的写能力 | Agent 起草一张单据，对话里出确认卡，人点了才落库；审计里看得到是谁点的 | M2 |
| 第二条线 | 生成应用的最小一圈：按数据描述读写业务记录的后端，数据描述的登记与版本；表单、列表的渲染器，组件库带上给 Agent 看的组件目录；管理端的外壳接上登录和真的接口；给 Agent 用的生成工具，即查控件、查数据、校验、预览、试发布；运行时安装数据描述的包，发布的审批和记录 | 说一句话，右侧生成一个填报的日报，有表单、列表、权限；预览，发布到本租户，管理端的菜单里出现 | M3 |

### 2.3 工作线的先后

提议：

1. 线 0 先做。
2. 然后线 1，和线 2、3、4 里的契约部分并行。
3. 线 6、7、8 排在契约之后。管理端、DSH 的对接、确认卡都要用权限的远程接口和模型服务的接口；这两个接口先定下来，后面的才不返工。

这是工作线之间的先后，不改第 2.1 节已定的顺序。工作线怎么对到里程碑上，没有定，见第 5 节。

## 3 顺序的理由

- **最小的一圈为什么提前。** 人用平台的入口是 Agent 工作区。入口、智能体主体、Agent 调用能力这一圈不通，后面的构建、互通、协同都没有地方落。所以先做只读的一圈（M1），再做写（M2），之后才是构建、组件、互通、历史系统与协同。
- **确认卡为什么不等 M1。** 先用替身，这一圈可以和 M1 并行；等 M1，它就排在 M1 后面。
- **两个接口为什么排在前面。** 这是第 2.3 节提议的理由：权限的远程接口、模型服务的接口是管理端、工作区服务和确认卡共用的。

## 4 风险

| 风险 | 应对 |
|---|---|
| 文档先于代码太多，写的和做的对不上 | 文档里区分「已有」与「规划」；每个里程碑完成时回头更新 |
| 上游的 DSH 发版快，升级会让我们的插件和补丁悄悄失效 | 版本钉死；升级照 [DSH 更新之后做什么](10-dsh-upgrade.md)的步骤，逐项核对接触面 |
| 最小的一圈依赖的东西多 | M1 只做只读；智能体主体、MCP 路由、Agent 工作区接上平台三样先各自打通，再合起来演示 |
| 权限的远程接口迟迟不定，各个系统各做一套 | 规矩已定：不论做什么系统，权限都走 Kun 这一套；接口排在工作线的前面 |
| 人审成了走过场 | 起步每条必审，并记下每条审了多久；放宽只能显式配置；审核界面把谁发给谁、要动用什么能力摆在最前面 |
| Agent 生成的应用质量参差 | 确认方案、校验器、一致性测试、预览，四道关；发布之后可以回滚 |
| 历史系统接入的成本被低估 | 分三档，先做界面融合；一套系统一个连接器，能力一项一项放开 |
| 被诱导的 Agent 越权，或者把内容发出去 | 权限取交集；只许人做的能力不给 Agent；外部内容当数据；发出去之前人确认 |
