路线重排过一次，最小的一圈提前（已定）：人用平台的入口是 Agent 工作区，入口这一圈不能等到最后才有。下表的顺序已定；每个里程碑都有一个能演示的完成标志。

| 里程碑 | 做什么 | 完成标志 |

### 2.4 产品页面放到匠心以后的三步

已定（2026-11-27）：Kun 保持现有基础框架和接口，继续负责认证、会话和权限；登录、工作区和管理端等产品页面统一放到匠心重新设计。次序是：

1. 先列清各个包的去向。匠心这边的清单见[包与应用的去向](15-packages.md)；Kun 的包、已发布的包、文档、示例和站点导航在 Kun 的仓库里整理。
2. 修订文档。
3. 再用登录页跑通前后端流程。

登录页是匠心第一处把自己的页面和 Kun 的接口从头接到尾的地方：页面在匠心，认证与会话在 Kun。跑通以前匠心这一侧要先有什么、哪些要等 Kun 的接口进公开契约，见包与应用的去向第 4 节。

下面几条是整理时的读法：

- 这三步和第 2.3 节的先后不冲突。登录页用的是 Kun 已有的认证与会话接口，不等权限的远程接口和模型服务的接口。
- 2026-11-27 的答复里还定了认证页先做找回密码与验证码登录，其余几页随后；和新方向合起来读，是登录页先跑通，再做找回密码与验证码登录，其余随后。
- 三步各拆成哪条工作线上的任务，随照工作线重排看板一起定。设计规范的底稿见[设计规范](16-design.md)，等产品负责人看过才算数。

## 3 顺序的理由

- **最小的一圈为什么提前。** 人用平台的入口是 Agent 工作区。入口、智能体主体、Agent 调用能力这一圈不通，后面的构建、互通、协同都没有地方落。所以先做只读的一圈（M1），再做写（M2），之后才是构建、组件、互通、历史系统与协同。
- **确认卡为什么不等 M1。** 先用替身，这一圈可以和 M1 并行；等 M1，它就排在 M1 后面。
- **两个接口为什么排在前面。** 这是第 2.3 节的理由：权限的远程接口、模型服务的接口是管理端、工作区服务和确认卡共用的。

## 4 风险

| 风险 | 应对 |
|---|---|
| 文档先于代码太多，写的和做的对不上 | 文档里区分「已有」与「规划」；每个里程碑完成时回头更新 |
| 上游的 DSH 发版快，升级会让我们的插件和补丁悄悄失效 | 版本钉死；升级照 [DSH 更新之后做什么](10-dsh-upgrade.md)的步骤，逐项核对接触面 |
| 最小的一圈依赖的东西多 | M1 只做只读；智能体主体、MCP 路由、Agent 工作区接上平台三样先各自打通，再合起来演示 |
| 权限的远程接口迟迟不定，各个系统各做一套 | 规矩已定：不论做什么系统，权限都走 Kun 这一套；接口排在工作线的前面 |
| 人审成了走过场 | 起步每条必审，并记下每条审了多久；放宽只能显式配置；审核界面把谁发给谁、要动用什么能力摆在最前面 |
| Agent 生成的应用质量参差 | 确认方案、校验器、一致性测试、预览，四道关；发布之后可以回滚 |
| 历史系统接入的成本被低估 | 分三档，先做界面融合；一套系统一个连接器，能力一项一项放开 |
| 被诱导的 Agent 越权，或者把内容发出去 | 权限取交集；只许人做的能力不给 Agent；外部内容当数据；发出去之前人确认 |
