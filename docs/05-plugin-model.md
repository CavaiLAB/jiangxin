# 一切皆插件

> 状态：规划稿，2026-11-26 按收拢后的方向改过。标法见[平台做什么与设计理念](01-vision.md)开头；本文的「已有」指在 Kun 的仓库里已经实现，说到本仓库时另外写明。
>
> 组件模型在 Kun 里已经成文并实现了大部分，本文是它的概述，细节以 Kun 的[组件模型规格](https://github.com/CavaiLAB/kun/blob/main/docs/prd/specs/component-model.md)为准。Agent 一级的范围与知识库（已定，P29、P30）还没有进那份规格；回写之前规格仍是原来的写法，以平台级裁定为准。
>
> 名字里带 `qian` 的地方（已定）：组件 id 前缀、清单目录这些运行期字面保留不改，`qian` 命令行与 `@qian/*` 导入名暂不改；它们都不表示产品名。

## 1 原则

一切皆插件是统一的原则（已定，P6）。平台没有只能打补丁的特权内核。运行时只有一个很小的核心：上下文、服务注册、类型化事件、可撤销的副作用、装载器。租户、身份、权限、文件、配置、网关、事件、审计，以及每一个业务功能，都是插件。

- 扩展平台的方式是把一个插件挂在别的插件旁边，不是修改内核。
- 插件声明自己依赖哪些服务，依赖就绪才启动，装载顺序由依赖关系决定。
- 插件做的每一项注册都是副作用，卸载时按相反的顺序撤销。
- 任何一项能力都可以从配置里替换、按范围收窄或遮蔽。

这是智能体能发现、调用乃至生成平台能力的前提：只要存在一块只有内部人能改的内核，第三方和智能体就只能在它允许的位置扩展。

部署的两种形态、多租户版与单租户版，也尽量用插件的形式实现（已定，2026-11-26，P83）；照整理时的读法，是把它们之间的差别做成 Kun 的组件。见[总体架构](04-architecture.md)第 5 节。

## 2 组件是什么

组件 = 一个文件夹 + 一份清单 + 若干声明式表面 + 可选的代码。它是分发与安装的单位。没有代码、只有表面的组件是常态。

```text
<组件>/
  .qian-plugin/plugin.json      清单，唯一必需的文件
  skills/<name>/SKILL.md        技能
  agents/<name>.md              子 Agent
  commands/<name>.md            给人用的命令
  hooks/hooks.json              钩子
  .mcp.json                     MCP 服务器声明
  tools/<name>.json             面向模型的工具描述
  ui/manifest.json              界面：远程模块、页面、控件
  metadata/                     权限点、角色、事件、消息类型
  forms/ lists/ flows/ pages/   业务元数据：表单、列表、流程、页面
  schemas/                      JSON Schema
  config/qian.patch.yml         配置补丁
  src/                          可选：.NET 或 TypeScript 代码
```

谈文件时叫「组件」，谈运行时叫「插件」：组件装进来、按一个条目挂进共享上下文之后，就是插件。

### 2.1 两种扩展：业务插件与 Agent 组件

用平台的人有两种扩展的办法（已定，P25）：在企业级平台上开发业务插件，给 Agent 增加组件。两种都是上面说的组件，区别在装在哪、里面主要是什么。下表是展开，属于提议。

| | 业务插件 | Agent 组件 |
|---|---|---|
| 装在哪 | 企业级平台 | Agent |
| 里面有什么 | 表单、列表、流程、页面；权限点与角色；事件；连接器配置 | 技能、子 Agent、命令、钩子、MCP 服务器声明、工具描述、知识库 |
| 谁来运行 | Kun 存储、校验、执行；界面由平台的渲染器按数据描述画出来 | Agent 运行时加载与执行，现在是 DSH（已定，P37）；Kun 登记，并按范围过滤 |
| 给谁用 | 租户里有权限的人，和他们的 Agent | 我的某个 Agent，或者共享给团队 |
| 现状 | 组件格式、清单校验、安装已有；按元数据读写业务记录、表单与列表的渲染器、流程是规划 | DSH 自己能加载技能、子智能体和 MCP 服务器；从平台取组件是规划，怎么取没有定；知识库这种内容还没有 |

一个组件可以两种内容都带。例如「合同管理」是业务插件，同时自带一个「合同审查」技能。装上它，多一个能打开的应用，Agent 也多一样本事。

平台提供所需的基础组件（已定，P25）。现在说的基础组件是：租户、身份、权限、事件、审计、文件、定时作业、消息通知、模型服务；业务插件直接用，不用自己做。其中权限都走 Kun 这一套（已定，P86）。前七项的核心已有，消息通知与模型服务是规划。

### 2.2 产品这一侧的插件

上面说的组件装在企业级平台上，由 Kun 的组件运行时装载。匠心这一侧还有另一层插件，装在 DSH 里：

| 哪一种 | 是什么 | 现状 |
|---|---|---|
| DSH 的插件 | 一个 npm 包，分宿主一半和浏览器一半：宿主一半跑在 DSH 的实例里，浏览器一半跑在 DSH 的客户端里 | 本仓库已有：品牌包、企业插件的样板，见 [packages 的说明](https://github.com/CavaiLAB/jiangxin/blob/main/packages/README.md) |
| 页面插件 | 只有浏览器一半的 Cordis 插件。管理端的页面是这一种，同样的内容要能显示在 DSH 右侧的页签里（已定，P65、P66）；「待确认」已定做成这一种，两边装同一份（已定，P71） | 规划。同一份页面两边都能装的做法是提议 |
| 数据描述的应用 | 智能体生成的应用：数据模型、表单、列表、流程、菜单、角色，界面由平台的渲染器画出来，生成的代码不当页面插件装（已定，P67） | 规划，排在里程碑 M3 |

两层是两套机制。Kun 的组件里的界面表面，在匠心的外壳里怎么承接，没有定，见第 8、9 节。每一种怎么动手做，见[在平台上做开发](11-development.md)。

## 3 表面一览

表面是组件向外暴露的一类声明式内容，是组件的顶层分类。

| 表面 | 内容 | 主要由谁承接 |
|---|---|---|
| 技能 | 教 Agent 怎么做一类事：front matter 加正文，可带参考资料与脚本 | Agent 运行时按需加载；Kun 登记并按范围过滤 |
| 子 Agent | 一个专门角色的定义：front matter 加系统提示 | Agent 运行时 |
| 命令 | 给人用的命令，不进入模型的消息 | 命令行；界面上的命令入口待定 |
| 钩子 | 在平台事件或 Agent 运行时的事件上触发的动作 | Kun 的事件体系；与 Agent 运行时的事件怎么桥接，待定 |
| MCP 服务器 | 外部工具服务的声明 | Agent 运行时的工具集；出网目标受 Kun 的策略约束 |
| 工具 | 面向模型的工具描述，由代码派生或手写 | Kun 的能力目录；Agent 运行时调用 |
| 界面 | 远程模块、页面、控件、设置卡 | Kun 仓库里现有的应用外壳按需加载；在匠心的外壳里怎么承接，待定 |
| 元数据 | 权限点、角色、事件、消息类型 | Kun 的权限、事件、通知各自的注册表 |
| 业务元数据 | 表单、列表、流程、页面 | Kun 存储与校验；平台的渲染器按数据描述画界面 |
| 配置补丁 | 对插件树里其他条目的替换、禁用或插入 | Kun 的装载器 |
| 知识库 | 一批资料连同它的整理方式。新增的一种内容（已定，P30）；格式待定，提议写明资料来源、整理与索引的方式、谁能访问 | 待定。提议 Kun 登记并按范围与权限过滤，Agent 运行时检索 |

Agent 运行时现在是 DSH（已定，P37）。表里写「Agent 运行时」的几项，DSH 自己都有对应的能力；Kun 登记的这些表面怎么送进 DSH 的实例，没有定。

所有模型看得到的东西都登记在注册表里，并且按范围过滤。被过滤掉的项既不出现在目录和提示词里，调用时也被拒绝，和不存在没有区别。

## 4 运行时的几个概念

- **上下文与服务键。** 插件经上下文拿到别的插件提供的服务，例如文件、身份、权限。服务键由定义它的包拥有。
- **能力的三个角色。** 一项能力拆成契约（接口与词汇，发成契约包）、提供方（一个或多个实现）、消费方。扩展插件只依赖契约包，不依赖具体实现。把文件存储从本地盘换成对象存储，消费方不用改。
- **事件就是扩展点。** 事件有五种分发方式：观察、环绕、并行、按序、取首个返回值。权限判定、租户校验这类强制执行点就是环绕式的监听器。
- **范围。** 任何一项注册要么是全局的，要么只属于一个范围。范围现有三种：租户、应用、Agent 会话。范围内的注册遮蔽同名的全局项。租户启用一个插件，就是在自己的范围里挂上它的条目；租户定制，就是在自己的范围里做一个遮蔽注册。另加一种 Agent 一级的范围（已定，P29），用来给「我的某个 Agent」长期挂组件；它还没有进规格，也没有实现，与另外三种范围怎么叠见第 9 节。
- **profile、组合包与补丁。** 运行中的平台是一棵插件树，由几层按顺序叠出来：profile 列出的组合包、profile 自己的补丁、本机补丁、命令行补丁，运行中再叠上存在数据库里的租户补丁。一条命令可以把整棵树打印出来，打印出的任何条目都能被补丁替换。

## 5 安装与目录

- **一条命令安装。** 安装一个组件，就是把它的表面复制进项目、把代码部分加成包依赖、把配置条目写进当前 profile 的补丁。安装、升级、移除、列出与打印配置树的命令已有；健康检查、成套的脚手架模板、本机运行、打包、签名与发布的命令是规划。
- **目录市场是一份清单文件。** 市场是 git 仓库里的一个 JSON 文件，每个条目只写名字、来源（本地路径、网址、git 子目录）、安装与认证策略、分类。清单格式与校验已有；官方市场仓库、由它生成目录网站、社区发现是规划。
- **多个市场并存。** 官方市场、租户私有市场、社区市场可以同时配置。
- **应用也是组件。** 一个业务应用 = 一个组合包加一个市场条目。以后的商业市场（授权、计费、审核）叠在同一格式上，不另起格式。

### 5.1 发布范围

提议。用平台的人做出来的组件，按发布到多大的范围，由不同的人批准。

| 范围 | 谁看得到 | 谁批准 |
|---|---|---|
| 只给自己 | 本人和本人的 Agent | 本人 |
| 本租户 | 租户里有权限的人 | 租户管理员 |
| 上架市场 | 私有市场：本企业自己的范围。公共市场：所有租户 | 私有市场由企业自己的审核人；公共市场由平台审核 |

挂在「我的某个 Agent」上的组件，用 Agent 一级的范围（已定，P29）。只给本人用的业务插件、草稿的预览怎么限定到本人，待定，见第 9 节。

### 5.2 内置内容

平台内置智能体、知识库模板等内容（已定，P25）。提议把智能体模板、知识库模板、应用模板、连接器模板都做成组合包，放在官方市场里。

安装有两种方式：拷贝一份自己改；或者托管安装，跟着发布者升级，自己的改动叠在上面。这是 Kun 已有的决策，还没有实现。

| 内置内容 | 例子 | 装上之后 |
|---|---|---|
| 智能体模板 | 搭建助手、管理助手、数据分析助手、文档助手、审批助手 | 成为我名下的一个 Agent，可以再加组件 |
| 知识库模板 | 制度文件、产品资料、合同范本、设备手册 | 一个带好整理方式的空库，往里放自己的资料 |
| 应用模板 | 审批、台账、工单、点检、采购申请 | 一个能用的应用，再让 Agent 按自己的业务改 |
| 连接器模板 | 标准接口描述、数据库只读视图、文件交换 | 填上地址与认证方式，生成一套历史系统的连接器 |

上表的例子是举例，第一批做哪些待定。连接器见[历史系统接入](07-legacy-systems.md)。

## 6 用现成的生态组件

社区里已经有大量现成的 Agent 组件：技能、子 Agent、命令、钩子、MCP 服务器声明、设置片段，按类型放在文件夹里，一条命令安装，并且有开源的组件目录在汇集它们。平台的表面采用同样的文件格式，所以对接是文件对文件：

| 社区组件 | 平台里的表面 |
|---|---|
| 技能：带 front matter 的 `SKILL.md`，可带参考资料与脚本 | `skills/<name>/SKILL.md` |
| 子 Agent：front matter 加系统提示的 Markdown | `agents/<name>.md` |
| 命令：Markdown | `commands/<name>.md` |
| 钩子：JSON | `hooks/hooks.json` |
| MCP 服务器声明：JSON | `.mcp.json` |
| 设置片段 | 配置补丁 |
| 整包插件与市场清单 | 组件文件夹与目录市场条目 |

目标（已定，P6）：开源组件目录里的组件能装进平台直接用。

企业不能把社区组件原样装进生产，所以装进来要过几道关：

1. **信任等级。** 每个组件有信任等级。社区来源的组件现阶段只接受不带代码的，它的代码永远不进平台的共享进程。
2. **装之前看得见。** 安装前展示它包含哪些表面、要哪些权限与密钥、会访问哪些外部地址，由有权限的人确认。应用之间的调用与订阅也要列在这张单子上（已定，P26；细则是提议），见[应用互通](06-app-interop.md)第 4 节。
3. **按租户启用。** 组件装进来不等于人人可用，租户在自己的范围里启用，谁启用的留审计。
4. **带脚本的部分不放行。** 技能目录里的脚本、命令里的内联 shell 是代码。现行规则：社区来源的组件里出现内联 shell，校验直接不过；这类脚本只在命令行、开发者本机，或平台自有组件的受限执行器里运行。放到沙箱里执行是提议，见下。

要做的事（规划）：

- 一个导入器，把社区目录的条目转成组件文件夹：补清单、定信任等级、跑校验器、列出它要的权限，并核对组件的许可与署名要求。
- 工具名的映射。社区组件里写的工具名与平台里的工具名对不上的，导入时要有对应办法。
- 统一技能的 front matter。社区规范与 Kun 现有规格的字段有出入；Agent 运行时用 DSH 以后，还要对上 DSH 认的写法。怎么对齐待定。
- 定下社区技能里的脚本在哪里执行。提议只在 Agent 运行时的沙箱里执行，待定。

## 7 自然语言构建：让智能体写插件

系统是一组插件，插件主要由声明式表面组成。于是「构建一个系统」可以这样走：

```mermaid
flowchart LR
  I["人说清要什么"] --> D["智能体生成或修改表面，得到草稿组件"]
  D --> V["校验器与一致性测试"]
  V --> P["预览"]
  P --> H{"人批准？"}
  H -->|"批准"| M["装进租户范围"]
  H -->|"驳回或修改意见"| D
  M --> R["运行"]
  R --> F["反馈"]
  F --> D
```

约束：

- 智能体产出的是草稿组件，和人写的组件走同一个校验器。校验器已有；一致性测试三套里完成了运行时语义一套，组件一致性那一套与发布前的闸门是规划。
- 智能体生成的组件固定为 `private` 等级，不得带进平台共享进程的模块代码；需要代码时只能是沙箱里的函数。这是 Kun 现行规格里的规则；函数沙箱的运行时还没有做。
- 智能体生成的应用，界面只能是数据描述，由平台的渲染器画出来；生成的代码不当页面插件装进外壳（已定，P67）。它与上一条同向，说的是界面这一半。
- 发布要人批准，发布后可以回滚。组件记录它由谁生成、依据的提示词摘要、由谁审核。这是 Kun 已有的决策，还没有实现；已有的是修订之间的回切。
- 表单、列表的 Schema（已有草案）不变；流程的 Schema 与拖拽设计器都还没有实现。拖拽设计器缓做（已定，P32）：先让智能体写，设计器以后作为第二种编写方式。以后无论由设计器还是由智能体来写，产出的是同一种 Schema。

自然语言构建这一块，先做的是生成应用的最小一圈：说一句话，右侧生成一个填报的日报，有表单、列表、权限；预览，发布到本租户，管理端的菜单里出现（已定，P70、P72）。它排在确认卡的最小一圈之后，对应里程碑 M3，还没有实现，见[路线](13-roadmap.md)第 2.1 节。

### 7.1 构建闭环的八步

提议。业务插件与 Agent 组件走同一条路；第 3、7 步由人决定。

| 步 | 做什么 | 谁 |
|---|---|---|
| 1 说要求 | 用自然语言说清要什么 | 人 |
| 2 出方案 | 数据、页面、流程、权限，以及要用到的别的应用 | Agent |
| 3 确认方案 | 看方案，改到满意 | 人 |
| 4 生成草稿 | 产出一个草稿组件，里面都是声明式内容 | Agent |
| 5 校验 | 校验器与一致性测试，和人写的组件同一套 | 平台 |
| 6 预览 | 草稿只对自己可见，在右侧试用 | 人 |
| 7 批准发布 | 按发布范围，由本人或租户管理员批准，见第 5.1 节 | 人 |
| 8 运行与反馈 | 用的情况回到 Agent，接着改 | 人与 Agent |

和上图相比，多出来的是「确认方案」单独成一步：先确认数据与权限的设计，再生成，返工更少。界面示意见[产品形态](03-product.md)第 8 节。

### 7.2 会写代码的人

会写代码的人可以不经对话，直接在本地写组件文件夹：用组件命令行，配合通用的编码智能体。写出来的组件走同一个校验器和同一条发布路，代码仍然只能是沙箱里的函数。命令行现在有什么，见第 5 节。

## 8 各部分由谁承担
