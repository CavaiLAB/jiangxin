# 管理端

先不做，目录先建好（[2026-11-20 产品裁定](../../docs/decisions/2026-11-20-product.md) P39）。什么时候开始做，产品负责人没有单独说。按 2026-11-25 定的先后（P72），生成应用的最小一圈要用到它的外壳，它最晚随那一圈开始做；这是推论。

它以后是什么，2026-11-25 定了几条（[2026-11-25 平台级裁定](../../docs/decisions/2026-11-25-platform.md)）：

- 它是 Web 端的两块之一，文档里也叫管理系统：多用户的网页应用，不需要 DSH 实例。另一块是按需托管的 Agent 工作区。两块放在两个域名上，管理系统的域名过 Kun 的网关（P63、P64）。
- 管理端也要支持 Cordis，管理端的内容要能显示在 DSH 右侧的页签里（P65）。
- 管理端只要浏览器一侧：界面是浏览器里的 Cordis 应用，页面是只有浏览器一半的 Cordis 插件。管理端不设多人共用的 Node 运行环境；带后端一半（Node）的插件只在各人的 DSH 实例里跑（P66）。
- 「待确认」做成页面插件，DSH 的右侧和这里装同一份；在这里它就是待办页（P71）。
- 业务与最终的界面在匠心，Kun 只提供登录这类通用的组件（P60）。放在本仓库还是另开一个仓库没有定，没有新的话之前放这里。

2026-11-26 又定了两条：

- 不管哪一种部署，统一由管理端管理（P83）。
- 平台上的系统，权限都走 Kun 这一套（P86）。照这一条的读法，管理端不自己判权限，只问 Kun。

所以它仍然是单独的一个应用，不是装在某个人的 DSH 实例里的插件。它的页面是 Cordis 插件，同样的内容要能在 DSH 的右侧打开。

以后放这里的页面，提议是管理员用的后台：用户与组织、登录方式、模型接入、工具与插件的策略、审计、实例的开通与回收。外壳怎么搭、页面怎么登记、数据走哪条路，都是提议，到做的时候再定。

登录用 Kun 的身份服务（P57、P64）。权限问 Kun；Kun 给不在它进程里的系统用的远程授权接口还没有，是规划。展开见[产品形态](../../docs/03-product.md)第 4 节与[总体架构](../../docs/04-architecture.md)第 2.1 节。
