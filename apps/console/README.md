# 管理端

先不做，目录先建好（已定）。随生成应用的最小一圈开始做（2026-11-27 定）。

它以后是什么，2026-11-25 定了几条：

- 它是 Web 端的两块之一，文档里也叫管理系统：多用户的网页应用，不需要 DSH 实例。另一块是按需托管的 Agent 工作区。两块放在两个域名上，管理系统的域名过 Kun 的网关。
- 管理端也要支持 Cordis，管理端的内容要能显示在 DSH 右侧的页签里。
- 管理端只要浏览器一侧：界面是浏览器里的 Cordis 应用，页面是只有浏览器一半的 Cordis 插件。管理端不设多人共用的 Node 运行环境；带后端一半（Node）的插件只在各人的 DSH 实例里跑。
- 「待确认」做成页面插件，DSH 的右侧和这里装同一份；在这里它就是待办页。
- 业务与最终的界面在匠心，Kun 只提供登录这类通用的组件。管理端放本仓库（2026-11-27 定）。

2026-11-26 又定了两条：

- 不管哪一种部署，统一由管理端管理。
- 平台上的系统，权限都走 Kun 这一套。管理端因此不自己判权限、只问 Kun，这一句 2026-11-27 也定了。

2026-11-27 又定了几条：

- Kun 里的登录页留在 Kun，原样冻结；租户与成员页、平台控制台、旧的应用外壳不再在 Kun 里做，在这里重做。成员管理页放这里，Kun 只出接口，和角色授权页一样。
- 模型服务在这里管：模型清单、健康状态、开放范围和上下线；推理服务的部署与扩缩留在 GPUStack 自己的界面里，接口留出以后加。改模型的配置分两类：不改流量出口的，点了就生效、留审计；改出口的经评审。
- 托管实例里的插件由这里统一下发，用的人不能自己装。
- 登录以后，管理员进管理端，普通用户直接进工作区，入口页兜底。

所以它仍然是单独的一个应用，不是装在某个人的 DSH 实例里的插件。它的页面是 Cordis 插件，同样的内容要能在 DSH 的右侧打开。

以后放这里的页面：租户与成员、角色授权、模型服务和托管实例里插件的下发已定，见上；其余是提议，有登录方式、工具的策略、审计、实例的开通与回收。外壳怎么搭、页面怎么登记、数据走哪条路，延期，要先有设计。

登录用 Kun 的身份服务（已定）。权限问 Kun；Kun 给不在它进程里的系统用的远程授权接口还没有，是规划。展开见[产品形态](../../docs/03-product.md)第 4 节与[总体架构](../../docs/04-architecture.md)第 2.1 节。
