    #1 名字

    名字指什么
    匠心工业智能体平台整个平台的名字，交付给客户的产品也叫这个名字，用匠心的 logo（已定）。英文写法先用拼音 Jiangxin（已定）；最终的英文名延期，到对外发布前再定。放不下全称的地方用短名「匠心」（已定）
    匠心讲结构时指产品这一部分：Agent 工作区的 Web 端与桌面端、管理端、产品的插件、部署清单。代码在 jiangxin 仓库（已定）；最终的界面放在匠心，也可以放到另一个仓库（已定）；最终的界面、管理端和带业务的 Kun 组件都放 jiangxin（已定）；登录、工作区和管理端等产品页面统一放到匠心重新设计（已定）。包名前缀用 @jx/（已定）
    Kun企业级框架，.NET 10：登录、权限、多租户、数据、事件、审计、模型服务的接口，以插件的形式装配；包名统一为 Kun.*。保持现有基础框架和接口，继续负责认证、会话和权限（已定）；平台上的系统，权限都走它这一套（已定）
    企业级框架、企业级平台都是产品负责人的叫法。「企业级框架」指 Kun。「企业级平台」指运行着的、给人和 Agent 提供登录、权限、模型服务这些的那一侧，以 Kun 的各项能力为主；讲 DSH 怎么对接时，把匠心在它上面做的工作区服务和管理端也算在内，见 DSH 与企业级平台的对接
    DSH一个开源的智能体运行框架，npm 包 @deepseek-ai/dsh，按 MIT 许可使用。平台的 Agent 运行时和界面外壳（已定）；现在钉的版本是 0.2.2-rc.5。文档里称呼它只写 DSH，不写它的全称：全称是注册商标，不进我们的产品名；照引上游原文和许可、商标声明时照写（已定）
    Qian前端框架，包名 @cavailab/qian-*。仓库已归档，只读；已发布的包留着，不再发新版（已定）
    SanYuanAgent一个 Python 的智能体引擎。仓库保留，暂不维护（已定）；平台的 Agent 运行时用 DSH

    现在只剩两个项目：匠心与 Kun（已定）。

    「里程碑」指路线第 2.1 节的 M0 至 M8；「工作线」指第 2.2 节的十二条（已定）。

    「整理者」指整理这些文档、把要定的事列给产品负责人、复核改动的那一方，见协作约定第 2、3 节。

    Kun 仓库里保留的历史文件多数写于这些名字定下之前，用的是当时的叫法；与本表有出入时，以本表为准。

    名字里带 qian 的字面。 组件 id 的前缀 qian.、清单与配置的文件名（.qian-plugin/plugin.json、qian.profile.yml、qian.patch.yml）、qian 命令行、@qian/* 的导入名保留不改（已定）：它们已经落库、上线或冻结，改动的代价大而不带来功能。它们只是字面，不表示产品名，也不表示前端框架。

    #2 部署与模型服务

    术语含义
    两种形态部署按带不带模型推理分成两种（已定）：带模型推理的集群；不带推理、通过 API 接第三方的模型服务（已定）。「形态」这个词在文档里只这样用，这是文档的约定
    多租户版、单租户版两个版本（已定）：一套部署服务多个组织，或者一个组织自己用一套。先交付的两套里，企业版是多租户，单机版是单租户（已定）。提议它们是同一套代码的两种装配
    企业版、单机版说的是部署的规模（已定）：企业版跑在集群上，单机版一台服务器上能跑。先交付这两套：企业版，集群、多租户、带推理；单机版，一台服务器、单租户、不带推理，平台自己的服务跑在单节点的 K3s 上，以桌面为主（已定）。它和上面两条是三件不同的事（已定），见总体架构第 5 节
    部署清单产品部署用的清单，放 jiangxin 的 deploy/，各环境的差异留在部署仓库（已定）。只有一套，企业版与单机版共用（已定）；两套各装哪些组件，延期，要先有设计。目录还没有建
    模型服务由 Kun 提供的一项平台能力（已定）。整个平台只有一个，各种部署、各个端、托管的工作区和应用都走同一套入口（已定）。要设计标准的接口，用来对接后面的模型推理服务，只提供一套（已定）。它管模型目录、路由、额度与计量；模型由平台管理员统一配，向哪些用户开放按租户、按角色两级，不做按人；用的人、租户管理员和应用都不能自带上游（已定）。平台不装 Higress，模型请求由它里面的模型入口转发（已定），见总体架构第 2.2 节。接口还没有实现
    调用面、接入面、管理面模型服务的接口分的三个面，是提议。调用面给 DSH 的实例、应用、Agent 调模型；接入面给模型后端的适配，做成插件；管理面给管理端，管模型目录、凭据的引用、额度与计量
    模型后端模型服务后面真正出模型的一方：自己的推理服务，或者第三方的模型 API
    模型网关转发模型请求并做限流、统计的外部组件，Higress 这一类，后面是模型后端。Kun 原来的设计里它也承载 MCP 流量，所以有的地方写作「模型与 MCP 网关」。平台不装 Higress，也不拿别的模型网关当入口；现场已有的，登记成模型入口的一个上游（已定）
    模型入口平台一侧接调用方的模型请求、转给模型后端的那一处，全平台只有这一个（已定）：Kun 的模型组件里的一个独立的服务，认调用方的凭据，查权限与额度，选上游，转发，记用量。没有实现
    积分额度的单位（已定）。积分按租户开关，关着时用量照记，积分也照算、不拦，打开时数字是连续的；周期可选日、周、月，缺省每周一重置；按 token 乘模型的系数算，输入、输出分开；按模型组计额度，用完就拒绝，不自动换模型（已定）。见总体架构第 2.2 节
    本机模型设备上的小模型（已定）。它算不算「都过模型入口」的例外，延期，要先定设备一侧用什么运行时；此前的提议是它不经过平台的模型服务，用量由设备一侧上报
    CubeSandbox一个开源的沙箱服务，每个沙箱是一台微型虚拟机。托管实例的首选（已定）；在 v0.8.0 上把托管实例试通以后定为默认（带条件：还没有在 v0.8.0 上试，现在还不是默认）；有 Kubernetes 的现场保留 Pod 作备选（已定）

    #3 平台术语

    术语含义
    自然语言构建人用自然语言说清要什么，智能体生成或修改声明式表面，经校验和人工批准后上线
    组件一个文件夹加一份清单、若干声明式表面和可选的代码；分发与安装的单位
    插件组件的运行时形式：挂进共享上下文，贡献服务、监听器和可撤销的副作用。产品这一侧另有装在 DSH 里的插件，见第 4 节的「页面插件」与一切皆插件第 2.2 节
    表面组件向外暴露的一类声明式内容：技能、子 Agent、命令、钩子、MCP 服务器、工具、界面、元数据、业务元数据、配置补丁。另新增知识库（已定；格式等细则，产品负责人 2026-11-24 说先移除）
    清单组件根目录下描述它的那份 JSON 文件
    能力的三个角色契约（接口与词汇）、提供方（实现）、消费方。消费方只依赖契约包
    契约包一项能力里只放接口、词汇类型、事件定义与错误码的那个包，没有实现
    跨服务契约服务之间共用的数据约定：令牌字段、事件信封、结构化错误、能力条目。冻结之后只做加法。与「契约包」是两回事
    组件运行时装载组件、把它们挂进共享上下文的那个很小的核心，在 Kun 里
    内核档、平台档Kun 的两档：内核档是不带产品语义、可以单独安装的通用机制；平台档带产品语义，以组件的形式装配
    范围一项注册的归属：全局，或者恰好一个租户、应用或 Agent 会话。另加 Agent 一级的范围（已定），用来给某个 Agent 长期挂组件；它还没有进规格
    profile一份具名的插件组装，也是一个可部署单元
    组合包带着一组配置条目的组件，被 profile 引用时整层叠加
    补丁对插件树里某个条目的替换、禁用或插入
    插件树由 profile、组合包和各层补丁叠出来的全部条目
    目录市场git 仓库里的一份清单文件，列出可以安装的组件及其来源
    信任等级组件的来源等级，决定它能带什么样的代码、在哪里运行
    主体行事的一方：user（人）、service（服务）、agent（智能体）
    委托链令牌里写明「谁代表谁行事」的一串记录
    能力目录平台全部能力的登记：输入输出 Schema、副作用等级、所需权限、是否对 Agent 暴露、是否要人确认
    强制执行点每次能力调用必经的权限判定位置
    等人输入的任务平台上的一条任务，状态是等人输入，带着允许的动作。等人点头的事都记成这样的任务：平台来的审批，Agent 要办的、要人确认的事（已定）。还没有实现
    协同消息Agent 与 Agent 之间往来的消息，经平台的信箱转交
    人审人对协同消息、Agent 要发出去的内容、智能体生成的变更或高风险动作做批准、修改或驳回
    出站确认Agent 往外发之前，由发件方的主人确认。「发出去」包括发给别的 Agent、发给别人、写外部系统（已定）
    入站审核别人的 Agent 发来的消息送达我的 Agent 之前，由我审核。起步出站、入站两道都必审（已定）
    入网一台设备上的 Agent，或者连接器装在内网的执行部分，第一次接入平台：在本机生成密钥，由人在平台上批准，之后用密钥换短期令牌。连接器这一头按提议推进，见历史系统接入；设备这一头延期，要先定设备一侧用什么运行时
    三级工业现场的智能体分工站、产线、工厂三级（已定），各自的智能体叫具身智能体、协同智能体、超级智能体，见工业智能制造第 3 节

    #4 产品

    展开见产品形态。

    术语含义
    Agent 工作区人用平台的入口（已定）：和 Agent 对话、办事的地方，外壳是 DSH 自己的客户端（已定）。Web 端的那一块后面是托管的 DSH 实例，桌面端的跑在本人的电脑上
    管理端也叫管理系统：Web 端里不需要 DSH 实例的那一块，多人用的网页应用（已定），代码的位置是 apps/console/。界面是浏览器里的 Cordis 应用，页面是只有浏览器一半的 Cordis 插件，内容要能显示在 DSH 右侧的页签里（已定）。不管哪一种部署，统一由管理端管理（已定）。先不做，目录先建好；随生成应用的最小一圈开始做（已定）。里面放哪些页面：租户与成员、角色授权、模型服务已定，托管实例里的插件也由它统一下发（已定）；其余随外壳一起定，外壳延期，要先有设计
    认证页登录、选择租户（界面上叫「选择工作空间」）、强制改密、找回密码这一族页面。界面统一放到匠心重新设计，旧布局和样式可以淘汰；认证与会话由 Kun 负责（已定）。现在用的是 Kun 里现有的那一套；匠心的还没有实现，放在哪见包与应用的去向
    设计规范匠心根据工业填报、管理和 Agent 工作区的实际场景制定的界面规范，Ant Design 仅供参考（已定）。现在只有底稿，见设计规范
    工作区服务匠心自己的一个服务：接工作区的域名，用 Kun 的登录组件认人，把登录的人送进他自己的 DSH 实例（已定）。所有人用同一个工作区域名，由它按人路由；用 C# 写，基于 Kun 的包（已定）。还没有实现
    托管实例跑在服务器上、给 Web 端用的 DSH 实例，每个正在用 Agent 的人一个，按需启动、空闲回收、有上限（已定）。跑在 CubeSandbox 里是首选，见第 2 节；空闲 30 分钟暂停，上限做成配置；用的人不能自己装插件，由管理端统一下发（已定）。桌面端里的 DSH 跑在各人自己的电脑上，不算托管实例
    页面插件只有浏览器一半的 Cordis 插件。管理端的页面是这一种（已定）；同一份页面 DSH 的右侧和管理端都能装，是提议，两边的适配延期，「待确认」这一页已定这样做
    确认卡Agent 要改数据或往外发内容时，在对话里给人确认的那张卡片。已定的几条：等人点头的事记在平台，卡片的点击由浏览器直接交给平台，审批时模型默认不参与；标了要人确认的能力由平台自己停下来等人点，等人点头的任务上的动作缺省只能人做（已定）。卡片的样子与位置也已定：输入框上方显示最新的一条，右侧的「待确认」列出全部，对话里提到某条任务时带出同一张卡；内容按任务去平台取，不用模型写的文字
    待确认列出等我点头的任务的那一页。做成页面插件，DSH 的右侧和管理端装同一份；在管理端里它就是待办页（已定）
    替身里程碑 M1 的智能体主体做好以前，代 Agent 向平台提出请求的一方：实例里的工具调匠心的工作区服务，由它用自己的服务身份调平台，写明代谁提出。只用于确认卡的最小一圈的演示，是过渡，M1 做好以后撤掉（已定）。用它演示出来的不算里程碑 M2 完成（已定）。还没有实现；做法与接口的形状是提议
    数据描述的应用智能体生成的应用：数据模型、表单、列表、流程、菜单、角色这些声明式的内容。界面由平台的渲染器画出来，生成的代码不当页面插件装（已定）
    业务插件两种扩展之一（已定）：在企业级平台上开发的插件，装上之后是能打开的应用，也是 Agent 能调用的能力
    Agent 组件两种扩展之一（已定）：加在 Agent 上的组件，例如技能、子 Agent、知识库
    知识库组件里新增的一种内容：一批资料连同它的整理方式（已定）。格式、由谁存放、整理与检索，产品负责人 2026-11-24 说先移除
    应用互通发布的应用之间可以互相通讯（已定）。缺省：目录里看得到，调用与订阅按声明、经批准放行。见应用互通
    历史系统企业里已有的、不在平台上的业务系统。经连接器接入，见历史系统接入
    连接器把一套历史系统翻译成平台的能力、事件与数据的组件。历史系统在内网的，它的执行部分装在内网，只向外连（已定）

    #5 产品的代码与 DSH

    出自产品代码旁边的说明。代码在仓库根下，各目录的入口见平台主页的「现状」。

    术语含义
    Web 端、桌面端客户可能用到的两个端（已定）。桌面端指装在电脑上的桌面应用，代码在 apps/desktop/，代码与旧文档里也叫客户端。Web 端分成管理端与按需托管的 Agent 工作区两块，放在两个域名上（已定）。「Web 端」有宽窄两种用法：说「两个端」时它指浏览器这一整侧，含管理端；说「Agent 工作区的 Web 端」时只指工作区那一块
    日历版本号匠心工业智能体平台的产品版本号：vYYYY.M.D 正式版，vYYYY.M.D-N 补丁版，vYYYY.M.D-beta.N 测试版，月和日不补零，构建时注入（已定）。没注入时显示「本地开发」。DSH 自己的版本号另算
    发行目录distribution/：钉死版本的 DSH、要装的插件包、按文件名顺序叠加的配置补丁，加上启动器和启动前检查。Web 端和桌面端都从它启动 DSH
    配置补丁叠在 DSH 配置上的一份 YAML 文件，按行 id 关掉、整行改写或插入一行。发行目录的配置补丁放在 distribution/patches/，启动时用 --patch 叠在最上层，界面上改不动。和第 3 节的「补丁」（插件树里条目的替换）不是一回事
    源码补丁对 DSH 源码的改动，一处一个文件，放在 patches/。原则上不改 DSH 的源码，现在只有样例
    品牌包@jx/brand-theme：把 DSH 界面里的名称、标志、主题色和文案换成匠心的。不改 DSH 的源码
    界面包@jx/ui-kit：产品自己的界面组件和插件的构建脚本。基础组件用 shadcn 这一套，样式用 Tailwind（已定）；只补 DSH 没有的、生成进这个包（已定）
    启动前检查distribution/bin/jx-preflight.mjs：查 DSH 的版本、插件包、补丁对不对，查不过就不启动。DSH 加载不了某个插件时只停用它、照常启动，品牌包没加载就会带着 DSH 自己的品牌起来，所以要查
    薄壳桌面端的一种做法：自己写的 Electron 壳里跑已发布的 DSH，窗口里装它的 Web 界面。另一种是从源码构建 DSH 上游的桌面壳。桌面端走薄壳（已定）
    一个用户一个实例已定：每人一个 DSH 实例，多个人靠实例之间的隔离。桌面端的跑在各人自己的电脑上；Web 端每个正在用 Agent 的人一个托管在服务器上的实例，按需启动、空闲回收、有上限。把登录的人送进他自己的实例，由匠心的工作区服务做。实例怎么隔离、凭据怎么保管，延期，要先有设计
