    #一切皆插件

    状态：规划稿，2026-11-26 按收拢后的方向改过，2026-11-27 跟上产品负责人对待定事项的答复。标法见平台做什么与设计理念开头；本文的「已有」指在 Kun 的仓库里已经实现，说到本仓库时另外写明。

    组件模型在 Kun 里已经成文并实现了大部分，本文是它的概述，细节以 Kun 的组件模型规格为准。Agent 一级的范围与知识库（已定）还没有进那份规格；回写之前规格仍是原来的写法；有出入时，以本文标「已定」的为准。

    名字里带 qian 的地方（已定）：组件 id 前缀、清单目录这些运行期字面保留不改，qian 命令行与 @qian/* 导入名暂不改；它们都不表示产品名。

    #1 原则

    一切皆插件是统一的原则（已定）。平台没有只能打补丁的特权内核。运行时只有一个很小的核心：上下文、服务注册、类型化事件、可撤销的副作用、装载器。租户、身份、权限、文件、配置、网关、事件、审计，以及每一个业务功能，都是插件。

    • 扩展平台的方式是把一个插件挂在别的插件旁边，不是修改内核。
    • 插件声明自己依赖哪些服务，依赖就绪才启动，装载顺序由依赖关系决定。
    • 插件做的每一项注册都是副作用，卸载时按相反的顺序撤销。
    • 任何一项能力都可以从配置里替换、按范围收窄或遮蔽。

    这是智能体能发现、调用乃至生成平台能力的前提：只要存在一块只有内部人能改的内核，第三方和智能体就只能在它允许的位置扩展。

    部署的两种形态、多租户版与单租户版，也尽量用插件的形式实现（已定）：把它们之间的差别做成 Kun 的组件（已定）。见总体架构第 5 节。

    #2 组件是什么

    组件 = 一个文件夹 + 一份清单 + 若干声明式表面 + 可选的代码。它是分发与安装的单位。没有代码、只有表面的组件是常态。

    <组件>/
  .qian-plugin/plugin.json      清单，唯一必需的文件
  skills/<name>/SKILL.md        技能
  agents/<name>.md              子 Agent
  commands/<name>.md            给人用的命令
  hooks/hooks.json              钩子
  .mcp.json                     MCP 服务器声明
  tools/<name>.json             面向模型的工具描述
  ui/manifest.json              界面：远程模块、页面、控件
  metadata/                     权限点、角色、事件、消息类型
  forms/ lists/ flows/ pages/   业务元数据：表单、列表、流程、页面
  schemas/                      JSON Schema
  config/qian.patch.yml         配置补丁
  src/                          可选：.NET 或 TypeScript 代码

    谈文件时叫「组件」，谈运行时叫「插件」：组件装进来、按一个条目挂进共享上下文之后，就是插件。

    #4 运行时的几个概念

    • 上下文与服务键。 插件经上下文拿到别的插件提供的服务，例如文件、身份、权限。服务键由定义它的包拥有。
    • 能力的三个角色。 一项能力拆成契约（接口与词汇，发成契约包）、提供方（一个或多个实现）、消费方。扩展插件只依赖契约包，不依赖具体实现。把文件存储从本地盘换成对象存储，消费方不用改。
    • 事件就是扩展点。 事件有五种分发方式：观察、环绕、并行、按序、取首个返回值。权限判定、租户校验这类强制执行点就是环绕式的监听器。
    • 范围。 任何一项注册要么是全局的，要么只属于一个范围。范围现有三种：租户、应用、Agent 会话。范围内的注册遮蔽同名的全局项。租户启用一个插件，就是在自己的范围里挂上它的条目；租户定制，就是在自己的范围里做一个遮蔽注册。另加一种 Agent 一级的范围（已定），用来给「我的某个 Agent」长期挂组件；它还没有进规格，也没有实现，与另外三种范围怎么叠见第 9 节。
    • profile、组合包与补丁。 运行中的平台是一棵插件树，由几层按顺序叠出来：profile 列出的组合包、profile 自己的补丁、本机补丁、命令行补丁，运行中再叠上存在数据库里的租户补丁。一条命令可以把整棵树打印出来，打印出的任何条目都能被补丁替换。

    #5 安装与目录

    • 一条命令安装。 安装一个组件，就是把它的表面复制进项目、把代码部分加成包依赖、把配置条目写进当前 profile 的补丁。安装、升级、移除、列出与打印配置树的命令已有；健康检查、成套的脚手架模板、本机运行、打包、签名与发布的命令是规划。
    • 目录市场是一份清单文件。 市场是 git 仓库里的一个 JSON 文件，每个条目只写名字、来源（本地路径、网址、git 子目录）、安装与认证策略、分类。清单格式与校验已有；官方市场仓库、由它生成目录网站、社区发现是规划。
    • 多个市场并存。 官方市场、租户私有市场、社区市场可以同时配置。
    • 应用也是组件。 一个业务应用 = 一个组合包加一个市场条目。以后的商业市场（授权、计费、审核）叠在同一格式上，不另起格式。

    #6 用现成的生态组件

    社区里已经有大量现成的 Agent 组件：技能、子 Agent、命令、钩子、MCP 服务器声明、设置片段，按类型放在文件夹里，一条命令安装，并且有开源的组件目录在汇集它们。平台的表面采用同样的文件格式，所以对接是文件对文件：

    社区组件平台里的表面
    技能：带 front matter 的 SKILL.md，可带参考资料与脚本skills/<name>/SKILL.md
    子 Agent：front matter 加系统提示的 Markdownagents/<name>.md
    命令：Markdowncommands/<name>.md
    钩子：JSONhooks/hooks.json
    MCP 服务器声明：JSON.mcp.json
    设置片段配置补丁
    整包插件与市场清单组件文件夹与目录市场条目

    目标（已定）：开源组件目录里的组件能装进平台直接用。

    企业不能把社区组件原样装进生产，所以装进来要过几道关：

    1. 信任等级。 每个组件有信任等级。社区来源的组件现阶段只接受不带代码的，它的代码永远不进平台的共享进程。
    2. 装之前看得见。 安装前展示它包含哪些表面、要哪些权限与密钥、会访问哪些外部地址，由有权限的人确认。应用之间的调用与订阅也要列在这张单子上（已定；细则按提议推进），见应用互通第 4 节。
    3. 按租户启用。 组件装进来不等于人人可用，租户在自己的范围里启用，谁启用的留审计。
    4. 带脚本的部分不放行。 技能目录里的脚本、命令里的内联 shell 是代码。现行规则：社区来源的组件里出现内联 shell，校验直接不过；这类脚本只在命令行、开发者本机，或平台自有组件的受限执行器里运行。社区技能里的脚本，只在 Agent 运行时的沙箱里执行（已定），见下。

    要做的事（规划）：

    • 一个导入器，把社区目录的条目转成组件文件夹：补清单、定信任等级、跑校验器、列出它要的权限，并核对组件的许可与署名要求。
    • 工具名的映射。社区组件里写的工具名与平台里的工具名对不上的，导入时要有对应办法。
    • 统一技能的 front matter。社区规范与 Kun 现有规格的字段有出入；Agent 运行时用 DSH 以后，还要对上 DSH 认的写法。怎么对齐，延期，要先做对照。
    • 让社区技能里的脚本只在 Agent 运行时的沙箱里执行（已定）。

    #7 自然语言构建：让智能体写插件

    系统是一组插件，插件主要由声明式表面组成。于是「构建一个系统」可以这样走：

    约束：

    • 智能体产出的是草稿组件，和人写的组件走同一个校验器。校验器已有；一致性测试三套里完成了运行时语义一套，组件一致性那一套与发布前的闸门是规划。
    • 智能体生成的组件固定为 private 等级，不得带进平台共享进程的模块代码；需要代码时只能是沙箱里的函数。这是 Kun 现行规格里的规则；函数沙箱的运行时还没有做。
    • 智能体生成的应用，界面只能是数据描述，由平台的渲染器画出来；生成的代码不当页面插件装进外壳（已定）。它与上一条同向，说的是界面这一半。
    • 发布要人批准，发布后可以回滚。组件记录它由谁生成、依据的提示词摘要、由谁审核。这是 Kun 已有的决策，还没有实现；已有的是修订之间的回切。
    • 表单、列表的 Schema（已有草案）不变；流程的 Schema 与拖拽设计器都还没有实现。拖拽设计器缓做（已定）：先让智能体写，设计器以后作为第二种编写方式。以后无论由设计器还是由智能体来写，产出的是同一种 Schema。

    自然语言构建这一块，先做的是生成应用的最小一圈：说一句话，右侧生成一个填报的日报，有表单、列表、权限；预览，发布到本租户，管理端的菜单里出现（已定）。它排在确认卡的最小一圈之后，对应里程碑 M3，还没有实现，见路线第 2.1 节。

    #7.1 构建闭环的八步

    提议，其中第 3 步「确认方案」单独成一步是已定的。业务插件与 Agent 组件走同一条路；第 3、7 步由人决定。

    步做什么谁
    1 说要求用自然语言说清要什么人
    2 出方案数据、页面、流程、权限，以及要用到的别的应用Agent
    3 确认方案看方案，改到满意人
    4 生成草稿产出一个草稿组件，里面都是声明式内容Agent
    5 校验校验器与一致性测试，和人写的组件同一套平台
    6 预览草稿只对自己可见，在右侧试用人
    7 批准发布按发布范围，由本人、租户管理员、本企业的审核人或平台审核批准，见第 5.1 节人
    8 运行与反馈用的情况回到 Agent，接着改人与 Agent

    和上图相比，多出来的是「确认方案」单独成一步（已定）：先确认数据与权限的设计，再生成，返工更少。界面示意见产品形态第 8 节。

    #7.2 会写代码的人

    会写代码的人可以不经对话，直接在本地写组件文件夹：用组件命令行，配合通用的编码智能体。写出来的组件走同一个校验器和同一条发布路，代码仍然只能是沙箱里的函数。命令行现在有什么，见第 5 节。
