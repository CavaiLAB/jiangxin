    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认

    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #SanYuanAgent 框架架构

    状态：规划稿（2026-11-17）。「已有」指已经实现：核心的部分在本仓库的 packages/core（2026-11-17 从私有产品里的 Python Agent 引擎迁入），服务层的部分还在原仓库。第 11、12、13 节是规划。

    2026-11-17 已定：SanYuanAgent 是独立运行的 SDK，每个端都要用到它，包括机器人这类边缘设备，装上就能用；模型服务由 Kun 提供，设备本地可能还有小模型。展开见独立运行的 SDK、接入平台：与 Kun 的交互、与模型服务的交互，本文只留摘要。

    #1 边界

    SanYuanAgent 负责智能体怎么想、怎么做：理解意图、规划、调用工具、记忆、在沙箱里执行、选择模型、编排多个 Agent。

    它是独立运行的 SDK（已定），目标是不接平台时自己能完整运行。下面三项说的是接入平台之后的分工。

    它不负责：

    • 用户、租户、角色、权限这些业务主数据，那在 Kun。
    • 界面，那在 Qian。
    • Agent 与 Agent 之间往来的转交与审核，提议由 Kun 的协同服务承担；引擎只负责收发：发出去的内容先经主人确认，收到的内容只执行人批准过的（起步出站、入站两道都必审，已定）。

    #2 分层

    层内容依赖
    核心推理循环、工具、技能、记忆、沙箱接口、模型供应方、编排、事件流定义不依赖服务层，可以单独安装
    服务层对外的服务接口：对话与运行、流式输出、工作流、模型治理、技能同步、用量记账、工作区依赖核心
    媒体适配层多模态能力的统一封装独立的包

    两条由检查强制的规矩：服务层可以引用核心，核心不得引用服务层；核心必须能在一个干净的环境里单独装上，命令行起得来。检查不包括跑通一个 Agent。

    核心内部再分「最小安装」与「按需附加」是提议，见独立运行的 SDK第 6 节。

    #3 推理循环

    循环建在状态图上：

    • 状态里有消息、工具结果、迭代次数与上限、感知记忆与工作记忆、累计用量。
    • 工具调用失败不会让运行崩掉：失败以结果的形式回到模型，由它决定下一步；连续失败有熔断。
    • 一个 Agent 用一份声明来描述：提示、模型、工具集、策略。

    #4 工具与策略

    • 工具注册表。 所有工具登记在注册表里。一个工具的声明包括名字、调用入口、输入 Schema，以及一组不参与执行的元数据：类别、能力、副作用、需要的密钥、是否产出产物、策略提示。元数据给策略、界面和审计用。
    • 提供方接口。 一组工具可以作为一个提供方整体登记。
    • 内置工具。 网页检索与抓取、文件、终端、浏览器、多模态、技能执行。
    • MCP。 引擎里有 MCP 客户端，以及把外部服务器的工具接进注册表的桥。现在只有本地进程这一种传输，客户端也还没有接进运行路径。远程传输是规划，接 Kun 的能力目录要用到它。

    引擎核心里有三类安全组件：

    组件做什么
    工具策略按 Agent 配置的一组规则，结果是允许、拒绝或需确认
    高风险动作识别识别破坏性命令这类危险操作，要求确认
    提示注入检测检测进入上下文的内容

    让人在界面上确认、运行暂停后再恢复的完整流程是规划。这些组件是对 Kun 权限判定的补充，不代替它。

    #5 技能

    • 技能是带 front matter 的 SKILL.md，写明名称、版本、描述、用到的工具和触发条件。
    • 引擎自带的技能随发行版一起发布，视为可信。
    • 自定义技能必须带签名。没有签名或者校验不过的技能处于待定状态，不会被加载。
    • 加载是按需的：模型先看到技能目录，用到某个技能时才载入它的正文。
    • 服务层按租户同步已经批准的自定义技能。

    #6 记忆

    记忆分四层：

    层存什么
    感知最近的原始事件，只留最近一段
    工作这次任务里「规划、行动、观察」的历史；超出上限时，较早的步骤压缩成摘要
    情节每次运行一条：用户的输入与最终回答
    长期沉淀下来的语义记忆，按范围隔离，用向量检索召回

    每条长期记忆有两个互相独立的属性：

    • 访问范围：个人、团队、租户。
    • 上下文层级：个人、项目、会话。

    召回只在允许的范围里做：个人的，加上当前项目的，加上当前会话的。记忆还可以投影成一份 Markdown 文件，方便人查看。

    这一节是概述。对着代码写的现状，以及提议怎么改，见记忆的模型。

    #7 沙箱

    Agent 产生的代码、终端命令和文件操作在沙箱里执行。核心只定义沙箱提供方的接口，后端可以换：

    后端用途
    本地实现开发时用
    桌面本地沙箱在用户自己的机器上受限地执行
    云上沙箱在集群里隔离执行，经服务层接入

    #8 模型

    • 核心有一个模型供应方的注册表，可以配置按顺序回退的备选模型。
    • 服务层做模型治理：先把请求按意图归到一个档位，再由档位选模型，租户可以覆盖默认的选择。
    • 对上游模型的调用经过模型网关。
    • 每次调用的用量和成本都记账。

    已定：模型服务由 Kun 提供；机器人这类设备本地可能还有小模型。平台的模型、本机的模型怎么一起用，怎么路由、计量，断网时怎么办，是提议，见与模型服务的交互。

    #9 多 Agent

    已有的是「编排者到工作者」这一种形态：

    • 子 Agent。 一个子 Agent 在全新的、隔离的状态里运行，只把结论和用量交回去。
    • 把子 Agent 当工具。 一个工作者可以包装成工具，由编排者调用。
    • 工作流。 一件事分成几个阶段，每个阶段把工作项并发分给多个子 Agent，最后可以汇总。进度以事件的形式输出。
    • 路由。 一个请求走单个 Agent 还是走工作流，由服务端判断。

    工作者之间不通信。Agent 与 Agent 之间对等的往来现在没有，见第 12 节。

    #10 运行、线程与事件流

    • 运行。 一次运行有排队、运行中、成功、失败、取消几个状态。
    • 线程与消息。 对话按线程组织，线程属于某个租户和账号。
    • 事件流。 运行过程以服务端推送的事件流输出，事件类型包括：步骤、工具调用、工具结果、执行、产物、消息增量、工具进度、计划、最终回答。Qian 的过程展示要渲染的就是这条事件流；前端契约里的事件类型与这里的事件名现在是两套，统一成一份契约是规划。
    • 后台运行。 工作流可以脱离连接在后台运行，客户端断开之后可以重新连上，从指定位置接着收事件。

    #11 对接平台

    规划。这里是摘要，展开见接入平台：与 Kun 的交互。

    事项做法
    前提（提议）不接平台也能运行。接入之后平台管的事以平台为准，本机配置只能收紧
    连接（提议）设备只向外连，只认平台的一个入口地址。设备上有本机模型时，断网后本机的活照干，联网后补传
    入网（提议）设备上的引擎第一次接入要入网：本机生成密钥，由主人本人在平台上批准，之后用设备密钥换短期令牌
    身份引擎以 agent 主体运行，令牌由 Kun 签发，带委托链，写明代表哪个人
    调用平台能力从 Kun 的能力目录按范围取可用的能力，作为工具登记进注册表；每次调用都经过 Kun 的权限判定
    取 Agent 表面技能、子 Agent 定义、钩子、MCP 服务器声明从平台的插件树按范围取，取代引擎自己的同步机制
    权限以 Kun 的强制执行点为准；引擎里的工具策略是补充，不能代替它
    审计与计量引擎产生的审计事件与用量交给 Kun 统一留存
    人的确认需确认的工具调用、智能体生成的变更、往外发的内容（发给别人、写外部系统），经 Kun 的审核流程交给人，批准后运行恢复
    模型模型服务由 Kun 提供（已定）。提议：平台的模型经模型与 MCP 网关调用；设备上的本机模型不经过模型网关，用量由引擎上报
    用社区组件社区的技能、子 Agent、MCP 声明经平台导入并校验之后，引擎按同样的方式加载

    #12 个人 Agent 与协同

    规划，其中协同与人审排在平台路线的里程碑 M7，见平台总览的 Agent 协同。已定的是：发给 Agent 的内容、Agent 发出去的内容都要由人审核，起步出站、入站两道都必审；「发出去」包括发给别的 Agent、发给别人、写外部系统三类。引擎这一侧要做的：

    • 一个 Agent 的声明里加上它的主人与授权范围。
    • 提供收发协同消息的工具。发出的消息交给 Kun 的协同服务，经主人确认之后才发出；收到的消息只有经人批准的才进入上下文，并且带着限定范围的授权。
    • 发给别人、写外部系统之前，同样先让人确认。提议在对话里出一张确认卡，人点了才执行。
    • 别的 Agent 发来的内容在引擎里始终按数据对待，不当指令执行。
    • 审核的结果（确认、批准、修改、驳回、撤回及理由）写进记忆，作为以后的依据。
    • 一个人名下多个 Agent 之间的分派，沿用已有的编排。

    #13 三种形态：工站、产线、工厂

    规划。已定的是一句话：SanYuanAgent 是工站、产线、工厂三级智能体的大脑，要能提供给这三级使用。三种形态的来历见平台总览的三种形态。下表是提议。

    层级形态引擎在这一级做什么对引擎的要求
    工站具身智能体作业智能体：分解工单、编排技能，根据作业结果调整计划；选定的技能交给具身大脑与工控小脑去执行贴近设备运行，资源受限，可能断网；实时控制不经过引擎；与感知、控制一侧经工具或 MCP 对接
    产线协同智能体任务智能体：以统一入口调用排程、质检等专业应用专业应用作为工具或平台能力接入；与孪生、调度对接
    工厂超级智能体多智能体协同：把任务分派给产线、机器人等智能体，协调资源冲突，按执行结果调整方案集群部署；跨级的分派走平台的协同机制，受人审规则约束

    已有的基础：核心可以脱离服务层单独安装，往工站一级放时只带核心；编排者到工作者的分派已有，可以用在一级之内；模型供应方可换。

    还没有的：面向现场一侧的打包与安装形态；断网时的运行与恢复联网后的同步；三级之间的通信；与感知、控制系统的接口约定。其中三项现在有了提议：打包与安装见独立运行的 SDK第 6 节，断网见接入平台：与 Kun 的交互第 9 节，与感知、控制一侧的接口见独立运行的 SDK第 7 节。三级之间怎么通信仍然待定。

    三级各怎么打包与部署打包与安装的提议见独立运行的 SDK；工站一侧用什么模型、断网时怎么办的提议见与模型服务的交互与接入平台：与 Kun 的交互。三级之间怎么通信、边缘节点上放什么，没有提议
