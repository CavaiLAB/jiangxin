    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程

    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳

    #从 yue 迁移到 qian

    给框架的使用方。前端框架在 F2（S1-YUE-022）里由 yue 更名为 qian：只改名字，组件的接口与行为不变，版本号也没有动。F3 以新名字首发：10 个包统一 0.2.0，公开发布在 GitHub Packages（安装见第 2 节）。10 个包已于 2026-11-17 发布。0.2.0 的数据组件包与业务选择器包一渲染就报错，2026-11-18 以 0.2.1 返修，10 个包一起升，请直接用 0.2.1。更名的规则与经过见迁移与更名第 5 节与第 10 节。

    #1 谁要改

    你在做的事要改的
    安装、导入这些包包名、.npmrc 的作用域、导入路径（第 2 节）
    覆盖样式变量、写测试选择器--qian-*、data-qian-density、测试标识的默认前缀（第 3 节）
    用到导出的类型与选项QianProps、ShellHost 的 qianVersion 等（第 4 节）
    依赖浏览器里存下的主题与偏好存储键换了，旧值不迁移（第 5 节）
    写插件的界面清单、做外壳宿主engines.qian，要和后端一起换（第 6 节）

    2026-11-21，GitHub Packages 已删除三个旧层包。升级时把直接依赖或 npm 别名指向下表的 0.2.1，重新生成锁文件，再用空缓存执行安装。

    旧包与版本包源现状归档替代版本
    @idadawn/yue-sdk@0.1.0已删除@cavailab/qian-sdk@0.2.1
    @idadawn/yue-contracts@0.1.0已删除@cavailab/qian-contracts@0.2.1
    @idadawn/yue-tokens@0.1.0已删除@cavailab/qian-tokens@0.2.1

    旧插件开发包依赖旧 SDK，旧 SDK 又依赖契约包和设计令牌包。即使锁文件钉住了版本和摘要，从空缓存运行 npm ci 仍会因旧包下载地址返回 404 而失败。已经构建并部署的静态页面加载现有资源，无须访问 npm 包源。

    #从 GitHub Packages 安装

    包是公开的，但 GitHub Packages 的 npm 包源装公开包也要带令牌（GitHub 文档：Authenticating to GitHub Packages，那里写明发布、安装、删除 private、internal 与 public 的包都需要访问令牌）。不带令牌装不上是预期的，不是没发布。

    在哪里装用什么令牌
    本机有 read:packages 权限的个人访问令牌（classic）。同一页写明这个包源只支持 classic 令牌
    GitHub Actions工作流自带的 GITHUB_TOKEN，工作流要声明 permissions: packages: read。公开的包任何仓库的工作流都能下载（GitHub 文档），不用另配访问权限

    项目根目录的 .npmrc（和 package.json 放在一起）只写作用域那一行，可以提交：

    @cavailab:registry=https://npm.pkg.github.com

    认证那一行放进用户级配置：~/.npmrc，或者环境变量 NPM_CONFIG_USERCONFIG 指向的文件。它只引用环境变量，不写令牌值：

    //npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}

    令牌放进环境变量 NODE_AUTH_TOKEN 再安装，例如 pnpm add @cavailab/qian-core 或 npm install @cavailab/qian-core。作用域要小写（同一页「Publishing a package」：包名与作用域只能用小写字母）。

    认证行不要写进项目的 .npmrc。10.34.2 起的 pnpm 10、11.5.3 起的 pnpm 11 以及 pnpm 12（安全公告 GHSA-3qhv-2rgh-x77r）不展开项目 .npmrc 认证设置里的环境变量：它忽略这一行、给出警告，装包得到 401；~/.npmrc 与 NPM_CONFIG_USERCONFIG 指向的文件里的照常展开（pnpm 文档「Environment variables in auth settings」）。npm 仍会展开项目 .npmrc 里的变量，所以同一份配置用 npm 能装、换成 pnpm 就装不上。2026-11-18 用 0.2.0 核对过：认证行写在项目 .npmrc 里，pnpm 12.9.1 与 11.5.3 都是 401，npm 11.20.0 与修复之前的 pnpm 11.2.2 能装；放进 ~/.npmrc 或 NPM_CONFIG_USERCONFIG 指向的文件，pnpm 12.9.1 能装。

    GitHub Actions 里用 actions/setup-node 并填 registry-url: https://npm.pkg.github.com：它把同样的认证行写进 RUNNER_TEMP 下的一份 .npmrc，再把 NPM_CONFIG_USERCONFIG 指向它，pnpm 与 npm 都会读。装包的步骤把 NODE_AUTH_TOKEN 设为 ${{ secrets.GITHUB_TOKEN }}。本仓库的发布工作流与消费者验证也是把认证行写进 NPM_CONFIG_USERCONFIG 指向的文件再装的。

    0.2.0 各包附带的说明还写着把认证行放进项目的 .npmrc，以这里为准；0.2.1 起包里的说明已经更正。

    已定：键换名，不迁移旧值（合并蓝图 D23.18）。升级之后用户第一次打开，主题与外壳偏好回到默认值（外壳偏好回到部署缺省），重新设置一次就按新键保存；旧键留在浏览器里，不再读取。给主题控制器显式传了 storageKey 的，不受影响。

    #6 插件清单的版本键

    插件界面清单里声明前端版本要求的键由 engines.yue 换成 engines.qian。取值照旧是 8 个层包的版本范围，宿主拿它和 qianVersion 比对。新名字的首个版本是 0.2.0，而 0.x 的 ^0.1.0 不包含 0.2.0：换到新包的宿主报的是 0.2.0，清单还写 ^0.1.0 的远程会被拒载，要放宽到 ^0.2.0（或覆盖两者的范围）后重发；微前端共享依赖的 requiredVersion 同理。

    这个键要清单、宿主与后端一起换：

    • 新的插件开发包登记远程时只认 engines.qian。清单 Schema 要求有这个键、不许别的键，只写 engines.yue 的旧清单在 registerRemote 时就以 INPUT_INVALID 被拒。
    • 界面清单 Schema 的唯一来源在后端仓库。后端的 Schema、一致性用例与命令行在 F4 之前只认 engines.yue。
    • 所以 F4 之前，已部署的远程照旧写 engines.yue、配旧名字的插件开发包；F4 在后端仓库把 Schema、一致性用例、各界面清单与外壳一次换完。本仓库的 Schema 副本在 F2 先换成新键，登记为「领先于来源」，见后端契约的副本。

    #7 不变的

    • 下面这些运行期字面不表示前端框架，照旧：组件 id 前缀 qian.、.qian-plugin/、x-qian-*、https://qian.dev/…（包括组件清单 Schema 的 $id）、qian 命令行、@qian/* 导入名。
    • 组件的接口与行为、data-slot 的取值。版本号在 F2 没有动，F3 首发时到 0.2.0（第 2 节）。
    • 带旧名字的任务编号 S1-YUE-* 与提交历史。

    #8 改完怎么查

    在自己的代码里不分大小写搜一遍 yue：样式、测试选择器、导入、.npmrc、界面清单里都不应再有（界面清单要等 F4，见第 6 节）；剩下的应该只是历史记录与任务编号。
