    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认

    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #11.2 GitHub Packages：可见性与安装

    查的是 GitHub 官方文档，2026-11-17 的版本。

    • 安装要令牌，公开包也一样。 Working with the npm registry：发布、安装、删除 private、internal、public 的包都要访问令牌；这个包源只支持个人访问令牌（classic）。GitHub Actions 里用 GITHUB_TOKEN，公开的包任何仓库的工作流都能下载（Publishing and installing a package with GitHub Actions）。.npmrc 的写法见迁移说明第 2 节。
    • 新包的默认可见性，两页说法不一。 npm 那页「Publishing a package」：第一次发布时默认是 private；Configuring a package's access control and visibility 也说组织的包首次发布默认 private，关联仓库只继承访问权限、不继承可见性。而 Actions 那页「Default permissions and access settings for packages modified through workflows」说，对支持细粒度权限的包源（npm 在内，见 About permissions for GitHub Packages），工作流用 GITHUB_TOKEN 新建的包继承运行工作流的仓库的可见性与权限模型；本仓库是公开的。哪一种会发生，发布前没法验证，以发布后包源上的实际为准（publish.mjs 会报告）。
    • publishConfig.access 起不起作用，文档没说。 它是 npm 的设置，npm 文档讲的是它在 npm 自家包源上的含义；GitHub 的文档里找不到它对 GitHub Packages 的作用。改成 public 是表达意图，不能当作公开的证明。本仓库早先的私有发布脚本也写过同样的提醒：不能把 --access=restricted 当作私有的证明。
    • 改可见性要人动手，而且不可逆。 包的管理员在包的设置页最下面 Danger Zone → Change visibility 改；公开之后不能再改回私有（访问控制那页）。工作流用 GITHUB_TOKEN 建包时，运行工作流的仓库的管理员成为包的管理员（Actions 那页）。REST 接口里只找到查询、删除与恢复，没有改可见性的。
    • 组织设置，读不到。 组织设置 → Packages 里，「Package creation」决定成员能建哪些可见性的包（public / private / internal），「Default Package Settings」的「Inherit access from source repository」默认开着（访问控制那页）。用 REST 读不到现状：GET /orgs/CavaiLAB 的结果里没有这些字段，读组织的 Actions 设置要 admin:org 权限，这次用的令牌没有。要组织所有者在网页上看。
    • 只读查到的现状。 CavaiLAB 名下还没有 npm 包；包源对 @cavailab/qian-core 返回 404（不存在），publish.mjs 的首次核对按「没有」处理。本仓库公开；Actions 开着、允许所有 Action，工作流令牌的默认权限是只读，release 在作业上显式声明了 packages: write（文档：permissions 可以修改 GITHUB_TOKEN 的权限）。
    • 撤回。 Deleting and restoring a package：公开包的版本下载不超过 5000 次才能删，要包的管理员；删除后 30 天内可以恢复。删掉之后能不能再发同一个版本号，文档没说，按不能处理。

    #11.7 0.2.1：data、biz 一渲染就报错的返修

    2026-11-18。0.2.0 发布之后，后端仓库换用已发布的包（F4），浏览器测试里 DataTable、OrganizeSelect、UserSelect 等一渲染就报 ReferenceError: React is not defined。包源上 data、biz 的 tarball 与 11.5 记的摘要相同，坏的就是发布的那一份。这次以 0.2.1 返修，10 个包都升版；发布要产品负责人点头，步骤照 11.3，版本换成 0.2.1，发布记录等发布之后补在这一节。

    项内容
    缺陷data、biz 的 dist/index.js 是经典 JSX 转换的产物：data 有 94 处 React.createElement、1 处 React.Fragment，biz 有 44 处 React.createElement，模块里只导入了 useState 等具名钩子，没有导入 React，渲染这两个包的任何组件都会报错。core、form、shell 导入的是 react/jsx-runtime，没有问题；tokens、contracts、sdk、运行时与插件开发包没有 JSX
    根因data、biz 的 rslib.config.ts 少了 core、form、shell 都有的 tools.swc.jsc.transform.react.runtime: 'automatic'，构建出来的是经典转换。原仓库起就缺这一行。工作区里各包的 exports 指向源码，演练场、SSR 用例与浏览器用例都由 @vitejs/plugin-react 按 automatic 编译源码，用不到构建出的 dist；这两个包 0.2.0 是第一次发布，所以以前没暴露

    构建data、biz 的 rslib.config.ts 补上那一行，dist 改为从 react/jsx-runtime 导入；修复本身不改其余 8 个包的制品（版本号不变时打包，与修之前逐字节相同）。没有另做 8 个层包共用的配置：放在 packages/qian/ 下的共用文件不属于任何一个包，它改了 turbo 的构建缓存不会失效；以后哪个包漏了，由下面两条检查在 PR 上拦住
