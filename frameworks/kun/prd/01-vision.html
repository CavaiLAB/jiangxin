    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认

    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #1. 愿景与定位

    状态：草案 v1 · 更新日期：2026-10-06 · 决策引用：ADR-001、ADR-002、ADR-003、ADR-014、ADR-016、ADR-018、ADR-019、ADR-020、ADR-021 · 上级索引：README

    #1.1 一句话定位

    匠心智能体平台面向 Agent 时代的多租户应用。Kun 提供 .NET 后端的运行时、内核库与平台组件，Qian 提供 React 前端框架与 TypeScript 运行时。开发者在 S1 用代码构建应用。后续阶段分别面向低代码搭建、租户市场和 Agent 协作。

    把这句话拆开：

    成分含义真相源
    多租户低代码 PaaS跑在 K3s 上、以 Apollo 为配置中心的 SaaS 底座；多租户、SSO、鉴权、微服务是硬性要求，不是可选特性ADR-004、ADR-005、ADR-006、ADR-007、ADR-017
    后端框架Kun 的内核档提供可独立使用的通用机制，平台档承载身份、权限等产品能力。两档共用 CalVer；组件运行时为 Kun.Runtime，目录市场使用 qian CLI。ADR-023、包迁移指南
    插件思维Kun.Runtime 装配组件。注册表、身份、权限、文件与配置使用同一套清单与运行时，部署组合由 profile 选择。组件以声明式表面和可选代码分发。ADR-002、ADR-003、ADR-020
    先开发者、后搭建者、再租户S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；组件化从 S1 起按 Agent 时代的做法交付：文件即组件、一键安装、一切皆插件，skill / agent / command / hook / MCP 等 Agent 原生表面在 S1 就是一等公民（ADR-020）ADR-018、ADR-020、ROADMAP
    Agent 原生能力契约机器可读、人与 Agent 共用权限与审计、元数据可校验可回滚；S4 经 MCP 对接外部 Agent 运行时，平台不写 Agent loopADR-016、§02、§10
    前端框架Qian 的 React 组件与外壳服务于后台应用。设计器与低代码运行时属于后续阶段。ADR-013、前端规格

    #1.2 与同类的分化

    维度传统低代码平台Agent 平台平台
    首要用户与起点业务人员与 IT 支持；一上来就给设计器Agent 开发者；一上来就给编排画布与模型接入先给开发者 SDK/CLI/TCK，再给搭建者设计器，再给租户市场；Agent 契约从 S1 起贯穿
    平台能力的组织方式内置模块，功能按菜单堆叠，系统能力与业务能力两套代码路径工具 / 模型 / 策略等类型化插件极小运行时 + 一切皆插件；平台能力也是插件（平台插件），同一清单、同一运行时语义、同一 TCK；一份清单派生路由、权限点、菜单、配置命名空间、OpenAPI、MCP 工具；文件即组件，qian add 一键安装
    多租户事后加租户列，租户解析常有请求头兜底与默认回退多为工作空间级隔离，不承诺数据层隔离租户只来自已校验令牌、fail-closed；共享库 + RLS 双保险；租户级生命周期是一等模型，并提供高隔离与私有化两档
    身份与权限自有账号体系，权限校验分散在控制器，可被客户端参数绕过API Key 为主，权限随 Key平台唯一 issuer（OpenIddict）；权限点由插件清单声明；单一判定点服务 UI / API / MCP 三入口；权限不进令牌、决策可解释
    元数据隐式契约，前后端各自理解；改表等于删表重建工作流 JSON，校验弱、回滚靠人带 Schema、版本化、可 diff、可回滚的元数据；正式的 Schema Migrator；元数据本身即 Agent 的上下文
    应用分发与升级模板复制为主，升级靠人工重导，导出包丢菜单与权限面向开发者的插件市场应用 = 组合包 + marketplace 条目（原 bundle，R28）；template / managed 两种分发；组件格式、升级冲突处理、权益 API 在 S1 定型
    扩展代码的位置进程内脚本引擎、热插 DLL沙箱或外部进程第三方代码永不进共享进程；信任等级决定允许的形态；前端不可信 UI 走沙箱
    Agent 的角色事后加一个「AI 助手」入口平台核心能力目录就是 Agent 的发现入口；写操作带 Schema 与副作用等级；Agent 作为一等主体、持委托链；S4 对接外部 Agent 运行时而非自建
    模型接入直连厂商 API，各模块各自配置自带模型抽象层复用模型服务网关（GPUStack + Higress）；平台只做租户、配额、计量，不自写模型代理
    部署与运维单体或多进程单库，配置散落云托管为主，私有化弱K3s + GitOps + Apollo；按 digest 的不可变发布；默认共享、高隔离租户、私有化整套 overlay 三档拓扑

    #1.3 为什么现在

    1. 行业已把 AI 写进低代码的品类定义。 调研（research/notes/d3-web-market.md）确认：权威分析机构 2026 年新版低代码应用平台象限直接以「AI 增强型」命名，其 2025 年的规划假设认为未来几年大部分企业会经由低代码平台落地 Agent；主流厂商都在做同样三件事——自然语言生成应用元数据、把平台能力以 MCP / CLI / Skills 开放给外部编码 Agent、在市场里上架 Agent 组件。一套 2026 年才开始建的平台若不把这些写进底座，上线即落后。
    2. Agent 协议层刚刚稳定，可以押注。 MCP 已进入中立基金会治理，2026-07-28 版把协议改为无状态、授权对齐 OAuth 2.1 与资源指示器；A2A 1.0 已稳定；官方 C# SDK 与 Higress 均已跟进。以这套标准为目标版本从头设计，比在旧协议上修补便宜得多（research/notes/d5-web-agent-native.md）。
    3. 「平台托管运行时 + 数据不出平台」成为市场信任标签。 外部托管的集成框架正在被平台托管形态取代，公有 SaaS 普遍「禁第三方任意代码、允许纯元数据包」。平台跑在 K3s 上并以组件（文件夹 + 清单 + 声明式表面，无代码组件是常态）为分发单元，天然适合这一形态。
    4. 我们自己的前置条件已经具备。 Kun 已有可生产的核心模块与多租户、Outbox、RLS 等设计；团队已有 K3s / GitOps / Higress / MaaS 基础设施与一套经过验证的 React 工程规范；参考平台的功能全集与反例已完成七个领域的基线梳理（research/baseline-digest.md）。缺的是把它们按正确的顺序组装起来。
    5. 再晚就要为旧设计买单。 基线明确列出「S1 起就要做对、否则 S4 返工」的清单（带 Schema 的写命令、统一主体模型、可解释权限、一份契约多处生成、租户只来自令牌、审计含主体链）。这些都是底座层的决定，越早定越便宜。

    #1.4 为什么是插件思维

    • 运行时小才守得住。 多租户、身份、鉴权是平台的可信计算基，必须「不可绕过」；v2 没有特权内核：运行时 Kun.Runtime 只剩上下文、服务注册、类型化事件、可逆副作用与装载器，租户、鉴权、审计的强制执行点是 platform profile base 组合包里的 waterfall 监听器（profile 标记为不可移除，patch 动不了），一切可替换的东西都是插件，运行时才能小到可以被完整审计与测试（ADR-020 D20.1）。
    • 平台能力也是插件（平台插件，原称系统插件），平台才会吃自己的狗粮。 租户、身份、鉴权、文件、配置这些官方能力按同一份清单、同一运行时语义、同一 TCK 交付，连注册表与生命周期控制器本身也是插件（qian.registry / qian.lifecycle），意味着第三方插件遇到的每一个坑官方插件会先踩到；SDK 的质量由平台自己先担保。
    • 一份清单派生一切，Agent 才有可读的契约。 清单（.qian-plugin/plugin.json；代码部分的字段由源生成器派生并合并进同一份）静态可索引，宿主不执行插件代码就能生成路由、权限点、菜单、配置命名空间、OpenAPI 聚合与 MCP 工具描述。这正是 Agent 就绪所需的「能力契约机器可读」，不是另起一套。
    • 组件化按 Agent 时代的做法，而不是传统平台设计。 文件即组件：组件 = 文件夹 + 清单 + 声明式表面（skill / agent / command / hook / MCP 服务器等 Markdown 与 JSON，Agent 可直接读写）+ 可选代码，无代码组件是常态；一键安装：qian add <component> 一条命令装进任何项目，目录市场是 git 仓库里的一份 marketplace.json；一切皆插件：没有需要打补丁的特权内核，能力按 seam 三角色拆分，换一个 Provider 就改变整个产品（ADR-020，§03 3.4a）。
    • 信任等级决定形态，才能同时服务 SaaS 与私有化。 policy.tier 决定允许的 runtime.form 与 policy.sandbox：官方 module 进程内编译期并入；第三方只能是声明式表面、package / function / 受限 ui 以及为某个 seam 提供 Provider 的组件（原 connector，R28），永不进共享进程。同一套模型下，共享 SaaS 可以安全开放生态，私有化客户可以装自己的 service。
    • 应用市场只是插件机制的延长线。 应用 = 组合包 + marketplace 条目（R28）；S1 末「一切皆包」跑通——qian add 一键安装与 marketplace.json 目录市场从 S1 就有，S2 低代码应用可打包（设计器保存即产出组件文件夹），S3 的商业市场（授权、计费、审核）叠在同一格式之上，不另起格式。市场不是另一个子系统，而是同一制品流水线换一个消费者。

    反过来说明确不做的事（ADR-002、ADR-020 D20.11）：为第三方代码与可 AOT 的边缘 profile 做运行时热插 DLL（R27）、进程共享的服务端脚本引擎、把 sidecar 作为默认依赖、引入许可证受限的开源低代码 / AI 平台代码；也不再按物理形态做顶层分类、不维护第二套清单格式。

    #1.5 为什么先做开发者底座

    • 低代码运行时的每一层都压在底座上。 动态数据引擎要复用租户上下文、RLS、Outbox；审批引擎要复用组织模型、事件总线、调度、表达式规范；设计器要复用元数据版本化契约。先把这些做成可被代码直接消费的技术组件，S2 的引擎才有地基，否则会像参考平台那样在引擎里重复实现一遍租户与鉴权。
    • 开发者是最严格的验收者。 「开发人员用代码在平台上写出一个多租户应用，登录、鉴权、存储、文件、配置、网关、事件、审计全部由平台提供」是 S1 的退出标准（ADR-018）；ADR-020 §6 又加了一条：在空白项目里 qian add identity authz files 后 30 分钟内跑通登录、权限检查与上传，不部署平台。能让开发者半天写完一个多租户应用、30 分钟装好通用能力的 SDK，才配承载低代码。
    • 底座错误最贵。 ADR-001 记录了早期多副本与多租户链路的缺口和测试要求。现行租户、事件与网关实现见 Kun 模块地图。
    • 插件机制与 SDK 本身就是第一款产品。 开发者插件市场（面向开发者的组件与连接器）与 S3 面向租户的应用市场共用同一套组件格式（文件夹 + 清单 + marketplace 条目）与发布流水线，只是消费者和授权模型不同；S1 把组件格式做对，后面两步才不返工。
    • Agent 就绪不能靠事后补。 统一主体模型、可解释权限判定、带 Schema 的写命令、审计含主体链都是底座层约定，在 S1 落地的成本最低，在 S4 补的成本最高。

    #1.6 本章非目标

    • 本章不描述功能细节与接口（见 §07–§10），不描述阶段里程碑（见 ROADMAP），不复述决策理由（见 docs/adr/）。
    • 本章不对市场规模与客户数量作任何数值承诺（见 §04 的「待定 / 区间」口径）。
