    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件

    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件

    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API

    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认

    #ADR-008: Introduce Kun.Identity Module — Reversing ADR-001

    本文是原 Kun 的决策记录，引用时写「Kun ADR-008」。2026-11-18 搬入本仓库时清理了引擎与下游产品的名字：正文照原文，方括号里是整理时替换的说法。

    Implementation update (S1-KUN-004): the identity client guide and canonical S2S guide supersede the legacy issuer and incomplete cookie-flow examples below. The original rationale is retained as history.

    S1-KUN-026 后续实现。平台 OIDC 连接器与 Cookie 应用复用 Kun.Identity 的发现、令牌交换和 ID token 校验。上游账号映射、用户目录与成员关系保留在平台包。参见身份客户端指南。

    Status: Accepted Date: 2026-04-22 Author: claude-kun (Kun framework specialist) Supersedes (partially): ADR-001 — Do Not Introduce a New Kun.Identity Module Context: ADR-001 (Apr 2026) declined to create a Kun.Identity module because Phase 1 identity needs were fully covered by Kun.Gateway (OIDC → S2S JWT translation) and Kun.Security (S2S JWT validation + JWKS). That decision explicitly anticipated a revisit: "If future phases need cross-cutting identity abstractions (e.g., IPermissionChecker with policy store), we will revisit this ADR." Consumer-side divergence observed across three ［下游的 C# 服务］ has now materialised exactly that signal.

    #What changed since ADR-001

    Three concrete divergences drove the revisit:

    1. Three near-duplicate AddJwtBearer configurations. ［下游的 C# 服务］ Edge, Platform, and Notification services each hand-roll services.AddAuthentication().AddJwtBearer(JwtBearerDefaults.AuthenticationScheme, opts => ...). The issuer / audience / JWKS URL pointing at Authentik is copied verbatim; the clock-skew and expiry-required flags differ slightly; each service reaches a subtly different security posture. The only way to pull these back into a single policy is a framework abstraction.
    2. Per-service S2SJwtIssuer wiring. The existing Kun.Security.S2SJwt.S2SJwtIssuer exists as an implementation, but the public DI surface is verbose (services.AddOptions<S2SJwtOptions>()... + manual key loading). Consumers have been wrapping it with small adapter helpers — five different helpers, five different signatures.
    3. OIDC code-exchange lives nowhere. Authentik supports both client-credentials (used by the gateway) and authorization-code flows. The code-flow exchange is not covered by either Kun.Gateway or Kun.Security today, so Edge open-coded an HttpClient.PostAsync against /application/o/token/ with inline form encoding. That code has drifted into five subtle variants across services.

    The generalisable pattern — validate external tokens, mint S2S tokens, talk to an OIDC provider — is orthogonal to the gateway / security split. Lifting it to Kun.Identity consolidates all three configurations behind one fluent builder.

    #Decision

    Introduce src/Kun.Identity/ (IsAotCandidate=true) exposing three public abstractions and a single DI entry:

    services.AddKunIdentity(id =>
{
    id.AddJwtBearer(opts => { opts.Issuer = ...; opts.Audience = ...; opts.JwksUri = ...; });
    id.AddS2SIssuer(opts => { opts.Issuer = ...; opts.SigningKeyPem = ...; });
    id.AddOidcClient("authentik", opts => { opts.Authority = ...; opts.ClientId = ...; opts.ClientSecret = ...; });
});
    AbstractionPurposeBacking implementation
    IJwtValidatorValidate external Bearer JWT → ClaimsPrincipal?KunJwtValidator (JsonWebTokenHandler + ConfigurationManager<OpenIdConnectConfiguration> JWKS rotation)
    IJwtIssuerMint signed JWTs (S2S flow)KunJwtIssuer (RS256 via JsonWebTokenHandler + RsaSecurityKey)
    IOidcClientOIDC discovery + authorization_code exchangeKunOidcClient (HttpClient + source-gen JsonSerializerContext)

    The module is a facade, not an IdP. It does not embed a token database, does not sign user credentials, does not implement the OIDC server role. Running Authentik / Keycloak / Auth0 remains the consumer's responsibility; Kun.Identity gives them a uniform client surface against that infrastructure.

    #Relationship to existing Kun.Security / Kun.Gateway

    • Kun.Security.S2SJwt (Issuer, Verifier, Options, JWKS middleware) stays in place unchanged for backward compatibility. New services prefer the Kun.Identity.IJwtIssuer / IJwtValidator surface because it also covers external tokens and OIDC clients in one registration — but existing consumers of Kun.Security.S2SJwt keep working.
    • Kun.Gateway.S2sTokenIssuer remains the Gateway-internal S2S issuer. A future refactor can have it implement Kun.Identity.IJwtIssuer and delete the duplicate code path — that migration is out of scope for this ADR.
    • Kun.Security.KunServiceAuthenticationExtensions.AddKunServiceAuthentication is the ASP.NET Core AddJwtBearer pipeline wiring. It is not subsumed here. Consumers that need ASP.NET Core's auth middleware still call it; consumers that need framework-neutral bearer validation (gRPC interceptors, background workers, custom middleware) use IJwtValidator directly.

    #Why ADR-001 was right at the time, and is wrong now

    ADR-001 weighed four drivers:

    DriverStill true today?
    "Capability already exists" — Gateway + Security cover the lifecyclePartially. They cover S2S, not external Bearer + OIDC code-flow.
    "No gap in Phase 1"No longer true. P1-CS-007 / P1-CS-010 shipped, and three consumer services now carry drift that a framework abstraction would eliminate.
    "Avoid framework bloat"Still a concern. This module adds ~9 types + two tests to the framework surface. The divergence cost exceeds that now.
    "Downstream simplicity"Inverted. Downstream is currently less simple because each service re-implements the same wiring.

    The drivers that made ADR-001 correct at the time — Phase 1 scope, no observed divergence, single pattern per service — are no longer the situation. ADR-008 records the revisit with the exact signal ADR-001 asked for.

    #Consequences

    #Positive

    • Consumer services replace per-repo auth helpers with one AddKunIdentity(...) call — the divergence driver goes away.
    • IJwtValidator is framework-neutral; gRPC interceptors / background workers can do bearer validation without spinning up ASP.NET Core's auth pipeline.
    • OIDC code-exchange moves into the framework, closing the last hand-rolled HttpClient.PostAsync against /token in consumer code.

    #Negative / Trade-offs

    • Framework surface grows by one module (~9 public types).
    • Two S2S issuer implementations coexist until the Kun.Security → Kun.Identity migration lands. Consumers picking "which one" is mildly confusing until the canonical choice is Kun.Identity.
    • The OIDC client only implements authorization-code grant. Refresh, client-credentials, and device-flow are follow-ups.

    #Risks

    RiskMitigation
    Microsoft.IdentityModel upgrade regresses AOTCI AOT matrix includes Kun.Identity; stop-gate rule applies.
    Consumer mistakes IJwtIssuer for user-password authAGENTS.md is explicit: this module is an identity client, not an IdP.
    Drift between Kun.Security.S2SJwtIssuer and Kun.Identity.KunJwtIssuer during the transitionBoth use Microsoft.IdentityModel.Tokens primitives and the same JWS algorithm set; tests in Kun.Identity.Tests + Kun.Security.Tests cover round-trips on both sides.

    #Follow-ups

    1. Migrate ［下游的 C# 服务］ off their hand-rolled AddAuthentication().AddJwtBearer helpers onto AddKunIdentity(id => id.AddJwtBearer(...)).
    2. Retire Edge's hand-rolled OIDC code exchange in favour of IOidcClient.ExchangeCodeAsync.
    3. Add refresh-token + client-credentials grants to KunOidcClient once a consumer requires them.
    4. Land the Kun.Security → Kun.Identity bridge: have Kun.Security.S2SJwtIssuer implement Kun.Identity.IJwtIssuer (or the reverse) so services can pick one canonical abstraction.
    5. Consider IPermissionChecker — ADR-001 flagged this as the specific trigger for a revisit. Still out of scope here; capture in a future ADR when a second consumer needs it.

    #主体类型字段补充（S1-KUN-013）

    ICurrentUser.PrincipalKind 属于当前身份的最小字段，来源是已经认证的 principal_kind claim，不是浏览器专有字段，也不是权限集合。依据当前身份扩展指南，字段放在已有 ICurrentUser 上，IAuthenticatedUser 继承，不增加第三个身份接口。

    旧实现通过默认接口值 user 保持兼容；框架 JWT / Cookie 适配器保留真实类型，无类型声明的旧浏览器身份按 user。权限执行点接受 user/service/agent 的显式类型，歧义/未知值拒绝，不能把机器服务悄悄当作用户。Agent 仅保留其主体维度，不因此开放 S2S 签发。主身份的 sub 与 NameIdentifier 若同时存在须一致，关键 claim 不能从次身份补齐。
