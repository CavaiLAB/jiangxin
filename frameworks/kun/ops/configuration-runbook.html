    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #配置开发、运行与故障处置（S1-CFG-001 / 002 / 003）

    配置源顺序与引导项见 Kun.Configuration.Platform。本手册描述已实现客户端的行为；L0–L4 为配置运维状态，与权限模型分层无关。

    #开发配置分工

    配置类别存放与读取位置边界
    部署级引导Kustomize / 宿主环境Apollo 端点、AppId、环境等；Apollo 不能改写自身引导
    平台 / 服务级非敏感参数Apollo发布前扫描；运行期每份原始快照与合并结果都校验，失败保留旧值
    密钥K8s Secret 投射文件配置只保存公开 secretRef，使用时经声明与审批取交集后解析
    租户级在线设置ITenantSettings不进入 Apollo；能力随 TEN 任务交付
    前端公开运行配置同源 /app-config.json（ConfigMap 挂载，S1-YUE-012）只允许浏览器可公开的数据，不能放原始密钥或后端解析能力；外壳只解析与校验，从不执行

    密钥解析、审计端口与内存边界见 密钥 Provider 开发说明，提交发布前使用 配置扫描门禁。ApolloConfigurationSchema 由宿主传入合成配置 Schema，敏感属性使用 x-qian-sensitive；Schema 自动收集仍属后续 CFG 任务。属性名与 patternProperties 的键都和配置键一样不区分大小写；模式按 ECMA-262 可移植子集解释，超出子集或规模上限即判 Schema 无效，键名含各方言判断不同的字符时按敏感处理。

    #降级矩阵

    状态当前行为处置
    L0 正常拉取和长轮询成功，IOptionsMonitor 随配置根更新读取最终生效值；Secret 文件、环境变量、命令行仍可覆盖 Apollo
    L1 运行期失联保留当前内存配置，告警并重试，业务宿主不重启恢复网络/服务，再核对实际值与修订；不能只看发布成功
    L2 离线启动且缓存有效网络/IO 类失败时读取同环境、端点、应用、集群、namespace 和标签的有效缓存保护缓存文件，恢复后回读新值；缓存只承载非敏感配置和引用
    L3 拒绝新快照或访问被拒运行期保留旧值并重试；启动 401/403 或访问密钥缺失直接拒绝，不回退缓存修正权限或候选配置；不要用删除缓存和反复重启掩盖原因
    L4 无可用基线无网络且无有效缓存，或引导/必需项无效时启动失败恢复有效配置来源；禁止用空配置启动

    #排查顺序

    1. 确认 AppId、UAT/PRO、Cluster、ConfigServer 地址和 namespace 顺序。引导来自宿主源，Apollo 不能修改自己的访问地址。
    2. 确认高优先级源是否覆盖了同名键，尤其是 Secret 文件、环境变量和命令行。配置发布成功不等于最终生效值发生变化。
    3. 检查网络、DNS 与长轮询超时；客户端超时必须大于 60 秒。默认客户端关闭自动重定向。
    4. 401/403 检查访问密钥引用与授权；只检查引用名和解析是否成功，不输出值。签名前每次解析引用，缺失不发送未签名请求。
    5. 检查缓存所属环境、目录权限与完整性；UAT/PRO 缓存在不同子目录，快照还按端点、应用、集群、namespace 顺序和标签分隔。

    #部署步骤：平台宿主装配

    platform profile 宿主（包括自建的组合包）在登记 ISurfaceReader 与 IToolContractHasher 之后，必须调用 services.AddKunCapabilities()。它装配能力契约的登记期检查：组件登记能力时就生成目录条目、预编译输入校验器，不合格的契约让组件挂载为 Failed，见 Kun.Capabilities「登记期契约检查」。

    漏掉这一步宿主照常启动，但检查退化为首次读目录或调用时才编译：不合格的能力不会在挂载时暴露，目录排除它并记一次告警（「能力 … 的契约不合格（规则），位置 …；该能力不登记、不进入目录。」），执行入口对它返回 404。预发环境上线后检查宿主日志：出现这条告警说明有组件带了不合格的契约；该组件的挂载状态仍是 Ready 而不是 Failed，说明组合包漏了这一步。

    #部署步骤：数据库迁移

    带迁移的组件上下文（如 qian.capabilities 的菜单偏好与幂等回执表）随宿主镜像交付迁移，每次发布按下面的顺序上线：

    1. 以 --migrate-only 启动迁移任务（K8s Job），用迁移属主连接执行全部待应用迁移。属主同样必须是 NOSUPERUSER / NOBYPASSRLS。
    2. 用 Kun.Data 「迁移执行与 RLS 核查」一节的 SQL 核对：每张租户表都强制 RLS，且恰有 qian_tenant_access 与 qian_tenant_guard 两条策略。不要用 dotnet ef database update 代替第 1 步：RLS 由 AddKunData<T> 登记的生成器在迁移执行期产出，dotnet ef 的设计时入口没有经 AddKunData<T> 装配时用的是 Npgsql 默认生成器，建出的租户表没有 RLS 与策略。设计时入口经 AddKunData<T> 装配时，dotnet ef migrations script 同样带 RLS，可以用来审阅将要执行的 SQL。
    3. 再滚动在线副本。启动检查发现未应用的迁移，或迁移生成器不是 Qian 的，会拒绝启动；按第 1 步处理，不要绕过。

    #过期幂等回执清理

    通用执行入口的幂等回执（plugin_qian_capabilities.invoke_receipts）过期后不再回放。物理删除靠本租户后续带键写调用登记时的惰性清理，每次最多 100 行；长期没有带键写调用的租户，过期回执会一直留在表里，其中可能有 public / internal 能力的响应原文。按需定期用下面的 SQL 清理，删除条件与惰性清理相同（expires_at <= now()）。执行中的登记租约未到期，不会被删。

    有 BYPASSRLS 的维护角色（如数据库管理员）一次清理全部租户，分批删除以免长时间持锁，重复执行到返回 DELETE 0：

    DELETE FROM plugin_qian_capabilities.invoke_receipts
WHERE ctid = ANY (ARRAY(SELECT ctid FROM plugin_qian_capabilities.invoke_receipts WHERE expires_at <= now() LIMIT 10000));

    迁移属主与在线业务角色都是 NOBYPASSRLS，表又强制 RLS，它们只看得到会话变量 app.current_tenant_id 指定的租户，要逐个租户执行（把 <租户 ID> 换成租户主档里的 ID）：

    BEGIN;
SELECT set_config('app.current_tenant_id', '<租户 ID>', true);
DELETE FROM plugin_qian_capabilities.invoke_receipts WHERE expires_at <= now();
COMMIT;

    #生命周期和验证

    配置根由创建者释放，释放会停止文件监视和 Apollo 长轮询。配置插件借用宿主根，卸载时撤销自己的 Config 服务与错误码登记，不释放其它独立消费者共用的根。

    快速协议回归使用共享 ApolloFixture；真实验收的四个类共用一套 RealApolloPortalFixture：Apollo 2.5.2 Portal、ConfigService/AdminService 与 MySQL 8.0.43，整个集合只启动一次（S1-QA-017）。通过真实 AdminService 修改并发布，检查同一 IOptionsMonitor 在 60 秒内从 10 更新到 25，然后停止服务验证缓存启动和无缓存失败；停服务的用例由类排序器排在集合最后。CI 测试制品中的 evidence/apollo-real-reload.json 保存更新耗时。

    真实发布回归还覆盖敏感字段明文：拒绝候选后，内存仍保留原引用、缓存不包含被拒值；再发布有效引用，长轮询能恢复更新。证据文件同时保存 sensitiveCandidateRejected、cacheContainsRejectedValue 和 recoveredAfterRejection，不能仅凭服务健康状态推断这些行为成立。

    强类型配置的最后有效值由 Kun.Configuration.Platform 的 AddKunOptions 保留，见下一节。生产高可用、Portal OIDC 与托管 MySQL 按部署任务验收。

    #热更新被拒、发布审计与 namespace 比对（S1-CFG-003）

    1. 强类型配置没有跟着 Apollo 变。 原始配置根已是新值、IOptionsMonitor 仍是旧值，说明候选值未通过校验、宿主保留了上一份有效值。看指标 qian_config_reload_failed_total（标签 options_type、options_name、plugin）是否增长、日志 EventId 2101，以及进程内事件 config/reload-failed；三者都不含配置值。修正候选值后重新发布，下一次变更即恢复。不要靠重启“刷新”：关键配置启动即校验，同一个非法值会让宿主启动失败（L4）。
    2. 核对一次发布有没有被接受。 每个 namespace 快照的接受与拒绝在平台审计链各记一条：能力 ID qian.config/release.applied / qian.config/release.rejected，资源 apollo://<AppId>/<Env>/<Cluster>/<namespace>，拒绝记录的 reasons 给出原因码（如 CONFIG_SECRET_EXPOSED）。日志 EventId 2112「发布记录未能写入平台审计链」表示平台链未显式启用 chain.platformRole 或审计组件故障：配置照常生效，但这次发布没有审计记录，需要对照 Apollo 的发布历史补查。审计组件缺席时最多暂存 256 条，就绪后按序补写。
    3. 发布前比对 namespace 骨架。 部署流水线（S1-DEP-002 / S1-DEP-005）从仓库根目录运行 dotnet build tools/Kun.Configuration.Tool/Kun.Configuration.Tool.csproj -c Release，发布前对目标环境的 ConfigService 运行 dotnet tools/Kun.Configuration.Tool/bin/Release/net10.0/Kun.Configuration.Tool.dll . --profile platform --compare <ConfigService 地址> --access-key-env <存放 AccessKey 的环境变量名>，见 Apollo namespace 骨架工具。退出码 1 时按 findings 的 kind、key、pointer 处理：missing 在 Apollo 补键或修正 Schema 的 required；extra 删除线上多余键或把键补进 Schema；namespace 本身 missing 表示宿主已订阅却没建。退出码 2 是参数、网络或 AccessKey 问题，输出不含配置值。namespace 名超过 32 个字符的组件（目前是 qian.notify.channel.sms / email）建不出来，工具只给 warning，处置见 S1-CFG-003 任务日志的建议裁决。CI 每次构建把各 profile 的骨架写进测试结果 evidence/apollo-namespaces，可作为新建 namespace 的导入稿。
    4. 配置值接口返回 403 / 404。 GET /api/config/values/{plugin} 只对平台主体开放。403 先确认不是租户令牌，再看决策审计的 reason：permission_not_registered 表示权限目录里没有 qian.config:values:read，应核对实际预装制品是否含该权限声明、Authz 是否已读取目录；qian.config 已通过既有安装门，不能再把未登记当作骨架期的默认状态。404 表示组件未预装、只有静态绑定没有制品文件快照、组件没有 Schema，或审计组件不可用。
