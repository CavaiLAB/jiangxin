    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #Why Kun Splits Writes from Reads

    Kun enforces a hard boundary between the write side and the read side of every bounded context. This is not a stylistic preference — it is enforced by module dependencies and verified by CI. Understanding the reasoning helps you work within the model rather than against it.

    #The write side: consistency first

    Command handlers use KunDbContext directly or inject a repository port defined by their domain. The write side loads an aggregate, calls domain methods, and delegates to IUnitOfWork.SaveChangesAsync. That single call does several things atomically:

    1. Applies EF Core change tracking to produce the correct SQL.
    2. Collects domain events from every modified IAggregateRoot via ChangeTracker.
    3. Dispatches domain events to in-process handlers via IDomainEventDispatcher.
    4. Converts any resulting integration events into OutboxMessage rows.
    5. Commits the aggregate changes and the Outbox rows in one database transaction.

    This sequence exists because consistency is the write side's job. A command either fully succeeds — business state updated, domain events dispatched, integration events enqueued — or it fully fails with no observable side-effects. The Specification pattern keeps query logic out of handler code while still letting the repository translate rich criteria into SQL without leaking EF Core types up into the domain layer.

    The cost is performance. Loading aggregates, tracking changes, and running the full pipeline takes more work per request than a raw SQL insert. For the write side this is the correct trade-off: correctness matters more than throughput.

    #The read side: performance first

    Query handlers open connections from a dedicated read-side NpgsqlDataSource (potentially pointing at a read replica) and run raw SQL with Dapper; Kun does not wrap either library. No EF Core context is involved; there is no change tracker, no aggregate loading, no domain logic.

    The result is flat DTOs returned directly to the caller. Because there is no object graph to navigate and no invariants to enforce, the read side can denormalize freely: a single query can join five tables and return a DTO shaped exactly for the API response, avoiding the N+1 problems that appear when EF Core navigation properties are misused.

    The read side can also be published as a native AOT binary, which the EF Core write side cannot. Dapper's classic Query<T> builds its row readers with reflection, so an AOT-published service adds Dapper's source generator (Dapper.AOT, [DapperAot]) or reads rows with NpgsqlDataReader directly; see read-side patterns.

    #How the Command/Query divide maps to Kun.Mediator

    KunMediator dispatches every IRequest<TResponse> to its registered handler through a FrozenDictionary<Type, RequestHandlerBase> — O(1) lookup with zero runtime reflection. Handlers are registered explicitly at startup via KunMediatorBuilder. The mediator does not scan assemblies; there is no runtime discovery.

    Pipeline behaviors wrap each dispatch. The standard write-side stack is:

    ValidationPipelineBehavior   ← rejects invalid commands before touching the database
UnitOfWorkPipelineBehavior   ← calls SaveChangesAsync after the handler returns
LoggingBehavior              ← structured log at entry and exit
TracingBehavior              ← opens an OpenTelemetry span per dispatch

    Query handlers carry only LoggingBehavior and TracingBehavior by default — there is nothing to validate or commit. Adding UnitOfWorkPipelineBehavior to a query handler is a configuration mistake that the type system cannot prevent, but CI code review does. The distinction is explicit: every registration in Program.cs names the request type, the response type, and the handler type. There is no magic.

    #Trade-offs to be aware of

    Two models to maintain. Every write-side aggregate and its corresponding read-side DTO are separate representations. When you add a field to an aggregate you must also update any queries and DTOs that need to surface it. The consistency guarantee you get from the write side does not automatically flow to the read side.

    Denormalization can drift. Read-side DTOs are shaped for API consumers, not normalized from aggregate state. If a consumer's requirements change and the DTO is updated but the underlying data is not re-projected, the read side and the write side can express different views of the same entity.

    No EF Core in query handlers. Using EF Core in a query handler breaks the UoW pipeline behavior's transaction boundary assumptions and gives up the option of publishing the read side as a native AOT binary. Neither the compiler nor the project references enforce this — command and query handlers usually live in the same project — so reviewers check that query handlers take no EF Core types.

    The split is explicit and by design. It makes each side independently optimizable and keeps the invariants of each clearly scoped.
