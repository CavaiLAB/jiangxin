    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #When to use ICurrentUser vs IAuthenticatedUser

    The host selects the authentication scheme and registers a request-scoped adapter. Choose the interface by the data and authentication context the caller needs.

    InterfaceData available to the callerRuntime source
    Kun.Core.Security.ICurrentUserUserId, PrincipalKind, Roles, IsAuthenticatedKun.Security.Security.JwtCurrentUser after S2S validation, or a host's browser or platform adapter
    Kun.Identity.IAuthenticatedUserCore fields plus an optional ClaimsPrincipal, tenant id, email and display nameKun.Identity.AspNetCore.KunCurrentUser in an OIDC cookie host
    Kun.Identity.Abstractions.ICurrentUserCore fields plus an optional Kun.Security.Principal snapshotIdentity.Client reads the authenticated session or validated service identity
    Kun.Identity.Abstractions.IAuthenticatedUserGuaranteed Principal and UserIdA platform contract for callers that have already required authentication. The default client registers the nullable current-user view

    AddKunIdentityAspNetCore registers the core and browser interfaces against the same scoped adapter. AddKunIdentityClient makes the platform current-user interface available and offers its implementation to core callers through a scoped alias. The core alias uses TryAddScoped, so an explicitly registered core adapter retains its place. Background workers can supply AnonymousCurrentUser.Instance.

    #Decision table

    Caller scenarioInjectWhy
    gRPC service handler (S2S JWT)ICurrentUserThe validated S2S principal supplies subject, kind and roles.
    gRPC interceptor / pipeline behaviourICurrentUserSame — operates at the S2S boundary.
    ASP.NET Core API endpoint the browser hits directlyIAuthenticatedUserCookie middleware populated TenantId / Email / Name / Principal; skip the cast.
    ASP.NET Core background worker (BackgroundService)ICurrentUser with a null checkNo request scope exists; bind AnonymousCurrentUser explicitly.
    Outbox publisherICurrentUser, usually AnonymousCurrentUser.Background context — obtain any required identity from the authenticated message context. OpenTelemetry baggage carries diagnostic context.
    Unit testICurrentUser with a hand-rolled fake (a record MyUser(…) : ICurrentUser) or AnonymousCurrentUser.Instance.Tests depend only on the narrow interface; no HTTP context is needed.
    Component that reads tenant (EF filter, cache key)ITenantContext, not either of these.Tenant identity propagation has its own abstraction — don't couple persistence-layer code to an auth interface.

    #How to extend correctly

    Happens rarely. When you need a new field:

    1. Is it present on S2S JWT claims? → add to ICurrentUser and to every implementation. Update docs/adr/kun/ADR-008-Kun.Identity-module.md with the rationale.
    2. Is it browser / cookie only? → add to IAuthenticatedUser. Update docs/adr/kun/ADR-010-Kun.Identity-cookie-session.md.
    3. Is it a concern of a different subsystem? (tracing, tenancy, feature flags) → add it to the subsystem's own abstraction (ITenantContext, ITracedCurrentUser, …) and have the current-user binding expose or forward it there if needed. Example precedent: ITracedCurrentUser carries TraceId without polluting ICurrentUser.

    #Anti-patterns (do not do these)

    • ❌ ICurrentUserEx / IEnhancedCurrentUser / ICurrentUserV2 — every one of these reinvents IAuthenticatedUser. If IAuthenticatedUser is missing a field, add the field to IAuthenticatedUser after reading Kun ADR-010, don't fork.
    • ❌ A per-service ICurrentUser subinterface in a downstream consumer — consumer services get no value from owning the abstraction.
    • ❌ ClaimsPrincipal injection as a first-class service — always go through IAuthenticatedUser.Principal. Direct ClaimsPrincipal injection hides which host provided it.
    • ❌ Mutable ICurrentUser implementations — instances are scoped to a single request; mutating one breaks baggage assumptions for the async context.
    • ❌ Making ICurrentUser depend on Microsoft.AspNetCore.Http.HttpContext — Kun.Core is BCL-only and the interface stays there so non-HTTP hosts (gRPC-only workers, integration tests) can target it without ASP.NET Core in their closure.

    #If you think you need something new

    1. Read this doc end-to-end. Yes, including the anti-patterns.
    2. Read Kun ADR-008 and Kun ADR-010.
    3. Post the proposed field + its source (JWT claim / cookie / header / derived) in the PR description and call out which interface it belongs to per the decision rules above.
    4. If none of the rules fit, write an ADR that supersedes / extends Kun ADR-010 with the new concern — before adding code.

    If the addition is still ambiguous after all that, leave the code as-is and raise it at the next framework review. The cost of one extra sprint of "injecting IAuthenticatedUser and casting to something" is far lower than the cost of shipping a third sibling abstraction that every downstream service then has to track.

    #授权主体类型

    PrincipalKind 是 principal_kind 的只读身份投影。内置 JWT / Cookie 适配器与 HTTP/gRPC 权限入口使用同一个主身份读取规则，Mediator 从 ICurrentUser 取值。不能从调用请求的 JSON、头或角色名推断它。旧自定义适配器默认 user；如果适配器代表服务或 Agent，必须显式实现此属性，不能让机器身份继续使用用户默认值。

    #端口登记与次序

    ICurrentUser 与 ITenantContext 只由身份 / 多租户适配器登记：AddKunSecurity()（JwtCurrentUser）、AddKunIdentityAspNetCore()（KunCurrentUser）、AddKunMultiTenancy()，或宿主自己的适配器。数据与审计组件不占这两个端口：AddKunDataConventions<TContext>() 与 AddKunAuditing<TContext>() 的拦截器在上下文创建时按需解析，没有登记时按匿名（AnonymousCurrentUser）、无租户（NullTenantContext）记录。所以适配器在数据组件之前或之后登记都生效，不存在「先登记数据组件就把身份适配器挤掉」的次序约束。

    • AddKunSecurity()、AddKunIdentityAspNetCore() 以 TryAdd 登记：同一宿主装了多个真实适配器时先登记者生效，要换实现就显式 Replace；AddKunMultiTenancy() 也以 TryAdd 登记租户上下文，保留宿主选择的实现。
    • 宿主自己的服务构造注入 ICurrentUser、而宿主又没有身份适配器时（后台作业、迁移任务），显式登记 AnonymousCurrentUser.Instance；框架不再顺带替它登记。
    • KunDbContext 的构造需要 ITenantContext：单租户宿主显式登记 NullTenantContext.Instance。
