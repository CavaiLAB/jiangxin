    Qian 架构决策记录（ADR）索引
    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #3 做法上的几条决定

    下面是本计划的提议，执行中发现行不通就回到这里改，并写明原因。

    1. 不改写历史。 两个来源都用子树合并带历史导入，原提交的 SHA 原样保留。原 Qian 的任务日志与决策记录里引用了几百处提交 SHA，改写历史会让它们全部失效。代价是旧提交说明里的 #N 改不了，GitHub 会把它们链到本仓库的同号 PR 上，读历史时以树内文件里改写过的写法为准。
    2. 两个来源先各落在一个过渡目录里：原 Kun 在 _import/kun/，原 Qian 在 _import/qian/。 两边顶层有 14 个同名项，其中包括各自的构建基线文件，叠在一起两边都构建不了；仓库根现有的入口文件与框架级文档也和原 Kun 的同名。各放进一个子目录之后，两棵树各用各的构建基线，导入当天就能各自通过自己的全部检查，导入的结果也能拿树对象逐字节核对。过渡目录随后搬空：B2 把原 Kun 提到仓库根，原 Qian 的随构建并轨与各域批次搬走，最后删除。
    3. 导入只带主干。 只导入两个来源仓库的 main 与原 Kun 的版本标签，别的分支不带。原 Kun 的发布说明留在原仓库里，不复制。
    4. PR 一律用合并提交合入。 压缩合并或变基合并会丢掉导入的历史。
    5. 先导入、后冻结。 子树合并可以重复做，所以不必先冻结再导入。导入的 PR 合入之后，两个原仓库进入收口期：只收在途任务的收尾与紧急修复，新的功能改动到本仓库来做。产品负责人宣布冻结之后，原仓库只再合入写明去处的说明，随即归档为只读，然后做最后一次同步：归档是硬冻结，同步拿到的就是归档时的头。最后一次同步合入之前，过渡目录里的文件不改名、不搬动、不改内容，同步才不会冲突，结果也才能拿树对象核对；所以整理（B2）从冻结开始，改到过渡目录里的 PR 可以先开、先跑检查，排在最后一次同步之后合入。
    6. 检查跑在 GitHub 托管的 runner 上。 原 Kun 的检查原来全部跑在自托管的 runner 上。本仓库是公开仓库，构建与测试改用托管 runner；基准测试与对象存储的实测先不接：产品负责人 2026-11-18 定自托管 runner 先不接到本仓库，需要时在本机跑（S1-DEC-038 D21）。原 Kun 的检查钉在与原 runner 同一个系统版本上，并把 SDK 装到独立目录，避开托管镜像预装的更新的 SDK。
    7. 迁移任务只在一处改。 原仓库归档之前，迁移任务的文件仍在原仓库里改，冻结之后只随写明去处的说明改一次；最后一次同步把它们带进来，此后只在本仓库的过渡目录里改。过渡目录在最后一次同步合入之前不动，任务文件也在其中。
    8. 不借迁移公开新东西。 导入的内容限于两个来源仓库主干上已经公开的内容。迁移过程中新写的文档照现行规矩：不写未修复的安全问题的细节，不写私有仓库的内部实现。

    B1 合入时留下的一项已知失败：原 Kun 的集成测试要用的对象存储镜像已经没有公开来源，托管 runner 拉不到，5 个测试失败、6 个被当成没有容器环境而跳过；原 runner 靠本地缓存的镜像才通过。它与导入无关，不改导入的内容就修不了。产品负责人 2026-11-17 定：带着它合入，原仓库冻结归档之后在本仓库修，排在 B2 提升原 Kun 之前。在那之前，原 Kun 的构建与测试作业在主干上是红的，其余作业与原 Qian 的全部检查是绿的；碰到 _import/kun/ 的改动，要看这个作业里还原、构建与单元测试这几步的结果。现状：2026-11-17 已修绿（CavaiLAB/kun#7，集成测试改用有公开来源的 S3 兼容服务），原 Kun 随后由 CavaiLAB/kun#12 提到了仓库根。

    导入时原 Kun 还有两处在原仓库或仓库根的工作流里解决了：样例宿主的依赖撞上新公布的安全通告，在原仓库升级后再同步（idadawn/kun#62）；网关包的 NativeAOT 发布测试在托管 runner 上选中了预装的更新的 SDK，改为把 SDK 装到独立目录。原 Qian 的镜像自检没有接：它的脚本按仓库根取路径，在过渡目录里跑不了，留给 B3。

    #5 导入怎么核对

    B1 的 PR 合入之前逐项核对，结果写进 PR 正文。

    • 原 Kun 主干的头提交与原 Qian 主干的头提交都是导入分支的祖先；两边的提交数与来源仓库一致。
    • _import/kun/ 与 _import/qian/ 的树对象分别与原 Kun、原 Qian 主干头提交的树对象相同。仓库根在过渡目录之外的改动只有工作流、入口说明与必要的忽略规则，逐个列出。
    • 原 Kun 的版本标签都在，指向的提交与来源仓库相同。
    • 抽查文件的历史：对导入后的路径看得到导入前的提交。
    • 根目录的忽略规则与换行规则没有改变子目录里的文件：检出后工作区干净，没有本该跟踪却被忽略的文件。
    • 原 Kun 在 _import/kun/ 下构建并通过自己的全部测试；原 Qian 在 _import/qian/ 下通过它原有的全部检查。两者都以本仓库托管 runner 上的运行结果为准，不以本机为准。跑不起来的检查逐个列出原因与去处。
    • 过渡目录之下没有任何文件内容变化：工作流是在仓库根另写一份接上去的，原件留在原处不动。没有任何包改名。

    #6 与前端计划的交接

    前端的迁移由另一份计划负责，在 CavaiLAB/qian 的 docs/migration.md。产品负责人给它定的范围是只迁框架库。两份计划已经对齐，约定如下。

    去处内容
    迁往 CavaiLAB/qian前端框架的八个包、组件演练场、前端插件开发包、TypeScript 运行时，以及它们的门禁、工程配置与发布工作流
    留在本仓库全部 .NET 代码；外壳应用与外壳工具包；平台组件自带的三个界面包；参考应用的远程模块；文档站；命令行；声明式表面的校验库；契约、Schema、TCK；plugins/、profiles/；部署清单；现有的决策记录与设计文档；任务与看板（迁移期间随本仓库，最终放在哪个仓库待定）
    • 本仓库留一套前端工作区，按钉住的版本消费前端仓库发出的包。包的作用域跟所有者走，名字由前端计划定。
    • 两边都从原 Qian 的主干取源码。本仓库导入的是整棵树，迁往前端仓库的那些目录会跟着进来，它们在本仓库里只读：改前端去前端仓库改。
    • B11 就是前端计划里的「后端仓库切换」那一步，由前端计划的执行会话在本仓库做：等前端仓库以新名字发出第一批包，把迁走的目录从本仓库删掉，留下的界面改为消费已发布的包。开工前两边先对一次当时的主干在哪个仓库。
    • 留在本仓库的界面有一部分要打进宿主的镜像，前端包的版本升级因此会牵动镜像的构建，B3 并轨检查时把这条依赖算进去。

    #7 执行方式

    • 每一批一个执行会话，在本仓库的独立工作区里做，开 PR，不自己合并，不归档仓库，不改仓库设置。
    • 计划会话在合并之前复核每一批：照第 5 节或该批的标准独立重跑一遍，不采信执行会话的自述。
    • 合并由产品负责人发话。
    • 批次的状态记在对应的任务文件里。
