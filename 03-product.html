    #产品形态

    状态：2026-11-26 重写，2026-11-27 跟上产品负责人对待定事项的答复，以及同一天他给的产品页面的新方向。第 1 节列的是已定的事；其余标「提议」的没有拍板，标「延期」的写明了要先有什么。标法见平台做什么与设计理念开头。

    本文说的管理端、工作区服务、托管的 DSH 实例、确认卡、「待确认」的页面都是规划，还没有实现。已有的是本机能跑起来的 Web 端与桌面端的原型，见第 2 节。

    匠心是产品：Agent 工作区的 Web 端与桌面端、管理端、产品的插件、部署清单，代码在本仓库。它和 Kun、DSH 各管什么，见总体架构第 2 节。

    #1 已定

    • 人用平台，入口是 Agent 工作区。企业级平台不另做一套入口。
    • 两种扩展：在企业级平台上开发业务插件；给 Agent 增加组件。平台提供基础组件，并内置智能体、知识库模板等内容；企业级平台里有应用市场。
    • Agent 运行时用 DSH；界面外壳用 DSH 自己的客户端，Web 端与桌面端都是。
    • 客户可能用到两个端：Web 端和桌面端。管理端先不做，目录先建好；随生成应用的最小一圈开始做，放本仓库。
    • 产品名「匠心工业智能体平台」，用匠心的 logo；产品版本号用日历版本号。
    • 登录用 Kun 的身份服务。交付给客户的产品里不带另一套身份系统。
    • Kun 是通用的组件，不负责任何业务。最终的界面放在匠心，也可以放到另一个仓库。
    • 每人一个 DSH 实例。桌面端的跑在各人自己的电脑上；Web 端分成管理端与按需托管的 Agent 工作区两块，放在两个域名上，托管实例每个正在用的人一个。
    • 工作区的域名由匠心的工作区服务直接接，不经过 Kun 的网关；管理端的域名过 Kun 的网关。
    • 管理端也支持 Cordis，管理端的内容要能显示在 DSH 右侧的页签里。管理端只要浏览器一侧：界面是浏览器里的 Cordis 应用，页面是只有浏览器一半的 Cordis 插件。
    • 智能体生成的应用，界面只能是数据描述，由平台的渲染器画出来；生成的代码不当页面插件装。
    • 等人点头的事记在平台，确认卡的点击由浏览器带着本人的登录直接交给平台。审批时模型默认不参与，人点了才让它看。
    • 「待确认」做成页面插件，DSH 的右侧和管理端装同一份。
    • 标了要人确认的能力，调用方不是人本人时，平台自己不执行，等人点了才执行。等人点头的任务上的动作，缺省只能人做。
    • 确认卡的最小一圈先用替身演示，不等里程碑 M1。
    • 基础组件用 shadcn 这一套，样式用 Tailwind。
    • 部署有两种形态；提供多租户版和单租户版；不管哪一种，统一由管理端管理。先交付企业版与单机版两套，两套共用同一个 Kun 模型服务。
    • 平台上的系统，权限都走 Kun 这一套。
    • 整个平台只有一个 Kun 模型服务，各种部署、各个端、托管的工作区和应用都走同一套入口。模型由平台管理员统一配，用的人在可用模型的列表里选。
    • 登录以后，普通用户直接进工作区，管理员进管理端，入口页兜底。所有人的工作区用同一个域名，由工作区服务按人路由。
    • 桌面端走薄壳。
    • 托管实例：CubeSandbox 是首选，在 v0.8.0 上把托管实例试通以后定为默认（带条件：还没有在 v0.8.0 上试，现在还不是默认）；有 Kubernetes 的现场保留 Pod 作备选；空闲 30 分钟暂停，上限做成配置；用的人不能自己装插件，由管理端统一下发，桌面端可以自己装；以加固过的配置为基线，每次升级 DSH 重新验证。
    • Kun 保持现有基础框架和接口，继续负责认证、会话和权限。
    • 登录、工作区和管理端等产品页面统一放到匠心重新设计，旧布局和样式可以淘汰。页面由匠心出，接口由 Kun 出。Kun 里现有的租户与成员页、平台控制台、旧的应用外壳在匠心的管理端里重做；成员管理页放管理端，Kun 只出接口。
    • 匠心根据工业填报、管理和 Agent 工作区的实际场景制定自己的设计规范，Ant Design 仅供参考。规范的底稿见设计规范，等产品负责人看过才算数。
    • 前后端都要有面向开发者和 Agent 的文档、MCP 和 CLI 入口，让人能找到匠心组件、Kun 接口和可运行的示例，见在平台上做开发第 10 节。
    • 确认卡的样子与位置见第 5 节；金额大或风险高的审批，在平台自己的页面上再确认一次。

    下面两句是整理时的读法：

    • 「工作区」的页面，指匠心在 Agent 工作区里加的页面与插件，比如右侧页签里的页面、确认卡、「待确认」；外壳用 DSH 自己的客户端这一条已定，不受影响。
    • 新的登录页在匠心跑通以前，登录照现有的页面用；跑通以后旧页面退不退、什么时候退，到时候再问产品负责人。这是过渡安排。

    各个页面放在哪个应用里，见包与应用的去向。

    已定清单头两条里的称呼按现在的说法写，内容没有变（已定）。早先还定过一句话，没有被取消：收起对话区就是企业级平台。它在 DSH 的外壳下怎么落，延期，要先有提议，见第 9 节。

    #2 几个端

    端是什么Agent 在哪里跑现状
    Web 端的 Agent 工作区浏览器里用 DSH 自己的客户端，和 Agent 对话、办事托管在服务器上的 DSH 实例，每个正在用 Agent 的人一个，按需启动、空闲回收、有上限已有：apps/web/ 能在本机起一个单人的实例，用假模型。规划：按人托管的实例，把登录的人送进他自己实例的工作区服务
    Web 端的管理端多人用的网页应用，不需要 DSH 实例不跑 Agent规划。apps/console/ 现在只有说明
    桌面端装在电脑上的应用，外壳也是 DSH 的客户端本人电脑上的 DSH 实例已有：apps/desktop/ 是一个薄的 Electron 壳的原型，没有发布过。走薄壳（已定）
    移动端延期—延期，到里程碑 M7 做移动端审批时再定。已定的只说了 Web 端和桌面端两个端

    几条说明：

    • 为什么每人一个实例。 DSH 的一个实例只有一种调用方身份，就是实例的主人；会话里没有用户和租户，设置、插件、凭据整个实例共用。所以多个人靠实例隔开（已定）。
    • 为什么 Web 端分两块。 管理页面给很多人用，不该每人为它占一个实例。工作区里要渲染模型生成的内容，还要跑插件；万一被注入了脚本，不能让它带着登录态去调管理接口。所以两块放在两个域名上（已定）。
    • 两个端用同一份发行目录。 distribution/ 里是钉死版本的 DSH、产品的插件包和配置补丁，Web 端和桌面端都从它启动，所以跑的是同一份 DSH、同一个品牌包。
    • 单机版以桌面为主（已定）。单机版指什么，见总体架构第 5 节。
    • 托管实例（已定）。跑在什么里：CubeSandbox 是首选，它是一个开源的沙箱服务，每个沙箱是一台微型虚拟机；在 v0.8.0 上把托管实例试通以后定为默认（带条件：还没有在 v0.8.0 上试，现在还不是默认）；有 Kubernetes 的现场保留 Pod 作备选。空闲 30 分钟暂停，上限做成配置。用的人不能自己装插件，由管理端统一下发；桌面端可以自己装。以加固过的配置为基线，每次升级 DSH 重新验证。
    • 登录以后先到哪一页（已定）。普通用户直接进工作区，管理员进管理端，入口页兜底。所有人的工作区用同一个域名，由工作区服务按人路由（已定）。
    • 延期的。 实例怎么隔离、凭据怎么保管，要先有设计；桌面端怎么连平台，要先有设计。见第 9 节。DSH 的实例怎么和企业级平台对接，见 DSH 与企业级平台的对接。

    #3 Agent 工作区是入口

    人打开的是 Agent 工作区（已定）。它的外壳是 DSH 的客户端（已定）：一边是和 Agent 的对话，右侧可以打开页签。

    企业级平台没有另一个要人去记的入口，它出现在三个地方：

    • 右侧打开的页面。 管理端的内容要能显示在 DSH 右侧的页签里（已定）。应用、应用市场、集成、管理这些页面具体怎么放，延期，见第 3.2 节。
    • Agent 调用的平台能力。 Agent 查业务数据、办业务上的事，调的是登记在 Kun 能力目录里的能力。照已有的决策，它的有效权限不超过本人的权限与授给它的范围的交集；这一条还没有启用。DSH 自带的工具和本机的工具不在此列。
    • 业务插件运行的底座。 人开发的业务插件装在企业级平台上，装好就是能打开的应用，也是 Agent 能调用的能力。

    对话和右侧是连着的，下面几条是早先的提议；怎么落到 DSH 的客户端上，延期，和第 3.2 节一起定：

    • 右侧当前的页面和选中的记录，是 Agent 的上下文。
    • Agent 的结果可以落到右侧：打开页面、定位记录、给出草稿的预览。产品负责人举过的例子是「我想生成一个什么什么系统，然后在右侧可以生成界面并进行发布」；右侧显示的是渲染器按草稿画出来的界面（已定）。
    • Agent 要改数据或往外发内容时，在对话里出一张确认卡，人点了才执行，见第 5 节。

    #3.1 三种用法

    用法例子靠什么
    办公「本周逾期未到货的采购订单有哪些，给供应商起草催货消息」能力目录、权限判定、确认卡
    做应用「做一个设备点检应用」「给采购助手加上看合同条款的本事」构建闭环，见一切皆插件第 7 节
    管理「把维修工单装上」「把 ERP 的采购订单接进来」应用互通、历史系统接入

    #3.2 导航里放什么

    提议，2026-11-19 写的，早于外壳改用 DSH 的客户端。实际的导航以 DSH 的客户端为准，这六项怎么落进去，延期：要先把这份提议对到 DSH 的客户端上。

    入口里面有什么
    对话和自己的 Agent 说话。一个人有几个 Agent，在这里切换；历史会话也在这里
    应用租户里已经装的应用，和应用市场
    组件我的 Agent，它们各自的组件与授权范围，和组件库
    待确认Agent 要发出去的、别人的 Agent 发给我的、等我批准发布的
    集成历史系统的连接器
    管理租户、成员、权限、审计、模型与用量。按权限显示

    其中「待确认」已定做成页面插件，见第 5 节。

    #4 管理端

    管理端也叫管理系统，是 Web 端里不需要 DSH 实例的那一块，代码的位置是 apps/console/。

    已定的：

    • 界面不在 Kun。 Kun 只提供登录这类通用的组件，不负责业务；最终的界面放在匠心，也可以放到另一个仓库（已定）。管理端放本仓库（已定）。
    • 什么时候做。 随生成应用的最小一圈开始做（已定）。在那以前，「管理端先不做」这一条不变。
    • 用 Cordis，只要浏览器一侧。 界面是浏览器里的 Cordis 应用，页面是只有浏览器一半的 Cordis 插件。管理端不设多人共用的 Node 运行环境；带后端一半的插件只在各人的 DSH 实例里跑（已定）。同样的内容要能显示在 DSH 右侧的页签里（已定）。
    • 入口过 Kun 的网关（已定）。
    • 管理端统一管理。 不管哪一种部署，统一由管理端管理（已定）。两种形态、两个版本用同一个管理端，模型服务也在里面管（已定）。
    • Kun 里现有的界面。 登录、工作区和管理端等产品页面统一放到匠心重新设计，旧布局和样式可以淘汰（已定）。租户与成员页、平台控制台、旧的应用外壳不再在 Kun 里做，改在管理端里重做（已定）。成员管理页放管理端，Kun 只出接口，和角色授权页一样（已定）。登录页也在匠心重新设计，认证与会话仍由 Kun 负责（已定），过渡安排见第 1 节。
    • 设计规范。 匠心根据工业填报、管理和 Agent 工作区的实际场景制定自己的设计规范，Ant Design 仅供参考（已定）；管理是其中一类场景。规范还是底稿，见设计规范。
    • 模型服务管到哪。 模型清单、健康状态、开放范围和上下线在管理端里管；推理服务的部署与扩缩留在 GPUStack 自己的界面里，接口留出以后加（已定）。管理端里改模型的配置分两类：不改流量出口的，点了就生效、留审计；改出口的经评审（已定）。见总体架构第 2.2 节。

    提议的：

    • 管什么。 租户与成员、角色与权限、模型服务、插件与应用、品牌、DSH 的实例与版本、审计。产品负责人说的场景里，管理端还有应用市场：里面是做好的应用，用自然语言生成的应用也上架到这里，见工业智能制造第 2 节。其中租户与成员、角色授权、模型服务放在管理端里已定，见上；托管实例里的插件由管理端统一下发，也已定，见第 1 节；其余随外壳一起定。
    • 同一份页面两边都能装。 页面做成只有浏览器一半的页面插件，DSH 的右侧和管理端各有一个很小的适配把它挂进去；页面的数据走平台的接口，不经过 DSH 实例。「待确认」这一页已定两边装同一份；其余页面是不是也这样、两边的适配怎么写、页面的数据走哪条路，延期，要先有设计，先做出适配的样板。

    延期的：外壳怎么搭、页面怎么登记，要先有设计。

    试过的：2026-11-25 在本机不起 DSH 进程，只用静态文件搭了一个不带对话的 Cordis 应用，把本仓库现有的插件样板和品牌包原样装进去，能用。用的是假的平台接口。

    #5 确认卡与「待确认」

    Agent 要办的事里，有一些要人点头：起草的单据要落库，要往外发一条消息。平台来的审批任务也要人点头：流程走到某个人这一步。两种来路在产品里是同一样东西。

    在哪里是什么状态
    对话里确认卡。任务来了默认只出卡片，不自动让模型读它；人点了，Agent 才去看已定
    DSH 的右侧「待确认」页签，列出等我点头的全部任务已定
    管理端同一份「待确认」页面，在管理端里就是待办页。对话里的卡片要 DSH 开着才有，所以这里是兜底已定

    背后的规矩：

    • 等人点头的事记在平台，只有一份记录；一处办了，别处一起消失（已定）。
    • 确认卡的点击由浏览器带着本人的登录直接交给平台，不经过模型，也不经过 DSH 实例（已定）。
    • 标了要人确认的能力，调用方不是人本人时，平台自己不执行，先生成一条等人输入的任务；人点了，平台才执行（已定）。
    • 任务上的动作，比如同意、拒绝，缺省只能人做（已定）。

    卡片长什么样、出现在界面的哪几处（已定）：输入框上方显示最新的一条，右侧的「待确认」页签列出全部，对话里提到某条任务时带出同一张卡。卡片的内容按任务去平台取，不用模型写的文字（已定）。

    金额大或风险高的审批，在平台自己的页面上再确认一次（已定）。

    这些都还没有实现。先做的是确认卡的最小一圈，对应里程碑 M2，先用替身演示（已定），见路线第 2.1 节。演示用的那条要人确认的能力是「起草单据」，做成带业务的组件放本仓库，接在 Kun 定下等人输入的任务的契约之后做（已定）。用替身演示出来的只算演示可看，不算 M2 完成；M2 完成要等换成真的那条路（已定）。规则的展开见 Agent 协同第 4.2 节。

    #6 两种扩展

    用平台的人可以自己扩展平台，有两种办法（已定）：

    业务插件Agent 组件
    是什么在企业级平台上开发的插件加在 Agent 上的组件
    装上之后多一个能打开的应用，Agent 也多一组能调用的能力我的某个 Agent 多一样本事，比如一个技能、一个知识库

    平台提供基础组件，并内置智能体、知识库模板等内容；企业级平台里有应用市场，做出来的应用可以上架（已定）。两种扩展里各有什么、怎么发布，见一切皆插件第 2.1、5 节；怎么动手做，见在平台上做开发。

    #7 交付给客户的是什么

    • 名字与版本号。 产品叫「匠心工业智能体平台」，用匠心的 logo。产品版本号是日历版本号：vYYYY.M.D 正式版，vYYYY.M.D-N 补丁版，vYYYY.M.D-beta.N 测试版，月和日不补零，构建时注入（已定）。产品还没有发布过。
    • 两种形态，两个版本。 带模型推理的集群，或者不带推理、通过 API 接第三方的模型服务；提供多租户版和单租户版（已定）。
    • 企业版与单机版。 这是另一条线，说的是部署的规模：企业版跑在集群上，单机版一台服务器上能跑，平台自己的服务跑在单节点的 K3s 上，以桌面为主（已定）。
    • 先交付两套（已定）。企业版：集群、多租户、带推理。单机版：一台服务器、单租户、不带推理。别的组合先不承诺。两套共用同一个 Kun 模型服务。部署清单只有一套（已定）；两套各装哪些组件，延期，要先有设计。
    • 管理端统一管理。 不管哪一种，统一由管理端管理（已定）。

    三条线怎么分、各装什么，见总体架构第 5 节。

    #8 界面示意

    下面六张图是 2026-11-19 画的示意，不是最终设计。图里窗口的标题是当时对 Agent 工作区的叫法；实际的外壳是 DSH 的客户端，布局以它为准。图里的企业、人名与数据是虚构的。

    办公：问数据，办事情。 Agent 在本人的权限与授给它的范围之内查了两个地方的数据，把结果落到右侧的页面上；要发给企业外的人的消息，停在确认卡上等人点。

    做应用：一句话做应用。 Agent 先给方案，人确认之后才生成。草稿在右侧可以直接试用，旁边列出它包含什么、和别的应用有什么往来。发布要另外提交。

    给 Agent 增加组件。 每个 Agent 有自己的授权范围和一组组件。添加组件之前，先看得见它包含什么、需要什么；授权范围变大要本人确认。

    安装确认：应用互通看得见。 安装之前，管理员一次看清这个应用和别的应用之间的全部往来。见应用互通。

    历史系统：连接器。 一套历史系统一个连接器。三档接入各自开关；每项能力写明副作用、是否对 Agent 开放、是否要人确认；写操作缺省不开。见历史系统接入。

    待确认：发出去之前人审。 Agent 要发出去的内容先停在这里。确认的人看得到谁发给谁、正文、数据来源、对方要动用哪些能力。见 Agent 协同。
