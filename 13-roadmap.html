    #2 里程碑与工作线

    #2.1 里程碑

    路线重排过一次，最小的一圈提前（已定）：人用平台的入口是 Agent 工作区，入口这一圈不能等到最后才有。下表的顺序已定；每个里程碑都有一个能演示的完成标志。

    里程碑做什么完成标志
    M0 迁移收口Kun 的归并：两套后端代码并成一个仓库，发出合并后的版本Kun 已经发布合并后的稳定版；旧应用外壳按冻结的 Qian 0.2.1 归档验收，见 Kun 的外壳迁移决策
    M1 能问能查Agent 工作区接上平台；启用智能体主体；能力目录给 Agent 用，先只读；右侧的页面作为上下文用户问一个数据问题，Agent 在本人的权限与授给它的范围之内查到，并在右侧打开对应的页面；没权限的人来问，被拒绝并留审计
    M2 能办事写类能力；对话里的确认卡；高风险动作要人确认Agent 起草一张单据，人确认后落库，审计里看得到是谁确认的
    M3 一句话做应用按元数据读写业务记录；表单、列表与详情的渲染器；构建闭环；回滚业务人员用自然语言做出一个带表单、列表、权限的应用，经批准后在租户里可用
    M4 给 Agent 加组件我的 Agent；组件库；技能、子 Agent、知识库模板；社区组件的导入用户给自己的 Agent 装上一个技能和一个知识库，Agent 当场用上
    M5 应用互通与市场互通的声明与安装确认；流程；私有市场上架两个应用经事件和能力调用配合完成一件事，其中一个从私有市场安装
    M6 历史系统连接器的规范；第一档与第二档；一个参考连接器；装在内网的执行部分Agent 查到历史系统里的数据，并在人确认后写回一笔
    M7 协同与人审信箱；待确认；两道关口；移动端审批两个人的 Agent 在人审之下完成一次跨人协同
    M8 端与三级桌面端；设备接入；工站、产线、工厂一台设备上的 Agent 入网，接受分派并上报结果
    • M6 可以和 M3 至 M5 并行，它只依赖 M1 和 M2。
    • M7 的契约设计现在就可以开始：消息信封、审核状态。
    • Agent 之间协同的机制排在 M7（先后已定），按提议推进；设备上的本机模型等设备一侧用什么运行时定下来再定，排在 M8 之前（先后已定），设备一侧的运行时延期，要先有提议。
    • M3 依赖的东西是当前最大的一块没做的：按元数据读写业务记录，表单、列表与详情的渲染器。
    • M1 要三样东西各自先打通，再合起来演示：智能体主体、MCP 路由、Agent 工作区接上平台。
    • M7 一行里的「待确认」是排里程碑时写的。「待确认」这一页已定随确认卡的最小一圈先做，对应 M2，见下面的三条线。移动端延期，到 M7 做移动端审批时再定。

    产品负责人 2026-11-25 说了三个要实现的场景：管理端的应用市场与用自然语言生成应用，平台的定位，对话里弹出确认框直接审批。它们用到的东西排成三条线，里程碑的顺序不变（已定）：

    先后做什么做完能演示什么对应的里程碑
    第一条线确认卡的最小一圈：平台上等人输入的任务与推送，对话里的确认卡与「待确认」的页面，加一个要人确认的写能力Agent 起草一张单据，对话里出确认卡，人点了才落库；审计里看得到是谁点的M2
    第二条线生成应用的最小一圈：按数据描述读写业务记录的后端，数据描述的登记与版本；表单、列表的渲染器，组件库带上给 Agent 看的组件目录；管理端的外壳接上登录和真的接口；给 Agent 用的生成工具，即查控件、查数据、校验、预览、试发布；运行时安装数据描述的包，发布的审批和记录说一句话，右侧生成一个填报的日报，有表单、列表、权限；预览，发布到本租户，管理端的菜单里出现M3
    第三条线往后：流程（审批）、报表、市场（上架、授权、开通）、函数的沙箱、通知业务审批在对话里弹出来；汇总的日报；市场；带自己逻辑的应用M5、M7
    • M3 的例子里，「日报」先按填报的日报来排：每人每天填一张单子，主管能看、能汇总。按天汇总已有数据的那种日报，等报表和应用互通（已定）。
    • 第一条线不依赖第二条线。业务审批在对话里弹出来要等流程；在那之前，确认卡先用在 Agent 自己要办的事上。
    • 三条线只排了这三个场景要用到的东西，不改 M0、M1 在前的顺序（已定）。
    • 第一条线不等 M1 的智能体主体与 MCP 路由，先用替身演示，和 M1 并行；M1 做好以后替身撤掉（已定）。里程碑的顺序、M1 自己的内容与完成标志都不变，变的是第一条线不再等 M1 才开工。用替身演示出来的只算演示可看，不算 M2 完成；M2 完成要等换成真的那条路（已定）。
    • 替身指 M1 做好以前代 Agent 向平台提出请求的一方：实例里的工具调匠心的工作区服务，由它用自己的服务身份调平台，写明代谁提出。它演示得了人点了才落库、审计里看得到是谁点的；演示不了「Agent 以谁的名义」和权限取交集。做法与接口的形状是提议。
    • 第一条线里要人确认的那个写能力，演示用「起草单据」，做成带业务的组件放匠心，接在 Kun 的 S1-RT-041 定下等人输入的契约之后做（已定）。
    • 三条线里的东西都还没有实现。各项由哪个仓库承担已定：界面与渲染器归匠心，按数据描述读写业务记录的后端、流程、等人输入归 Kun。拆成任务，随照工作线重排看板一起做。

    各里程碑展开在：产品形态（M1、M2）、一切皆插件（M3、M4）、应用互通（M5）、历史系统接入（M6）、Agent 协同（M7）、工业智能制造（M8）。

    已定（2026-11-27）：

    2. 然后线 1，和线 2、3、4 里的契约部分并行。

    #2.4 产品页面放到匠心以后的三步

    已定（2026-11-27）：Kun 保持现有基础框架和接口，继续负责认证、会话和权限；登录、工作区和管理端等产品页面统一放到匠心重新设计。次序是：

    1. 先列清各个包的去向。匠心这边的清单见包与应用的去向；Kun 的包、已发布的包、文档、示例和站点导航在 Kun 的仓库里整理。
    2. 修订文档。
    3. 再用登录页跑通前后端流程。

    登录页是匠心第一处把自己的页面和 Kun 的接口从头接到尾的地方：页面在匠心，认证与会话在 Kun。跑通以前匠心这一侧要先有什么、哪些要等 Kun 的接口进公开契约，见包与应用的去向第 4 节。

    下面几条是整理时的读法：

    • 这三步和第 2.3 节的先后不冲突。登录页用的是 Kun 已有的认证与会话接口，不等权限的远程接口和模型服务的接口。
    • 2026-11-27 的答复里还定了认证页先做找回密码与验证码登录，其余几页随后；和新方向合起来读，是登录页先跑通，再做找回密码与验证码登录，其余随后。
    • 三步各拆成哪条工作线上的任务，随照工作线重排看板一起定。设计规范的底稿见设计规范，等产品负责人看过才算数。

    #3 顺序的理由

    • 最小的一圈为什么提前。 人用平台的入口是 Agent 工作区。入口、智能体主体、Agent 调用能力这一圈不通，后面的构建、互通、协同都没有地方落。所以先做只读的一圈（M1），再做写（M2），之后才是构建、组件、互通、历史系统与协同。
    • 确认卡为什么不等 M1。 先用替身，这一圈可以和 M1 并行；等 M1，它就排在 M1 后面。
    • 两个接口为什么排在前面。 这是第 2.3 节的理由：权限的远程接口、模型服务的接口是管理端、工作区服务和确认卡共用的。

    #4 风险

    风险应对
    文档先于代码太多，写的和做的对不上文档里区分「已有」与「规划」；每个里程碑完成时回头更新
    上游的 DSH 发版快，升级会让我们的插件和补丁悄悄失效版本钉死；升级照 DSH 更新之后做什么的步骤，逐项核对接触面
    最小的一圈依赖的东西多M1 只做只读；智能体主体、MCP 路由、Agent 工作区接上平台三样先各自打通，再合起来演示
    权限的远程接口迟迟不定，各个系统各做一套规矩已定：不论做什么系统，权限都走 Kun 这一套；接口排在工作线的前面
    人审成了走过场起步每条必审，并记下每条审了多久；放宽只能显式配置；审核界面把谁发给谁、要动用什么能力摆在最前面
    Agent 生成的应用质量参差确认方案、校验器、一致性测试、预览，四道关；发布之后可以回滚
    历史系统接入的成本被低估分三档，先做界面融合；一套系统一个连接器，能力一项一项放开
    被诱导的 Agent 越权，或者把内容发出去权限取交集；只许人做的能力不给 Agent；外部内容当数据；发出去之前人确认
