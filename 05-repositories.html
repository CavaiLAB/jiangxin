    Qian 架构决策记录（ADR）索引
    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单
    组件模型 v2：一切皆插件、声明式组件、一键安装、目录市场

    #1.1 组合体

    已定（2026-11-19 平台级裁定 P23、P24）：

    • 平台开发交付两样东西，一个 Agent 框架，一个企业级应用平台。最终是一体化的产品，jiangxin 仓库就是组合体。
    • 最终用户的使用界面是 Agent 平台，它的客户端基于企业级框架。企业级应用平台不另做一套入口。这一条 2026-11-20 被部分取代，见下。

    已定（2026-11-20 产品裁定 P37 至 P41）：

    • Agent 运行时用 DSH（P37）。界面外壳用 DSH 自己的客户端，网页与桌面都是；Qian 冻结在 0.2.1，组件以后缺哪个，按 DSH 的写法迁进自己的界面包（P38）。
    • 客户可能用到两个端：Web 端和客户端（桌面）。管理端先不做，目录先建好（P39）。
    • 产品名「匠心工业智能体平台」，用匠心的 logo，产品版本号用日历版本号（P40）。
    • 这批产品代码放进 jiangxin（P41）。

    由此，P24 里「客户端基于企业级框架」和据它写的「界面用 Qian 搭」被部分取代，这里原来的几条提议也跟着改写。逐条见那份裁定的第 2 节，没定的事在它的第 3 节。

    主页与文档站照旧在 jiangxin。组合体里现在有的东西都在仓库根下，都还没有发布过：

    目录放什么约定的入口
    distribution/发行目录，Web 端和桌面客户端共用：钉死版本的 DSH（0.2.2-rc.5）、以 tarball 装入的品牌包与插件包、按文件名叠加的配置补丁、启动器和启动前检查distribution/README.md，用 npm
    apps/web/Web 端：启动脚本，放在反向代理后面的配置与验证apps/web/README.md
    apps/desktop/客户端（桌面）：一个薄的 Electron 壳的原型，里面跑发行目录里的 DSHapps/desktop/README.md，用 npm
    apps/console/管理端，先不做，目录占位（P39）apps/console/README.md
    packages/品牌包 @jx/brand-theme；企业插件的样板 @jx/enterprise-workbench，数据是假的；界面组件包 @jx/ui-kit，按 DSH 的写法迁组件的地方packages/README.md，各包各用 pnpm
    tests/egress/外联检查：在不通外网的容器网络里看实例想连哪些地址tests/egress/README.md
    tools/mock-model/本机的假模型服务，本机试用和测试不需要真的模型与密钥tools/mock-model/README.md
    patches/对 DSH 源码的改动，一处一个补丁文件。现在只有两个样例patches/README.md
    contracts/以后从后端契约生成的类型，占位contracts/README.md
    brand/匠心 logo 的原图brand/README.md

    做法上的几条：我们的东西只有自己写的插件包和叠在 DSH 配置上的补丁，不改 DSH 的源码，绕不过去的改动一处一个补丁放进 patches/；DSH 的版本钉死，不写范围；以后直接引用 DSH 内部接口的代码收进一个包（提议名 dsh-compat），其余的包只引用它。这几条是工程上的做法，属于提议，不是产品负责人的裁定。

    #3 依赖方向

    • Kun 的框架包不依赖另外两个框架。跨服务的契约随 kun。
    • jiangxin 作为组合体，按钉住的版本装三个框架发布出来的包与镜像，不引用它们的源码；三个框架都不依赖 jiangxin（提议，见第 1.1 节）。2026-11-20 起它还按钉死的版本装 npm 上的 DSH（P37、P38）。
    • 留在 kun 仓库里的平台自带界面（应用外壳、组件自带的界面、参考应用的界面）按钉住的版本装 qian 发布的 npm 包，不引用 qian 的源码，见第 2.2 节。
    • qian 与 sanyuan-agent 只经运行时的接口和契约依赖 Kun 的服务，不引用 kun 的源码。
    • sanyuan-agent 对 Kun 的依赖只在接入平台时才有。它是独立运行的 SDK（已定），不接平台也能用。
    • 三个框架各自发包：Kun 发 NuGet 包，Qian 发 npm 包，SanYuanAgent 发 Python 包。使用方装包，不拉源码。
    • 跨仓库的源码引用会把两边的构建绑在一起，一边改了另一边就坏。这是来源仓库里已经吃过的亏，新仓库不再这么做。
