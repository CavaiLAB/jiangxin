    Qian 架构决策记录（ADR）索引
    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop
    部署：沿用现有 K3s / ArgoCD / Kustomize / Harbor 约定；Qian 独立命名空间 + 专属 PG/Redis；不以 per-tenant namespace 为默认
    阶段切分与 S1 范围：S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台；每阶段有可验收的退出标准
    库优先（Library-first）：每个 Qian 系统组件首先是可独立安装使用的 NuGet 包，其次才经清单成为插件；插件 = 库 + 清单

    #1 迁移的规矩

    1. 先建库写文档，代码分批迁。 迁入完成之前，来源仓库照常开发，在途的里程碑和任务不受影响。
    2. 一个来源仓库只冻结一次。 冻结窗口里来源仓库只读，迁完就在新仓库继续。
    3. 带着历史迁。 提交历史一起带过来，不做「复制一份文件重新开始」。
    4. 先并轨，后改名。 先让两边的代码在一条流水线上跑通，再一个域一批地归并和改名。
    5. 能验证才算完成。 原有的测试和门禁在新仓库里全部通过，才算一步做完。

    #2.1 里程碑

    路线重排，最小的一圈提前（已定）。原来的阶段 4 把智能体主体、协同、自然语言构建放在一起，排在最后；Agent 平台既然是最终用户的入口，就不能等到最后才有。下表的顺序已定；每个里程碑都有一个能演示的完成标志。

    里程碑做什么完成标志
    M0 迁移收口在做。后端归并，前端独立成库，引擎核心迁入，即上表的阶段 2、3。后端在途的里程碑照旧阶段 2、3 的完成条件
    M1 能问能查三栏工作台；启用智能体主体；能力目录给 Agent 用，先只读；工作区的页面作为上下文用户问一个数据问题，Agent 在本人的权限与授给它的范围之内查到，并在工作区打开对应的页面；没权限的人来问，被拒绝并留审计
    M2 能办事写类能力；对话里的确认卡；高风险动作要人确认Agent 起草一张单据，人确认后落库，审计里看得到是谁确认的
    M3 一句话做应用按元数据读写业务记录；列表与详情的渲染器；构建闭环；回滚业务人员用自然语言做出一个带表单、列表、权限的应用，经批准后在租户里可用
    M4 给 Agent 加组件我的 Agent；组件库；技能、子 Agent、知识库模板；社区组件的导入用户给自己的 Agent 装上一个技能和一个知识库，Agent 当场用上
    M5 应用互通与市场互通的声明与安装确认；流程；私有市场上架两个应用经事件和能力调用配合完成一件事，其中一个从私有市场安装
    M6 历史系统连接器的规范；第一档与第二档；一个参考连接器；装在内网的执行部分Agent 查到历史系统里的数据，并在人确认后写回一笔
    M7 协同与人审信箱；待确认；两道关口；移动端审批两个人的 Agent 在人审之下完成一次跨人协同
    M8 端与三级桌面端；设备接入；工站、产线、工厂一台设备上的 Agent 入网，接受分派并上报结果
    • M6 可以和 M3 至 M5 并行，它只依赖 M1 和 M2。
    • M7 的契约设计现在就可以开始：消息信封、审核状态。
    • M3 依赖的东西是当前最大的一块没做的：按元数据读写业务记录，列表与详情的渲染器。由 Schema 渲染的表单已有。
    • M1 要三样东西各自先打通，再合起来演示：智能体主体、MCP 路由、三栏工作台。

    各里程碑展开在：角色与产品形态（M1、M2）、一切皆插件（M3、M4）、应用互通（M5）、历史系统接入（M6）、Agent 协同（M7）、三种形态（M8）。

    里程碑怎么拆成任务、与后端在途的里程碑怎么衔接，待定，见第 5 节。

    #3 顺序的理由

    • 阶段 2 与阶段 3 可以并行。 Agent 引擎和后端是两套代码，互不依赖，引擎适合先走一遍迁移流程。引擎的改动频率在冻结之前再核对。
    • 阶段 3 最重。 两个后端有重叠的职责，归并是一个域一批地做。原定来源仓库这边正在推进的里程碑先收口、再进冻结窗口；2026-11-17 改为现在开始（P20）。
    • 前端原定排在后端之后，2026-11-17 改为同时开始（P21）。 原来的考虑是：后端各域的包名统一之后再动前端，文档站只改写一遍。同时开始之后，这一点不再自动成立。
    • 阶段 4 的设计可以早做。 协同消息信封这类契约的设计不依赖代码迁移，阶段 1 就可以开始；实现要等阶段 2、3 完成。
    • 最小的一圈为什么提前（2026-11-19）。 最终用户的入口是 Agent 平台。入口、智能体主体、Agent 调用能力这一圈不通，后面的构建、互通、协同都没有地方落。所以先做只读的一圈（M1），再做写（M2），之后才是构建、组件、互通、历史系统与协同。

    #4 风险

    风险应对
    新旧文档混着读会误解过渡目录里的原件与平台级裁定有出入时，以平台级裁定为准；来源仓库的说明文档指向新仓库
    迁移期间两处同时开发，代码分叉一个来源仓库只冻结一次，窗口里来源仓库只读
    归并时把在用的行为改坏两边都有实现的，留有宿主在用、有测试覆盖的一边；每一批归并之后全量测试通过才算完成
    改名让按名字判定的门禁不声不响地失效改名之前先把门禁换成显式的档位表，并带自测
