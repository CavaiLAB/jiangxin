    Qian 与 Kun 的关系：Kun 是底座 SDK，Qian 内核自成一层
    插件模型：kind × role × distribution 三轴，平台自带能力也是插件，第三方代码永不进共享进程
    内核边界与 S1 服务拆分：内核只留契约、强制执行点与注册表；S1 共 5 个可部署服务 + 18 个系统插件
    数据库与租户隔离：PostgreSQL 唯一一等库；默认共享库 + RLS；schema-per-service
    身份与 SSO：基于 OpenIddict 自建 qian.identity 作平台唯一 issuer，外部 IdP 一律做成连接器插件
    鉴权模型：Kun 只加判定端口，Qian 自建权限引擎；权限不进令牌；UI/API/MCP 唯一判定入口
    配置中心：Apollo 作 L1 共享组件，自研 AOT 友好的 .NET provider；只存非敏感配置与密钥引用；租户级配置不进 Apollo
    事件与消息：RabbitMQ 上 K3s；修复 Outbox 丢消息与至少一次语义；事件信封对齐［下游智能体平台］契约
    审计：只留一套——命令级哈希链落 PostgreSQL + 实体级同事务写入；actor 含 agent
    网关分层：Traefik（北向入口）→ qian.gateway（Kun.Gateway 加固，业务 API 边界）；Higress 只管模型与 MCP 流量
    元数据与动态数据层：元数据驱动运行时为主；动态表走「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为可选薄壳
    流程引擎：自研 .NET 轻量审批内核；简单/标准流程合并为一套 JSON 定义；S2 只做节点树视图设计器
    前端与［前端框架］：React 19 + Vite + Tailwind v4 + Base UI + shadcn 源码自有化；六层分层；一套表单/表格/弹层引擎；Module Federation 2 外壳
    应用市场形态：应用 = 插件包（bundle）；template / managed 两种分发；S1 就定下包格式、升级与冲突处理、权益 API
    模型服务网关：并入团队现有 Higress / MaaS 基础设施；GPUStack 作 OpenAI 兼容上游 + Provider Adapter；不自写模型代理；不把 SSO 交给 Higress
    与［下游智能体平台］的边界：Qian = 能力提供方 + 业务主数据权威；［下游智能体平台］ = Agent 运行时 + AI 资产控制面；Qian 不写任何 Agent loop

    #匠心智能体平台

    企业级的 AI 原生平台。人用自然语言说清要什么，智能体把它落成可运行的系统；系统上线后在人的反馈里继续改进。

    状态：规划稿（2026-11-20）。 本仓库是平台的主页与总览，也是把 Agent 框架与企业级框架拼成一个产品的组合体（已定）。组合体的代码在本仓库，见下面的匠心工业智能体平台；三个框架的代码在各自的仓库里，迁入与归并按路线分阶段进行。文档里标「已定」的是产品负责人已经裁定的事，标「提议」「待定」的还没有拍板。

    #这是什么

    过去企业搭业务系统的省力办法是低代码或无代码平台：把系统拆成表单、列表、流程这些可配置的元数据，由人在设计器里拖拽出来。匠心保留「系统由声明式元数据描述」这一点，把写元数据的人换成智能体。人负责提出意图、判断结果对不对，智能体负责理解、生成和执行。按设计，每一步都受权限、审计和人工审核约束。

    平台面向组织，不面向个人消费者。单点登录、权限、审计、私有部署是底线要求；交付给客户的可以是多租户的版本，也可以是单租户的版本（已定）。它建在 Kubernetes 与微服务之上。

    #两种角色，一个入口

    平台上分两种角色（已定）：

    平台开发最终用户
    做什么开发 Agent 框架与企业级应用平台基于 Agent 平台，在企业级框架上构建自己需要的软件。不负责框架与核心的开发，只使用工具
    交付或产出两样东西：Agent 框架（Agent 运行时加 Agent 平台；运行时 2026-11-20 定为 DSH，SanYuanAgent 以后怎么接待定），企业级应用平台（Kun 加 Qian）。两者互补，最终是一体化的产品两种扩展：基于企业级应用平台开发的业务插件；加在 Agent 上的组件

    最终用户的使用界面是 Agent 平台（已定）。提议它是一个三栏的工作台：左边是导航，中间是和 Agent 的对话，右边是工作区，企业级应用平台的页面在工作区里打开。下图是示意，不是最终设计，图里的企业、人名与数据是虚构的。

    #三元全智生命体

    平台的设计理念叫「三元全智生命体」，三个词各管一件事：

    词管什么在平台里是什么
    三元躯体，结构怎么融合：云边端；工蜂、章蜂、群蜂；人机物平台底座，也就是企业级框架：Kun（后端）与 Qian（前端）
    全智心智，智能到什么水平：从工具到能自己做主的智能体智能体引擎 SanYuanAgent
    生命体活法，以什么状态运转：自主、代谢、进化平台上长出来的系统与智能体。它们在「意图 → 决策 → 行动 → 反馈」的闭环里运转，每转一圈改进一点

    展开见理念。

    #三种形态：工站、产线、工厂

    平台从工业智能体走向工业生命体。「工蜂、章蜂、群蜂」对应工站、产线、工厂三级，每一级是一种智能体，SanYuanAgent 是它们的大脑（已定）：

    层级形态做什么
    工站（工蜂）具身智能体感知工件，调用技能，控制工具完成作业
    产线（章蜂）协同智能体协调工序、工站和物料，保持生产节拍
    工厂（群蜂）超级智能体协调跨系统制造任务，支撑物理 AI 研发

    每一级的技术架构、与三个框架怎么对应，见三种形态。

    #三个框架

    框架角色技术栈仓库来源代码现在在哪
    Kun企业级后端框架：租户、身份、权限、数据、事件、审计、网关、组件运行时与能力目录；模型服务也由它提供.NET 10CavaiLAB/kun两套后端代码归并而成：.NET 微服务框架与建在它上面的平台层CavaiLAB/kun 的 src/ 放 .NET 项目；组件清单、profile 和宿主分别在根目录的 plugins/、profiles/ 和 hosts/
    Qian前端框架：设计令牌、组件库、应用外壳、微前端、由 Schema 驱动的界面TypeScript、ReactCavaiLAB/qian后端仓库前端工作区里的框架库CavaiLAB/qian；已发布到 GitHub Packages，现在是 0.2.1，冻结在这一版（2026-11-20 定）
    SanYuanAgent智能体引擎，一个独立运行的 SDK：推理循环、工具、技能、记忆、沙箱、模型路由。云上、桌面和机器人这类边缘设备都要用到它（2026-11-20 起，Web 端和客户端的 Agent 运行时改用 DSH）Python 3.12CavaiLAB/sanyuan-agent私有产品里的 Python Agent 引擎核心已在 CavaiLAB/sanyuan-agent，服务层与媒体适配层还在原来的私有仓库

    三个框架各用一种主语言、各占一个仓库，彼此只经契约和发布出来的包往来，不做跨仓库的源码引用。

    #匠心工业智能体平台

    组合体现在放的是「匠心工业智能体平台」：用开源的智能体运行框架 DSH 做 Agent 运行时和界面外壳，在它上面加企业要用的能力，换上匠心的名称、logo 与主题色。客户可能用到 Web 端和客户端（桌面）两个端，管理端先不做；产品版本号是日历版本号 vYYYY.M.D。这几条是产品负责人 2026-11-20 定的。第一版是不是全部基于 DSH、登录与策略由哪个后端提供、SanYuanAgent 以后怎么接，都还没有定。见 2026-11-20 产品裁定。

    目录放什么
    distribution/发行目录：钉死版本的 DSH、品牌包与插件包、配置补丁、启动器。Web 端和客户端共用
    apps/web/Web 端
    apps/desktop/客户端（桌面）：一个薄的 Electron 壳
    apps/console/管理端，先不做
    packages/品牌包、企业插件的样板、界面组件包
    tests/egress/外联检查
    tools/mock-model/本机的假模型服务

    这些代码都还没有发布过。DSH 按 MIT 许可使用，产品里带着它的版权与许可声明。

    旧应用外壳保留在现网，本次迁移按 Qian 0.2.1 归档验收并保留数据库。见旧应用外壳迁移裁定 P42。

    #总体结构

    SanYuanAgent 是独立运行的 SDK（已定）。提议：不接平台也能运行；装在设备上时只向外连到平台；设备上有本机模型时，断网后本机的活照干。见总体架构第 5 节。

    2026-11-20 补：匠心工业智能体平台的 Agent 运行时与界面外壳改用 DSH（已定）。上图是这之前的规划，SanYuanAgent 在里面的位置、登录与策略由哪个后端提供，怎么改待定。

    #四条主线

    1. 一切皆插件。 没有只能打补丁的特权内核。租户、身份、权限这些平台能力和每一个业务功能都是插件：一个文件夹、一份清单、若干声明式表面，一条命令安装。技能、子 Agent、命令、钩子、MCP 声明沿用社区通行的文件格式，目标是开源组件目录里的现成组件过了校验就能装进来（导入器是规划）。见一切皆插件。
    2. 自然语言构建。 系统是一组插件，插件主要由声明式表面组成，所以构建系统这件事可以交给智能体：它按人的意图生成或修改表面，经过校验、预览和人工批准后装进租户。
    3. 每个人都有 Agent，协同必经人审。 每个人可以有一个或多个 Agent。发给每个 Agent 的内容、每个 Agent 发出去的内容都要由人审核，起步两道都必审（已定）。提议 Agent 之间不直接互调，往来的内容走平台的信箱。见 Agent 协同。
    4. 云原生与多租户。 运行在 Kubernetes 上，可部署单元由 profile 定义；租户隔离、零信任的服务间通信、审计链贯穿全栈。见总体架构。

    另有两件已定的事：发布的应用之间可以互相通讯，缺省是目录里看得到、调用与订阅按声明经批准放行，见应用互通；企业里已有的历史系统经连接器接进来，并融合进 Agent 框架，见历史系统接入。
