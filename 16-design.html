    #设计规范

    状态：底稿，通篇是提议，等产品负责人看过才算数。2026-11-27 起写。

    和这份规范直接有关的已定事项是这几条，都出自产品负责人：匠心要根据工业填报、管理和 Agent 工作区的实际场景制定自己的设计规范，Ant Design 仅供参考；登录、工作区和管理端等产品页面统一放到匠心重新设计，旧布局和样式可以淘汰；基础组件用 shadcn 这一套，样式用 Tailwind；产品名「匠心工业智能体平台」，用匠心的 logo。文中照引的已定事项都标了「已定」，其余都是提议。

    这一版只搭提纲：每一节写要回答的问题，加上从现有文档能直接得出的内容。具体的色值、字号、间距这些数值都还没有设计，写「待设计」。

    #1 这一篇回答什么

    • 匠心的界面长什么样、为什么这样，给做界面的人和写界面的编码代理当依据，也当验收的依据。
    • 管到的界面：认证页（登录、选择租户等）、管理端、Agent 工作区里匠心自己加的页面与插件、智能体生成的应用由渲染器画出来的界面。DSH 自己的客户端不在里面，它和本规范的关系见第 8 节。产品负责人说的「工作区」的页面，这里读作匠心在 Agent 工作区里加的页面与插件，外壳仍是 DSH 的客户端（已定），这是整理时的读法。
    • Ant Design 仅供参考（已定），本规范不照搬它的条目。参考它的什么、不参考什么，在每一节里写明理由。

    要回答的问题：

    • 规范分几层，每层的东西放在哪里（文档、@jx/ui-kit 里的样式变量、组件）？
    • 怎么验收一个页面符合规范：看什么、用什么检查？

    #2 三类场景

    规范从这三类场景出发（已定）。每一类先写现有文档里已经有的界面与约束，再列要回答的问题。

    #2.1 工业填报

    现有文档里有的：

    • 第一个工业参考应用做生产日报的填报，再接到排产（已定）。日报先按填报的来排：每人每天填一张单子，主管能看、能汇总（已定）。见工业智能制造第 2 节。
    • 智能体生成的应用，界面只能是数据描述，由平台的渲染器画出来（已定）。所以填报界面的规范要能落到渲染器上，而不是只给手写的页面用。
    • 车间里的系统包括设备、工艺、质量、排产、仓储这一类；现场分工站、产线、工厂三级（已定）。
    • 插件样板里有设备台账的筛选与表格，数据是假的，见企业插件样板。

    要回答的问题：

    • 填报的人在哪里填：办公室的电脑、车间里的终端、平板、手机？各要支持到什么程度？
    • 车间里的终端与大屏要不要单独的版式：字号、触摸目标、戴手套操作、强光下的对比度？
    • 一张单子很长、字段很多时怎么分组；批量录入、连续录入怎么做，键盘能不能一路填完？
    • 数值、单位、班次、日期时间这些工业里常见的字段，输入与显示的统一写法。
    • 断网或提交失败时，已经填的内容怎么保住。

    #2.2 管理

    现有文档里有的：

    • 管理端是多人用的网页应用，不需要 DSH 实例；界面是浏览器里的 Cordis 应用，页面是只有浏览器一半的 Cordis 插件（已定）。见产品形态第 4 节。
    • 放进管理端的页面里已定的有：租户与成员、角色授权、模型服务、托管实例里插件的下发；「待确认」在管理端里就是待办页（已定）。场景里还有应用市场（已定）。
    • 管理端的内容要能显示在 DSH 右侧的页签里（已定）。所以同一个页面要在两种宽度下都能用。
    • 改模型的配置分两类：不改流量出口的，点了就生效、留审计；改出口的经评审（已定）。界面上要分得出这两类。

    要回答的问题：

    • 密集的表格：行高、对齐、数字列、排序与筛选、分页还是滚动、批量操作放在哪？
    • 列表、详情、表单之间怎么跳，在右侧页签那么窄的地方怎么退化？
    • 危险操作、要评审的操作、立即生效的操作，在界面上怎么区分？
    • 按权限显示：没有权限的入口是藏起来还是置灰？（判权限在后端，界面只决定显示，见总体架构第 2 节。）

    #2.3 Agent 工作区

    现有文档里有的：

    • 外壳是 DSH 自己的客户端：一边是和 Agent 的对话，右侧可以打开页签（已定）。见产品形态第 3 节。
    • 确认卡的样子与位置（已定）：输入框上方显示最新的一条，右侧的「待确认」页签列出全部，对话里提到某条任务时带出同一张卡；卡片的内容按任务去平台取，不用模型写的文字。金额大或风险高的审批，在平台自己的页面上再确认一次（已定）。见产品形态第 5 节。
    • 做应用时，右侧显示的是渲染器按草稿画出来的界面（已定）。
    • 匠心在工作区里加的东西是 DSH 的插件，品牌包换掉了名称、标志、主题色和文案。

    要回答的问题：

    • 匠心加的页面、右侧页签里的页面，怎么和 DSH 自己的界面看起来是一个产品？
    • 确认卡：信息的先后（谁、要做什么、动到哪些数据、风险多大）、按钮的文字与位置、处理过以后的样子。
    • 要让人看得出哪些内容是模型写的、哪些是平台给的，尤其在审批的地方。
    • 生成中的草稿和已经发布的应用，界面上怎么区分。

    #3 基础层

    每一项都待设计。从现有的东西能得出的写在「现在」一列。

    项要回答的问题现在
    色彩品牌色、语义色（成功、警告、错误、信息）、中性色各几级；工业现场的告警色怎么用；对比度够不够品牌包里的主题色是匠心红加安全帽黄，从 logo 取样的初稿，深浅两种模式各一套。色值待设计
    字体中文、英文、数字各用什么字体；等宽数字；字号分几级待设计
    间距基准单位与倍数；页面、卡片、表单、表格里的间距待设计
    圆角分几级，各用在哪待设计
    密度要不要分宽松与紧凑；管理端的表格、车间的终端各用哪一种待设计
    深浅色两种都做还是先做一种；跟系统走还是让人选品牌包深浅两种模式都有。认证页与管理端待设计
    图标用哪一套图标、线性还是面性、尺寸分几级；工业里的设备、状态图标待设计

    这些落在哪里也要定：提议做成样式变量放在 @jx/ui-kit 里，认证页、管理端、匠心的插件用同一份；在 DSH 里跑的插件，变量要接到 DSH 的主题上。

    #4 组件层

    现在有的（已有）：@jx/ui-kit 里有 shadcn 生成、按 DSH 的规矩适配过的五个基础组件（带搜索的选择器、下拉选择、日期选择、单选组、多行输入），手写的抽屉和数据表格的最小版本，样式是带 jx: 前缀的 Tailwind。见界面包的说明。

    已定的：基础组件用 shadcn 这一套，样式用 Tailwind；组件放在 @jx/ui-kit。

    要回答的问题：

    • 规范里的每个组件，对应 @jx/ui-kit 里的哪一个；规范写什么（用法、状态、文案），组件包里写什么（属性、实现）？
    • 认证页与管理端不在 DSH 里跑，组件包现在有几处依赖 DSH，怎么分开（见包与应用的去向第 3 节）？
    • 渲染器画数据描述的应用时用哪些组件；Agent 生成界面时看的组件目录从哪里来？
    • 缺的组件按什么顺序补：先补登录页和日报填报用得到的。

    #5 页面模板

    每个模板写：用在哪、版式、有哪些状态（加载、空、错误、没有权限）、在窄屏和右侧页签里怎么退化。都待设计。

    模板用在哪现在知道的
    登录认证页族：登录、选择租户、强制改密、找回密码页面放匠心重新设计、认证与会话由 Kun 负责（已定）；先用登录页跑通前后端流程（已定）。按服务端回的下一步推进、防止猜出账号存不存在、错误按结构化错误的错误码分支，这些是 Kun 认证页规格（草案）里的规则，页面要照着显示
    列表管理端的租户与成员、模型、插件，填报应用的列表待设计
    详情一条记录的详情，管理端与填报应用待设计
    表单填报、管理端的编辑待设计。生成的应用由渲染器画表单，模板要能落到渲染器上
    工作区右侧页签里的页面、确认卡、「待确认」外壳是 DSH 的客户端；确认卡的位置已定，见第 2.3 节

    #6 可访问性与键盘操作

    现有的：

    • 界面对着 ISO/IEC 40500:2025，即 WCAG 2.2，见遵循的标准第 2、3.9 节。匠心现在没有自动的无障碍检查，界面只在网页端核对过。
    • @jx/ui-kit 的组件给读屏的名字由调用方给，日期选择怎么拼读屏的名字写在它的说明里。

    要回答的问题：

    • 做到 WCAG 2.2 的哪一级；怎么验收（自动检查加人工抽查）？
    • 键盘：表单一路填完、表格里移动与选中、确认卡上同意与拒绝的快捷键要不要有、焦点去哪？
    • 触摸目标的最小尺寸，车间终端要不要更大？

    #7 多语言

    现有的：品牌包做了中文与英文两份换过品牌的语言包；DSH 自带的其余语言没有换品牌。

    要回答的问题：

    • 先支持哪几种语言；繁体中文要不要？
    • 文案的口吻与用词表：按钮用动词、错误怎么说、术语和术语表对齐。
    • 日期、时间、数字、单位的显示跟语言走还是跟租户走；接口里照 ISO 8601 等写法，见遵循的标准第 3.8 节。

    #8 与 DSH 自带界面的关系

    此前定的做法（2026-11-27 认可）：界面上 DSH 自带的控件直接用 DSH 的；DSH 没有的基础组件用 shadcn 加 Tailwind 补进 @jx/ui-kit；弹窗的壳用 DSH 的；Tailwind 带前缀。抽屉的壳也用 DSH 的、Tailwind 只在组件包里用，是照在 DSH 里试过的结果定的做法。

    要回答的问题：

    • 新的规范以后，这几条在 DSH 里跑的插件上还照旧吗？认证页和管理端不在 DSH 里跑，用不上 DSH 的控件，它们和工作区里的插件怎么保持一致？
    • 品牌包改 DSH 的主题色到什么程度，和规范的色彩怎么对齐？
    • DSH 升级以后界面变了，怎么发现我们的页面跟不上了（见 DSH 更新之后做什么）？

    #9 参考

    • Ant Design 的设计基础，仅供参考（已定）。参考的是它怎么组织一套企业级的设计规范；具体的条目照匠心的三类场景重新定，不照搬。
    • Kun 的认证页规格（草案）：页面要显示的状态与错误、按下一步推进的规则，见 Kun 的仓库。它里面的样式取值来自已归档的前端框架，旧布局和样式可以淘汰（已定）。

    #10 接下来

    都是提议：

    1. 产品负责人看这份提纲，指出哪几节的问题要先回答。
    2. 先把基础层和登录模板做出来，用在登录页跑通前后端流程上（见路线第 2.4 节）。
    3. 再做列表、表单两个模板，用在日报填报上。
